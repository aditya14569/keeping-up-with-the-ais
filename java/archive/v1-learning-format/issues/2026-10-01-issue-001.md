# Part 1 · Learn

## 🗺️ The map: Java 8 → 27, and what actually matters

<span class="tag learn">CATCH-UP</span><span class="tag learn">~10 MIN</span><span class="tag learn">LEVEL 3</span>

**If your mental model of Java is "Java 8 with Spring," you're not behind on syntax. You're behind on a whole way of writing Java.** Nineteen releases have shipped since Java 8. Most changes are small, but a handful change how you'd design a service from scratch. Even Java 17 is no longer new: Oracle's Premier Support for it ended in **September 2026**. [(Oracle support roadmap)](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)

Today is the map. The next few issues zoom into each region.

### First, how Java ships now

Since Java 10, there's been a **feature release every six months** (March and September) and a **long-term support (LTS)** release every two years. Most companies run only LTS versions in production. Non-LTS releases are where features mature. [(Oracle support roadmap)](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)

<div class="box jargon" markdown="1">
**📖 Jargon buster**

- **JEP** (JDK Enhancement Proposal): the design document behind each feature. "JEP 444" is how Java people refer to virtual threads.
- **Preview feature:** fully built but not final. It's off unless you pass `--enable-preview`, and it may change. Don't ship previews to production.
- **Incubator:** an experimental *API* in a `jdk.incubator.*` module, one step before preview.
- **LTS:** a release that vendors patch for years. Non-LTS releases get about six months of updates.
</div>

### Big idea #1: data-oriented Java

Records, sealed types and pattern matching are three features designed to work as one. Together they let you say **"a Shape is exactly a Circle or a Square, nothing else"**, and the compiler holds you to it.

```viz:codecompare
title: "Same logic, two eras"
left:
  title: "Java 8: classes + instanceof chains"
  code: |
    abstract class Shape {}
    final class Circle extends Shape {
      final double r;
      Circle(double r) { this.r = r; }
      // + equals, hashCode, toString…
    }
    // Square: same again…

    double area(Shape s) {
      if (s instanceof Circle) {
        Circle c = (Circle) s;
        return Math.PI * c.r * c.r;
      } else if (s instanceof Square) { … }
      throw new IllegalArgumentException();
    }
right:
  title: "Java 21+: sealed + records + switch"
  code: |
    sealed interface Shape
        permits Circle, Square {}
    record Circle(double r)
        implements Shape {}
    record Square(double side)
        implements Shape {}

    double area(Shape s) {
      return switch (s) {
        case Circle c ->
            Math.PI * c.r() * c.r();
        case Square q ->
            q.side() * q.side();
      }; // no default needed: the
    }    // compiler knows every case
note: "Add a `Triangle` to the sealed interface and every `switch` that doesn't handle it **stops compiling**. The Java 8 version would fail at runtime, in production."
```

That's the payoff: **exhaustiveness checking**. In a payments service, `sealed interface PaymentResult permits Approved, Declined, NeedsOtp` means nobody can forget the OTP branch. Records give you `equals`, `hashCode`, `toString` and accessors for free. Their fields are final, so they're a natural fit for DTOs, events and value types.

### Big idea #2: concurrency got cheap again

For 20 years, a Java thread was a thin wrapper over an OS thread: about a megabyte of stack, and expensive to create and to switch between. So we pooled them, and when pools ran dry we reached for reactive frameworks. **Virtual threads (Java 21)** are managed by the JVM. When one blocks on I/O, the JVM parks it and frees the OS thread underneath for other work.

```viz:layers
title: What runs where with virtual threads
layers:
  - label: Your code, one virtual thread per request
    sub: "millions possible, cheap to block"
  - label: JVM scheduler (a ForkJoinPool)
    sub: mounts/unmounts virtual threads
    highlight: true
  - label: Carrier threads (platform threads)
    sub: "≈ one per CPU core"
  - label: OS threads & CPU cores
    sub: what actually executes
taper: 18
```

```viz:codecompare
title: "Calling a slow API for 10,000 orders"
left:
  title: "Java 8: a bounded pool of OS threads"
  code: |
    ExecutorService pool =
        Executors.newFixedThreadPool(200);
    for (Order o : orders) {
      pool.submit(() -> callPaymentApi(o));
    }
    // 200 run at once; the other
    // 9,800 wait in the queue
right:
  title: "Java 21+: one virtual thread per task"
  code: |
    try (var exec = Executors
            .newVirtualThreadPerTaskExecutor()) {
      for (Order o : orders) {
        exec.submit(() -> callPaymentApi(o));
      }
    } // close() waits for all tasks
    // all 10,000 can wait on I/O at once
note: "Illustrative. Virtual threads help **I/O-bound** work (HTTP, JDBC, queues), not CPU-bound number crunching. The real limit moves to what you call: the payment API and your connection pool still need explicit limits."
```

### Big idea #3: the small wins you'll use every day

None of these will change your architecture, but together they remove a surprising amount of noise from everyday code.

```viz:codecompare
title: "Everyday code, then and now"
left:
  title: "Java 8"
  code: |
    Map<String, List<Order>> byCity =
        new HashMap<String, List<Order>>();

    String sql = "SELECT id, total\n" +
                 "FROM orders\n" +
                 "WHERE city = ?";

    String label;
    switch (status) {
      case NEW:  label = "Pending"; break;
      case PAID: label = "Done";    break;
      default:   label = "?";
    }
    Order last = list.get(list.size() - 1);
right:
  title: "Java 21+"
  code: |
    var byCity =
        new HashMap<String, List<Order>>();

    String sql = """
        SELECT id, total
        FROM orders
        WHERE city = ?
        """;

    String label = switch (status) {
      case NEW  -> "Pending";
      case PAID -> "Done";
      default   -> "?";
    };
    Order last = list.getLast();
note: "`var` (10), text blocks (15), switch expressions (14) and `getLast()` from sequenced collections (21). A forgotten `break` in the old switch silently falls through; the arrow form can't."
```

A few rules of thumb from teams that adopted these:

- **Use `var` when the right-hand side already says the type** (`new`, factory methods). Avoid it when the type is the point, like `var result = service.process(x);`.
- **Text blocks strip common indentation for you**, so keep the closing `"""` on its own line, aligned with the content. Pair them with `.formatted(...)` for simple templating.
- **Switch expressions must be exhaustive.** With enums, leaving out `default` means a new enum constant becomes a compile error, the same safety net sealed types give you.

### Your upgrade path, if you're on 8 or 11

| Step | What to do | Why |
|---|---|---|
| 1 | Upgrade **build plugins and libraries** first (Lombok, Mockito, Jackson, ByteBuddy, your ORM) | Most "Java broke my app" errors are old libraries poking at JDK internals |
| 2 | Move the JDK to **17**, then **21/25**, running tests at each stop | Smaller jumps make failures easier to pin to a cause |
| 3 | If you use Spring: **Boot 2 → 3** (`javax` → `jakarta`), then **3 → 4** | Boot 3 requires Java 17; the namespace change is mechanical but touches everything |
| 4 | Turn on modern features **gradually**: records for new DTOs, switch expressions in new code | No need for a big-bang rewrite |
| 5 | Try **virtual threads** on one I/O-heavy service, with pinning monitoring (JFR `jdk.VirtualThreadPinned`) | Measure before and after; limit downstream calls explicitly |

Oracle's migration guide lists removed APIs and tools, release by release. Read the sections for every version you're skipping. [(JDK 25 Migration Guide)](https://docs.oracle.com/en/java/javase/25/migrate/getting-started.html) The JFR event recommendation comes from InfoQ's production checklist. [(InfoQ)](https://infoq.com/articles/virtual-threads-after-jdk24)

<div class="box realworld" markdown="1">
**🌍 In the real world: Netflix and the missing lock**

Netflix moved Spring Boot 3 services (embedded Tomcat) to Java 21 virtual threads and hit **intermittent hangs**: instances stopped serving traffic, with thousands of "blank" virtual threads in their dumps. The cause was **pinning**. Virtual threads that blocked *inside `synchronized` blocks* couldn't release their carrier threads, so the few carriers filled up and everything stalled. [(InfoQ on Netflix's write-up)](https://www.infoq.com/news/2024/08/netflix-performance-case-study/)

**JEP 491 (JDK 24)** fixed most of this. Virtual threads can now unmount while inside `synchronized`. [(JEP 491)](https://openjdk.org/jeps/491) A 2026 InfoQ review recommends JDK 25 LTS as the first LTS with that fix. Pinning can still happen in native frames, in class initialisers, and with local file I/O on Linux. [(InfoQ, Jul 2026)](https://infoq.com/articles/virtual-threads-after-jdk24)
</div>

<div class="box gotcha" markdown="1">
**💥 Gotcha: the upgrade that "just" bumps the version**

Moving from 8/11 to 17+ breaks most often **not in your code, but in old libraries**. JDK 17 strongly encapsulates JDK internals (JEP 403), so libraries that reflect into `sun.*` or private JDK fields now throw `InaccessibleObjectException`. [(OpenJDK 17)](https://openjdk.org/projects/jdk/17/) The fix is to **upgrade the library** (Lombok, Mockito, older Jackson/ByteBuddy versions). Use `--add-opens` only as a temporary bridge. And if you move to Spring Boot 3+ at the same time, every `javax.*` import becomes `jakarta.*`. Oracle's migration guide lists what's been removed release by release. [(JDK 25 Migration Guide)](https://docs.oracle.com/en/java/javase/25/migrate/getting-started.html)
</div>

<div class="box devs" markdown="1">
**🔬 Under the hood**

- A `record` compiles to a `final` class extending `java.lang.Record`, with `private final` fields and generated accessors (`c.r()`, not `getR()`), `equals`, `hashCode` and `toString`. You can add methods and a **compact constructor** for validation: `record Money(long paise) { Money { if (paise < 0) throw new IllegalArgumentException(); } }`.
- `sealed ... permits` is enforced by both the compiler **and** the JVM (via the `PermittedSubclasses` class-file attribute), so even reflection-generated code can't sneak in a new subtype.
- A blocked virtual thread's stack is copied to the heap as an ordinary object, and the carrier thread goes back to the pool. That's why a blocked virtual thread costs kilobytes, not a megabyte.
</div>

## Top story 1 · Java 27 is out: fewer knobs, less memory

<span class="tag hot">RELEASED 15 SEP</span><span class="tag watch">NON-LTS</span>

**What happened.** JDK 27 went GA on **15 September 2026** with **nine JEPs**. Four are final, and five are still in preview or incubation. [(Oracle)](https://www.oracle.com/nl/news/announcement/oracle-releases-java-27-and-strengthens-post-quantum-cryptography-support-2026-09-15/) [(InfoQ)](https://www.infoq.com/news/2026/09/java27-released/)

```viz:versus
    - "JFR in-process data redaction (JEP 536)"
note: "Source: [InfoQ, Java 27 so far](https://infoq.com/news/2026/08/java-27-so-far)."
```

**The details that matter:**

- **G1 everywhere.** Until now, on a "small" machine (roughly a single CPU or under ~1.8 GB of memory) the JVM quietly picked the **Serial** collector instead of G1. That catches people out in small containers. Now it's G1 unless you choose otherwise. [(JEP 523)](https://openjdk.org/jeps/523)
- **Compact object headers by default.** Every Java object carries a header. Java 25 shipped a smaller one as an opt-in flag. Java 27 turns it on for everyone. [(InfoQ)](https://infoq.com/news/2026/08/java-27-so-far) When the feature was finalised, OpenJDK reported these measurements:

```viz:bars

    value: 22
    display: "−22%"
    highlight: true
  - label: Fewer GCs (G1 / Parallel)
    value: 15
    display: "−15%"
  - label: Less CPU (SPECjbb2015)
    value: 8
    display: "−8%"
note: "Figures from [JEP 519](https://openjdk.org/jeps/519) for one configuration each. Your app's gain depends on how many small objects it allocates. In Java 25 you opt in with `-XX:+UseCompactObjectHeaders`; in 27 it's the default."
```

- **Post-quantum TLS.** JEP 527 adds hybrid key exchange to TLS 1.3, pairing a classical algorithm with a quantum-resistant one. It defends against "harvest now, decrypt later" attacks, where traffic recorded today is broken by a future quantum computer. [(Oracle)](https://www.oracle.com/nl/news/announcement/oracle-releases-java-27-and-strengthens-post-quantum-cryptography-support-2026-09-15/)

**Why it matters.** Two of the four final features are things you get **without changing a line of code**: less memory and saner GC defaults. They will reach most teams via the next LTS, Java 29, in September 2027.

<div class="box care" markdown="1">
**👀 What to do.** Stay on **25 LTS** in production. Add a **JDK 27 job to CI** now, so the 29 upgrade is boring. If you run on 25 today, try `-XX:+UseCompactObjectHeaders` on one service in staging and compare heap usage. It's the same feature 27 now enables by default.

## Top story 3 · The road to JDK 28 (March 2027)

<span class="tag watch">WATCH</span><span class="tag dev">PERFORMANCE</span>

**What happened.** JEP 544, **Ahead-of-Time Code Compilation**, was promoted to *Proposed to Target* for JDK 28. It aims to have optimised native code ready the moment HotSpot starts, which means faster startup and warm-up. Two ZGC JEPs (545 and 546) on adaptive heap sizing and faster startup reached *Candidate*. Early-access build 17 of JDK 28 is out. [(InfoQ)](https://www.infoq.com/news/2026/09/java-news-roundup-sep21-2026/) InfoQ also lists **Project Valhalla's value classes (JEP 401)** among the features to watch for JDK 28. As of today they're not officially targeted. [(InfoQ)](https://www.infoq.com/news/2026/09/java27-released/)

```viz:flow
title: "How a JEP becomes a feature"
headers: [Proposal, Scheduled, Shipped]
columns:
  - - label: Draft → Candidate
      sub: "JEP 545, 546 now"
  - - label: Proposed to Target
      sub: "JEP 544 now"
      style: accent
    - label: Targeted
      sub: locked to a release
  - - label: Preview / Incubator
      sub: try with a flag
      style: soft
    - label: Final
      sub: "production-ready"
      style: warn
note: "Typical path. Many features spend several releases in preview (structured concurrency is on its 7th)."
```

**Why it matters.** Project Leyden's AOT work goes straight at Java's oldest complaint: **slow start and warm-up**. It builds on two steps that already shipped in **JDK 25**: AOT command-line ergonomics (JEP 514) and AOT method profiling (JEP 515). [(OpenJDK 25)](https://openjdk.org/projects/jdk/25/) The idea: do a "training run" of your app, save what the JVM learned (loaded classes, hot methods, profiles), and reuse it at the next start. JEP 544 goes a step further and saves *compiled native code* too, so a new pod can start near full speed instead of spending its first minutes in the slow interpreter.

For a Spring Boot service on Kubernetes, that changes the maths on **autoscaling**. New pods can take real traffic sooner, so you need less over-provisioning. Value classes, if they land, would eventually give you objects that behave like primitives in memory: no identity, flat layouts in arrays, fewer allocations. That's a big deal for anything that crunches lots of small objects (money amounts, coordinates, timestamps).
