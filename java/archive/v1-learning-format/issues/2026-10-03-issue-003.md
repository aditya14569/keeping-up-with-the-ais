# Part 1 · Learn

## 🔑 `equals`, `hashCode`, `compareTo`, and how HashMap really works

<span class="tag learn">REVISE</span><span class="tag learn">~10 MIN</span><span class="tag learn">LEVEL 3</span>

**Every cache, dedup step and `groupingBy` you write leans on three methods you probably last thought hard about in an interview.** When they're wrong, nothing crashes. A `get` returns `null`, a `Set` holds a "duplicate", a `TreeSet` drops an item. These bugs survive code review because each method looks fine on its own. The failure only appears when a collection uses them together.

### 1 · The two contracts, in one breath

The `Object` Javadoc spells out both. **`equals` must be an equivalence relation**: reflexive, symmetric, transitive, consistent over time, and `x.equals(null)` is `false`. **`hashCode` has one hard rule: equal objects must have equal hash codes.** Unequal objects *may* share a hash code. That's legal, just slow. [(Oracle, `Object` Javadoc)](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/lang/Object.html)

The Javadoc adds the line that causes most real bugs: **if you override `equals`, you generally must override `hashCode` too.** [(Oracle)](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/lang/Object.html) A hash table checks the hash first and only calls `equals` on keys that land in the same bucket. Two "equal" objects with different identity hashes almost never meet.

```viz:codecompare
title: "A map key: naive vs correct"
left:
  title: "Java 8: equals only, mutable"
  code: |
    class OrderKey {
      String customerId;   // not final
      LocalDate day;
      @Override
      public boolean equals(Object o) {
        if (!(o instanceof OrderKey)) return false;
        OrderKey k = (OrderKey) o;
        return customerId.equals(k.customerId)
            && day.equals(k.day);
      }
      // no hashCode(): identity hash
    }
right:
  title: "Java 16+: a record"
  code: |
    record OrderKey(String customerId,
                    LocalDate day) {
      OrderKey {
        Objects.requireNonNull(customerId);
        Objects.requireNonNull(day);
      }
    }
    // equals, hashCode, toString are
    // generated from all components,
    // and every field is final.
note: "We compiled both on JDK 21. On the left, `set.contains(new OrderKey(...))` returns `false` for a key you just added (barring a lucky hash match), because each instance hashes by identity. On the right, the same lookup works. Records get the full topic in two issues' time."
```

**When you can't use a record** (a JPA entity, a class with a superclass, a legacy DTO), write the pair by hand and keep two rules:

- **Use the same fields in both methods.** If `equals` compares `customerId` and `day`, `hashCode` hashes exactly those, for example `Objects.hash(customerId, day)`. A field in `hashCode` but not in `equals` breaks the contract outright. A field in `equals` but not in `hashCode` is legal, but costs you collisions.
- **Choose `getClass()` or `instanceof` on purpose.** `instanceof` lets a subclass equal its parent, and the moment the subclass adds a field to its own `equals`, symmetry breaks: `parent.equals(child)` is `true`, `child.equals(parent)` is `false`. Make the class `final`, or compare `getClass()`. Note that Hibernate proxies are subclasses, which is why ORM-friendly `equals` methods usually use `instanceof`.

### 2 · What `put` actually does

**A `HashMap` is an array of buckets, and your `hashCode` decides which bucket.** Here's the path of one `put(key, value)`, confirmed with `javap` on JDK 21.

```viz:flow
title: "One put(key, value), step by step"
headers: [Hash, Pick bucket, Store]
columns:
  - - label: key.hashCode()
      sub: "your method (null → 0)"
    - label: "h ^ (h >>> 16)"
      sub: mix high bits into low
      style: soft
  - - label: "(n - 1) & hash"
      sub: "n = table size, a power of 2"
      style: accent
  - - label: Linked list
      sub: "usual case: few entries"
    - label: Red-black tree
      sub: "8+ entries and table ≥ 64"
      style: warn
note: "Constants from `javap -constants java.util.HashMap`: default capacity 16, load factor 0.75, `TREEIFY_THRESHOLD` 8, `UNTREEIFY_THRESHOLD` 6, `MIN_TREEIFY_CAPACITY` 64. These are implementation details, not API, and can change."
```

Three things fall out of that picture:

- **The XOR step exists because the bucket index uses only the low bits.** With 16 buckets, only the bottom 4 bits of the hash matter. Folding the high 16 bits down means a `hashCode` that varies only in its high bits still spreads out.
- **Resizing doubles the table.** When the entry count passes capacity × 0.75, the map rebuilds with about twice the buckets. [(Oracle, `HashMap` Javadoc)](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/HashMap.html) Because the size is a power of two, each entry either stays at its index or moves up by exactly the old capacity, which makes the split cheap.
- **Pre-size when you know the count.** `new HashMap<>(1000)` is a classic trap: 1000 is a *capacity*, rounded up to 1024, so the map still resizes after 768 entries. Since Java 19, **`HashMap.newHashMap(1000)`** picks a capacity that fits 1000 mappings without resizing. [(Oracle)](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/HashMap.html)

### 3 · Treeification: Java 8's insurance policy

**Before Java 8, a bucket was always a linked list, so many keys with the same hash made lookups O(n).** JEP 180 changed that: once a bucket grows past a threshold, it switches to a balanced tree, improving the worst case to **O(log n)**. [(JEP 180)](https://openjdk.org/jeps/180) The tree is ordered by hash and, when keys are `Comparable`, by `compareTo` to break ties. That's why the Javadoc says comparable keys help when "many keys" share a hash. [(Oracle)](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/HashMap.html)

The `MIN_TREEIFY_CAPACITY` of 64 is a nice detail. In a small table, a long bucket more likely means "too few buckets" than "bad hash", so **the map resizes first and only builds trees once the table has at least 64 buckets.** A tree that shrinks to 6 entries turns back into a list.

<div class="box realworld" markdown="1">
**🌍 In the real world: the 2011 hash-flooding attacks**

In December 2011, Alexander Klink and Julian Wälde showed that attackers could send **HTTP POST requests full of parameter names chosen to share one hash code**. Servers parse parameters into a hash table, so each request turned into a quadratic pile of collisions. oCERT's advisory listed Java, **Tomcat up to 7.0.22, Jetty up to 7.5.4 and GlassFish up to 3.1.1** among those affected, and warned that one request could keep a CPU at 100% for a long time with very little attacker bandwidth. [(oCERT-2011-003)](https://ocert.org/advisories/ocert-2011-003) Java's `String.hashCode` is easy to collide on purpose: `"Aa"` and `"BB"` both hash to 2112, and you can combine such pairs into thousands of colliding strings. JEP 180's tree bins, shipped in Java 8, cap the damage at O(log n) per lookup, because `String` is `Comparable`. [(JEP 180)](https://openjdk.org/jeps/180)
</div>

### 4 · `compareTo`: the third contract

**`TreeMap` and `TreeSet` never call `equals`. They decide "same key" with `compareTo` (or your `Comparator`).** The `Comparable` contract asks for sign symmetry and transitivity, and strongly recommends being **consistent with equals**: `compareTo` returns 0 exactly when `equals` returns `true`. Break that and sorted collections behave, in the Javadoc's word, "strangely". [(Oracle, `Comparable` Javadoc)](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/lang/Comparable.html)

The JDK's own famous exception is **`BigDecimal`**: `4.0` and `4.00` compare as equal but aren't `equals`. [(Oracle)](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/lang/Comparable.html) We checked on JDK 21: put both in a `HashSet` and you get **2 elements**; put both in a `TreeSet` and you get **1**.

```viz:codecompare
title: "Sorting items by price: naive vs correct"
left:
  title: "Naive: subtraction, no tie-break"
  code: |
    Comparator<Item> byPrice =
        (a, b) -> a.cents() - b.cents();
    // overflows: MIN_VALUE - 1 wraps
    // to MAX_VALUE, so "less" becomes
    // "greater" and sorting breaks

    var set = new TreeSet<Item>(byPrice);
    set.add(new Item("pen", 100));
    set.add(new Item("cap", 100));
    set.size();  // 1: "cap" was dropped
right:
  title: "Correct: comparing + thenComparing"
  code: |
    Comparator<Item> byPrice =
        Comparator.comparingInt(Item::cents)
                  .thenComparing(Item::name);


    var set = new TreeSet<Item>(byPrice);
    set.add(new Item("pen", 100));
    set.add(new Item("cap", 100));
    set.size();  // 2: ties broken by name
note: "`record Item(String name, int cents)`. Both panes compiled and ran on JDK 21: the left comparator returns 2147483647 for (MIN_VALUE, 1). The right one is consistent with the record's equals, because it compares every component."
```

<div class="box gotcha" markdown="1">
**💥 Gotcha: the key you mutated after `put`**

The hash is computed **once, at `put` time**, and stored with the entry. Change a field that `hashCode` uses afterwards, and the entry sits in the bucket for its *old* hash. We tried it on JDK 21: `map.get(key)` with the very same object returns **`null`**, `containsKey` with a fresh copy of the old value returns `false`, and `size()` still says 1. The entry is unreachable until it's removed by iteration. The `Object` contract only promises a stable hash "provided no information used in `equals` comparisons on the object is modified". [(Oracle)](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/lang/Object.html) The fix is boring and total: **make keys immutable.** A record with immutable components is the easiest way. Watch out for JPA entities with a generated `@Id` in `hashCode`: the id changes from `null` to a value on persist.
</div>

<div class="box devs" markdown="1">
**🔬 Under the hood**

- **`String` caches its hash** in a field after the first call, so repeated lookups with the same string don't rehash it. That's one reason strings make good keys.
- **Record `equals` and `hashCode` are generated through `invokedynamic`** (`ObjectMethods.bootstrap`, as `javap -v` shows), not written into the class file as code, so the JDK can improve them without recompiling your classes. Note a record's `equals` uses each component's own `equals`, so **a record holding a `BigDecimal` inherits the `4.0` vs `4.00` problem**. We checked: `new Money(new BigDecimal("4.0")).equals(new Money(new BigDecimal("4.00")))` is `false`.
- **`HashMap` isn't thread-safe.** Unsynchronized concurrent writes can corrupt it, and its iterators are fail-fast, throwing `ConcurrentModificationException` on a best-effort basis. [(Oracle)](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/HashMap.html) Use `ConcurrentHashMap` for shared maps.
</div>

<div class="box tryit" markdown="1">
**🧪 Try it (15 minutes, jshell on JDK 17+)**

1. **Lose a key.** Define `class K { int id; K(int i){id=i;} public boolean equals(Object o){return o instanceof K k && k.id==id;} public int hashCode(){return id;} }`. Put `k = new K(1)` into a `HashMap`, set `k.id = 2`, then try `get(k)` and `get(new K(1))`. Print `size()`.
2. **BigDecimal split personality.** Add `new BigDecimal("4.0")` and `new BigDecimal("4.00")` to a `HashSet` and a `TreeSet`. Compare sizes. Then try `stripTrailingZeros()` on both before adding.
3. **Watch treeification pay off.** Make `record Bad(int id)` with `hashCode()` always returning 42. Put 20,000 instances in a `HashMap` and time 20,000 `get`s. Then add `implements Comparable<Bad>` (compare by `id`) and time again. In one rough run on our JDK 21 sandbox with 50,000 keys, the gets took **about 17 seconds without `Comparable` and about 40 ms with it**. Not a benchmark, but the gap is JEP 180 at work.
</div>

## Top story 1 · Free Oracle JDK 21 updates end with the 20 October patch

<span class="tag hot">ACT THIS MONTH</span><span class="tag watch">LICENSING</span>

**What happened.** Oracle has been shipping JDK 21 under its **No-Fee Terms and Conditions (NFTC)** licence, which allows free production use. That free period has ended. In Oracle's words, further Oracle JDK 21 updates, **"beginning with the October 2026 Critical Patch Update"**, are planned under the **Java SE OTN licence**, the same model that already covers Oracle's Java 8, 11 and 17 updates. [(Oracle Java blog)](https://blogs.oracle.com/java/jdk-21-approaches-end-of-permissive-license) The October CPU is scheduled for **Tuesday 20 October 2026**. [(Oracle security alerts)](https://www.oracle.com/securityalerts)

The support roadmap now states the same thing, and adds that **JDK 25 stays under the free licence through September 2028**. Java 21 itself is far from dead: paid Premier Support runs to September 2028 and Extended Support to September 2031. [(Oracle roadmap)](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)

**Why it matters.** This is the "free LTS for three years" model doing exactly what it said, but it catches teams that adopted Oracle's JDK 21 images or installers in 2023 and never revisited the choice. From the October CPU on, **staying patched on Oracle's JDK 21 binaries means accepting the OTN terms**, so read them before your next patch run. Oracle recommends moving to JDK 25 and points to its Java SE Universal Subscription for anyone who needs to stay. [(Oracle Java blog)](https://blogs.oracle.com/java/jdk-21-approaches-end-of-permissive-license) The change is about **Oracle's binaries**. OpenJDK builds from other distributors have their own licences and support schedules, so check which one you actually run.

The usual hiding places are not the servers you think about. They're the **Dockerfile `FROM` line copied from an old template**, the CI image that builds your jars, the desktop tool someone installed with the Oracle installer, and the vendored JRE inside an on-prem product. A licence change is also a good moment to ask the bigger question: **JDK 25 has been out for a year**, Spring Boot 4 and Quarkus 4 both run on it, and the jump only gets bigger the longer you wait.

<div class="box care" markdown="1">
**👀 What to do.** Run `java -version` on your servers and check your base images: the vendor string tells you whose build it is. If it's **Oracle JDK 21 in production**, pick one path before 20 October: move to **JDK 25**, switch to another vendor's JDK 21 build, or budget for a subscription. Don't just stop patching: the October CPU will carry security fixes.

<div class="box revision" markdown="1">
**📌 Revision card**

- **Override `equals`, override `hashCode`.** Equal objects must have equal hashes; unequal ones may collide.
- **Keys must be immutable.** The hash is stored at `put` time; mutate a key and the entry becomes unreachable.
- **`HashMap` = power-of-two bucket array.** Index is `(n-1) & (h ^ h>>>16)`; it doubles when size passes capacity × 0.75.
- **Buckets become trees** at 8 entries once the table has 64+ buckets (JEP 180, Java 8). `Comparable` keys help.
- **Use `HashMap.newHashMap(n)`** (Java 19+) to pre-size; `new HashMap<>(n)` sets capacity, not expected size.
- **`TreeSet`/`TreeMap` use `compareTo` only.** Keep it consistent with `equals`; never compare by subtraction.
- **Oracle JDK 21:** updates from the 20 Oct CPU move to the OTN licence. JDK 25 is free until Sep 2028.
