# Part 1 · Learn

## 📦 Records: data carriers done right

<span class="tag learn">CATCH UP</span><span class="tag learn">~10 MIN</span><span class="tag learn">LEVEL 3</span>

**Records arrived as a final feature in Java 16, so if your Java stopped at 8 or 11, you've been writing them by hand (or with Lombok) ever since.** Yesterday's issue showed the payoff: a record key gets `equals` and `hashCode` right for free. Today is about the rest: **how to put validation in a record, what "immutable" really means for one, and where a record is the wrong tool.**

The design goal in JEP 395 isn't "less boilerplate". It's **"modeling data as data"**: a record is a *transparent* carrier for immutable data, and the class declaration is the whole story. [(JEP 395)](https://openjdk.org/jeps/395) Keep that idea in mind. Every rule below follows from it.

### 1 · What one line buys you

```viz:codecompare
title: "A value type: then vs now"
left:
  title: "Java 8: hand-written"
  code: |
    public final class Range {
      private final int lo, hi;
      public Range(int lo, int hi) {
        this.lo = lo; this.hi = hi;
      }
      public int getLo() { return lo; }
      public int getHi() { return hi; }
      @Override public boolean equals(..)
      @Override public int hashCode()
      @Override public String toString()
      // ~40 lines once written out,
      // and one more field means
      // editing five places
right:
  title: "Java 16+: a record"
  code: |
    record Range(int lo, int hi) {
      Range {
        if (lo > hi)
          throw new IllegalArgumentException(
              lo + " > " + hi);
      }
      int length() { return hi - lo; }
    }
    // new Range(1, 5).lo()   → 1
    // new Range(1, 5)        →
    //   Range[lo=1, hi=5]
    // new Range(5, 1)        → IAE
note: "Right pane compiled and run on JDK 21. Note the accessor is `lo()`, not `getLo()`. Frameworks that look for JavaBean getters need record support, which Jackson, Spring and Hibernate all have today."
```

From that header, the compiler generates **a `private final` field and a public accessor per component, a canonical constructor, and `equals`, `hashCode` and `toString`.** [(Oracle, Record Classes)](https://docs.oracle.com/en/java/javase/25/language/records.html) `javap` on our `Range` shows the rest of the contract: `final class Range extends java.lang.Record`. You can't extend a record, and a record can't extend anything else. It can implement interfaces.

You can add **static fields, static factory methods, instance methods and nested types**. You can't add **instance fields** or instance initializers. [(Oracle)](https://docs.oracle.com/en/java/javase/25/language/records.html) Try `record Bad(int x) { int y; }` and javac answers: `field declaration must be static`. That's the transparency rule at work: if state isn't in the header, it doesn't exist.

### 2 · The compact constructor: where invariants live

**The compact constructor is the one feature that turns a record from a tuple into a type.** You write it without a parameter list. The parameters are implicit, and **the fields are assigned automatically at the end**. [(Oracle)](https://docs.oracle.com/en/java/javase/25/language/records.html) Because every way of creating a record goes through it, it can do three jobs:

- **Validate.** Throw on bad input, as `Range` does above.
- **Normalize.** Reassign a parameter before the implicit assignment: `currency = currency.toUpperCase(Locale.ROOT);` stores `"EUR"` even if you passed `"eur"`. (We ran it.)
- **Defensively copy.** This one matters most, and it's where most people slip.

```viz:codecompare
title: "A record holding a list: naive vs correct"
left:
  title: "Naive: shallow immutability"
  code: |
    record Team(String name,
                List<String> members) {}

    var src = new ArrayList<>(
        List.of("ana", "bo"));
    var t = new Team("core", src);
    src.add("eve");
    t.members().size();   // 3 (!)
    t.members().add("x"); // works (!)
right:
  title: "Correct: copy in the constructor"
  code: |
    record Team(String name,
                List<String> members) {
      Team {
        members = List.copyOf(members);
      }
    }
    var t = new Team("core", src);
    src.add("eve");
    t.members().size();   // 2
    t.members().add("x"); // throws UOE
note: "Both compiled and run on JDK 21. `List.copyOf` (Java 10+) returns an unmodifiable list, rejects nulls, and generally doesn't copy a list that's already unmodifiable."
```

**A record's fields are final, but `final` only freezes the reference.** If a component is a mutable object, callers can still change what it points to, and they can change your `equals` and `hashCode` with it. Copy mutable inputs on the way in, and the accessor can return the field as is.

### 3 · Where records fit, and where they don't

```viz:versus
left:
  emoji: ✅
  title: Great fit
  points:
    - "DTOs and API request/response bodies"
    - "Query projections (JPQL `select new …`)"
    - "Map keys, composite IDs, value objects (Money, Range)"
    - "Config properties (Spring Boot binds to records)"
    - "Multiple return values from a private method"
right:
  emoji: 🚫
  title: Poor fit
  points:
    - "JPA entities: need a no-arg constructor, non-final class and fields"
    - "Anything with identity or a lifecycle that mutates"
    - "Types that need a superclass"
    - "Public APIs whose internal representation may change"
```

**The JPA case is the one you'll meet first.** An entity needs a no-arg constructor, must not be `final` (so the provider can create lazy-loading proxies) and needs non-final fields to map and dirty-check. Records break all three. [(Thorben Janssen)](https://thorben-janssen.com/java-records-hibernate-jpa) Use them for the **read side** instead: projections, DTOs and embeddables.

**The last row is the subtle one.** A record's API *is* its representation: the components become the constructor, the accessors and the `toString`. Rename a component or split one in two, and every caller breaks. For a public library type whose internals may change, a normal final class with a private representation is still the better choice. For a DTO inside your service, that tight coupling is the whole point.

### 4 · Three everyday patterns

**Static factories for meaningful names.** The canonical constructor takes every component, in order. When some calls always pass the same value, add a static factory instead of a second constructor: `static Money eur(String v) { return new Money(new BigDecimal(v), "EUR"); }`. It still goes through the compact constructor, so validation can't be skipped.

**"Withers" instead of setters.** A record can't change, so "changing" one means building a new one. Write small `withX` methods that call the canonical constructor:

```java
record Range(int lo, int hi) {
  Range { if (lo > hi) throw new IllegalArgumentException(); }
  Range withHi(int newHi) { return new Range(lo, newHi); }
}
// new Range(1, 5).withHi(9)  → Range[lo=1, hi=9]
// new Range(1, 5).withHi(0)  → IllegalArgumentException
```

Because every wither goes back through the constructor, **an invalid record can never exist**. That's the guarantee a setter-based POJO can't give you.

**Local records for intermediate results.** Instead of a `Map.Entry` or an `Object[]` in the middle of a stream, declare a record inside the method. `record Scored(String name, int score) {}` gives the intermediate value a name, real accessors and a readable `toString` for debugging, and it's invisible outside the method.

<div class="box realworld" markdown="1">
**🌍 In the real world: Spring Boot and Hibernate are built for records now**

**Spring Boot** binds `@ConfigurationProperties` straight into a record. Its reference docs say that a single parameterized constructor implies constructor binding, and that **"unless your record has multiple constructors, there is no need to use `@ConstructorBinding`"**. Defaults come from `@DefaultValue` on a component. One catch: the class must be enabled with `@EnableConfigurationProperties` or property scanning, not declared as a `@Component`. [(Spring Boot docs)](https://docs.spring.io/spring-boot/reference/features/external-config.html)

**Hibernate 6.2** (March 2023) added mapping **Java records as embeddables**, so an `@Embeddable record Name(String first, String last)` can sit inside an entity. [(Hibernate blog)](https://in.relation.to/2023/03/30/orm-62-final/) The entity itself stays a class, but its value parts can be records.
</div>

<div class="box gotcha" markdown="1">
**💥 Gotcha: arrays in records**

The generated `equals` compares each component with its own `equals`, and **arrays don't override `equals`**. We checked on JDK 21: `new Blob(new byte[]{1,2}).equals(new Blob(new byte[]{1,2}))` is **`false`**, while `Arrays.equals` on the two arrays is `true`. The `hashCode` is identity-based too, so two "identical" blobs are different `HashMap` keys. The array is also mutable through the accessor. **Prefer a `List` (copied with `List.copyOf`)**. If you must hold an array, clone it in the compact constructor and the accessor, and override `equals`, `hashCode` and `toString` with the `Arrays` helpers. At that point, ask whether a record still fits.
</div>

<div class="box devs" markdown="1">
**🔬 Under the hood**

- **Serialization goes through the front door.** A normal `Serializable` class is rebuilt by reflection, without running its constructor. A record is **deserialized by calling its canonical constructor**, so your compact-constructor validation runs on untrusted streams too. You can't customize it with `readObject`/`writeObject`. [(Oracle)](https://docs.oracle.com/en/java/javase/25/language/records.html) [(inside.java)](https://inside.java/2021/03/12/simpler-serilization-with-records/)
- **Records are reflectable as records.** `Range.class.getRecordComponents()` returns `[int lo, int hi]` in declaration order. That's how frameworks can learn component names and find the canonical constructor without relying on getters.
- **Nested and local records are implicitly `static`**, so they can't capture an enclosing instance or local variables. JEP 395 calls out this "no hidden state" rule. [(JEP 395)](https://openjdk.org/jeps/395)
- **Annotations on components propagate** to the field, accessor and constructor parameter, wherever the annotation's `@Target` allows. That's why `@NotBlank String url` works for Bean Validation in a config record. [(Oracle)](https://docs.oracle.com/en/java/javase/25/language/records.html)
</div>

<div class="box tryit" markdown="1">
**🧪 Try it (15 minutes, jshell on JDK 17+)**

1. **Build a `Money` value.** `record Money(BigDecimal amount, String currency)`, with a compact constructor that rejects null and negative amounts and upper-cases the currency. Check that `new Money(new BigDecimal("4.50"), "eur")` prints `Money[amount=4.50, currency=EUR]`.
2. **Break, then fix, immutability.** Write `record Team(String name, List<String> members) {}`, mutate the source list after construction, and watch `members()` change. Add `members = List.copyOf(members);` and try again.
3. **Write a "wither".** Add `Range withHi(int hi) { return new Range(lo, hi); }`. Confirm that `withHi` still goes through your validation: `new Range(1, 5).withHi(0)` should throw.
</div>

## Top story 1 · Spring moves to one release day a month

<span class="tag hot">PLAN FOR IT</span><span class="tag watch">SECURITY</span>

**What happened.** The Spring team has **re-engineered how it releases the whole portfolio**. Instead of releases spread over about two weeks, every Spring project now ships **"in one large train"** on a single day: **the Thursday after the third Monday of each month**, the same rhythm Spring Boot already used. The September milestones on 24 September were the dry run. **The first patch releases under the new model are due on 22 October.** [(spring.io)](https://spring.io/blog/2026/09/21/releasing-spring-for-modern-challenges/)

The reason is security. The team says it has averaged **nearly 80 new community-reported security reports a month since March**, with vulnerabilities now exploited within hours rather than days, and that it recently fixed **over 160 CVEs**. It has also rebuilt **spring.io/security** so you can filter advisories by CVE ID, severity and project. [(spring.io)](https://spring.io/blog/2026/09/21/releasing-spring-for-modern-challenges/)

**Why it matters.** Before, a fix in Spring Framework could land days before the Boot release that pulled it in, and you had to choose: override one version, or wait. **One train means one coordinated set of versions on a known day**, so a Boot bump picks up every fixed project at once. This month it also lands two days after Oracle's quarterly CPU on 20 October, so one patch week can cover both. [(Oracle security alerts)](https://www.oracle.com/securityalerts)

It also changes what a milestone month looks like. Between 23 and 25 September, Spring Boot 4.2.0-M2, Spring Data 2026.1.0-M2, Spring Security 7.2.0-M2, Spring Batch 6.1.0-M2, Spring Integration and AMQP milestones and the first Spring Cloud 2026.0 milestone all landed. [(spring.io releases)](https://spring.io/blog/category/releases/) **Expect the same clustering every month from now on**: one big day, then quiet.

The flip side: **80 reports a month means patch releases will keep carrying security fixes.** A team that bumps Spring Boot "when we get around to it" will drift further behind each month.

<div class="box care" markdown="1">
**👀 What to do.** Put a **standing monthly slot** in the calendar for the Friday after release day (23 October first), and let Dependabot or Renovate open the Boot bump PR automatically. Bookmark spring.io/security and filter it by the projects you actually use. On Boot 4.0, also note that its open-source support ends on **31 December 2026** [(endoflife.date)](https://endoflife.date/spring-boot), so a 4.1 move belongs in this quarter's plan.

## Top story 2 · Jackson CVE-2026-68497: small request, big CPU bill

<span class="tag hot">PATCH</span><span class="tag dev">JSON</span>

**What happened.** A denial-of-service flaw in **jackson-databind** was published on 28 September with a **CVSS score of 7.5 (High)**. When Jackson deserializes a JSON string into a **`javax.xml.datatype.Duration` or `XMLGregorianCalendar`** field, it passes the raw string to the JDK's `DatatypeFactory` with no length limit. An attacker can send a small request with an extremely long number and trigger expensive `BigInteger` parsing. No authentication is needed. [(GitLab advisory)](https://advisories.gitlab.com/maven/tools.jackson.core/jackson-databind/CVE-2026-68497/) [(CVE record via Vulners)](https://vulners.com/cvelist/CVELIST:CVE-2026-68497)

| Line | Affected | Fixed in |
|---|---|---|
| Jackson 2 (`com.fasterxml`) | 2.0.0 → 2.18.9, 2.19.0 → 2.21.5, 2.22.0 → 2.22.1 | **2.18.10, 2.21.6, 2.22.2** |
| Jackson 3 (`tools.jackson`) | 3.0.0 → 3.1.5, 3.2.0 → 3.2.1 | **3.1.6, 3.2.2** |

Sources: [CVE record](https://vulners.com/cvelist/CVELIST:CVE-2026-68497), [GitLab advisory](https://advisories.gitlab.com/maven/tools.jackson.core/jackson-databind/CVE-2026-68497/).

The ecosystem is already moving. **jOOQ** opened an upgrade issue on 1 October [(jOOQ #20265)](https://github.com/jOOQ/jOOQ/issues/20265), and **Micronaut 5.2.1** (1 October) moves to Jackson 3.2.3 "to address a vulnerability" and recommends that users update. [(Micronaut)](https://micronaut.io/2026/10/01/micronaut-framework-5-2-1/)

**Why it matters.** The vulnerable path needs a `Duration` or `XMLGregorianCalendar` somewhere in a type you deserialize from untrusted input. **That's rare in new code, but common in SOAP-to-REST bridges and JAXB-generated classes**, where `XMLGregorianCalendar` is the default date type. It's the same family of problem as the 2011 hash-flooding attacks from yesterday's issue: **cheap for the attacker, expensive for the server.** And since almost every Spring, Quarkus and Micronaut app has jackson-databind on its classpath, the version check is worth doing even if you think you don't use those types.

<div class="box care" markdown="1">
**👀 What to do.** Run `mvn dependency:tree -Dincludes=*:jackson-databind` (or `gradle dependencyInsight --dependency jackson-databind`) to see which version you actually resolve. If it's in an affected range, override it through your framework's managed property (in Spring Boot, the Jackson BOM version property) or wait for your framework's next patch, Spring's on 22 October. Meanwhile, search your DTOs for `XMLGregorianCalendar` and `javax.xml.datatype.Duration`. On public endpoints, replace them with `java.time` types.
</div>

<div class="box jargon" markdown="1">
**📖 Jargon buster**

- **CVSS 7.5, `AV:N/AC:L/PR:N/UI:N`:** reachable over the network, low complexity, no privileges, no user interaction. The impact is availability only (`A:H`): nothing leaks, the server just stops answering. [(GitLab advisory)](https://advisories.gitlab.com/maven/tools.jackson.core/jackson-databind/CVE-2026-68497/)
- **BOM (bill of materials):** a Maven POM that pins versions for a family of artifacts. Spring Boot's dependency management works this way, which is why you override one property instead of editing every Jackson artifact.
- **Release train:** many projects shipped together as one tested set of versions. Spring Cloud has long used named trains; now the whole Spring portfolio ships like one.
</div>

<div class="box revision" markdown="1">
**📌 Revision card**

- **A record = final class extending `java.lang.Record`,** with private final fields, accessors (`x()`, not `getX()`), a canonical constructor, `equals`, `hashCode` and `toString`.
- **No instance fields, no superclass.** Static members, instance methods and interfaces are fine.
- **Compact constructor:** validate, normalize, copy. Fields are assigned automatically at the end.
- **Immutability is shallow.** Use `List.copyOf` for collections; avoid arrays (their `equals` is identity).
- **Not for JPA entities.** Use records for DTOs, projections, keys, config and (since Hibernate 6.2) embeddables.
- **Records deserialize through the canonical constructor,** so your validation also guards untrusted streams.
- **Spring ships monthly on one Thursday,** starting with patches on 22 Oct. Plan a standing upgrade slot.
- **Jackson CVE-2026-68497:** upgrade to 2.18.10 / 2.21.6 / 2.22.2 or 3.1.6 / 3.2.2.
