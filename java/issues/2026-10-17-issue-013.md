☕ Today's two stories

1. **JDK 28 makes the most common Foreign Function & Memory pattern up to ~19x cheaper, without any change to your code.** Small allocations from `Arena.ofConfined()` now come from a reusable 64-byte native pool held by each thread, instead of a fresh `malloc` and `free` every time. On 14 October the JDK deleted its own internal workaround for the old cost. Helidon 4.5 stays on as the long-term "tail". Here's what Tip & Tail (JEP 14) means, what changed, and how to decide whether to stay or move.

# Story 1 · JDK 28 recycles your tiny native allocations

<div class="byline">JDK 28 · Core libraries · FFM API · JDK-8385697 · Integrated 3 Sep 2026, explained by Oracle 5 Oct · ~14 min read</div>

<p class="opener" markdown="1">You call a C function and it needs somewhere to write four bytes: an error code, a file descriptor, a single int. In Java's modern native-interop API, the safe way to do that is to open a tiny memory "arena", allocate four bytes, make the call and close the arena. It's clean and it can't leak. Until now it also meant a trip to the C allocator and back for every call, and that bookkeeping could cost far more than the four bytes it was for. JDK 28 makes that pattern almost free, and the JDK's own developers have already deleted the workaround they built because of it.</p>

### What happened

On 3 September 2026, Oracle engineer Per-Åke Minborg integrated **JDK-8385697, "Add a Pooled Confined Arena"** into the JDK 28 main line, reviewed by Jorn Vernee and Alan Bateman.[^commit] It touches 17 files (1,960 lines added, 18 removed), most of them tests, and adds one new internal class, `jdk.internal.foreign.ConfinedSegmentPool`.[^commit] We checked the build tags: the change isn't in JDK 28 early-access build 14 (tagged 3 September) but it is in build 15 (10 September) and every build since.[^tags]

On 5 October, Minborg explained the change on Inside.java, Oracle's Java team blog.[^minborg] The summary: starting with JDK 28, **small allocations made through `Arena.ofConfined()` can be served from reusable native-memory pools kept by each thread**, and "no source code changes" are needed.[^minborg] His development benchmarks show speedups of 6.8x to 18.9x for 5- and 20-byte allocations, depending on the platform.[^minborg]

Then, on 14 October, a follow-up commit, **JDK-8392541**, removed two internal JDK classes, `BufferStack` and `CaptureStateUtil`, deleting 1,526 lines.[^bufferstack] `BufferStack` was a thread-local recycling stack the JDK's own native-call machinery used to avoid exactly the cost that the pool now removes. Its replacement is a plain `Arena.ofConfined()`.[^bufferstack] When the platform team throws away its own optimisation because the public API is now fast enough, that's a fairly strong signal.

JDK 28 is due in March 2027. Nothing in the public API changed: we compared `Arena.java` and the pooling commit, and the change lives entirely in internal classes.[^commit]

### The background you need

#### Calling C from Java, then and now

Java programs sometimes need to call code written in C: an operating-system function, a compression or crypto library, a GPU driver. For 25 years the official way was {{JNI|the Java Native Interface (1997), the original way to call C/C++ code from Java. It needs a Java `native` method, a generated C header and hand-written C glue code}}. JNI works, but it's painful. JEP 442 lists the problems: you maintain three artifacts across two toolchains (the Java declaration, a generated header, a C implementation), there's no mapping between Java objects and C structs, and developers often fall back on `sun.misc.Unsafe` to pass raw addresses around.[^jep442] Off-heap memory had its own trouble: a direct `ByteBuffer` tops out at about 2 GB, has a rudimentary API and is freed only when the garbage collector gets around to it.[^jep442]

The replacement is the {{FFM API|the Foreign Function & Memory API (package `java.lang.foreign`): call native functions and work with native memory from pure Java, with no C glue code. Final since JDK 22}}, built in {{Project Panama|the OpenJDK project that improves the connection between Java and native code}}. It took a long road. A foreign-memory API first incubated in Java 14 (JEP 370) and a foreign linker in Java 16 (JEP 389). JEP 412 merged them in JDK 17.[^jep412] A second incubator came in JDK 18 (JEP 419),[^foojay] then previews in JDK 19 (JEP 424), JDK 20 (JEP 434) and JDK 21 (JEP 442).[^jep442] JDK 22 finalised it in March 2024 with JEP 454, "after two rounds of incubation and three rounds of preview", in InfoQ's words.[^infoq22]

#### Arenas: who owns this memory, and for how long?

The FFM API's central idea is that every piece of native memory, a {{MemorySegment|a Java object that describes a contiguous region of memory (native or on the heap) with a size and a lifetime, and checks every access against both}}, belongs to an {{Arena|the FFM object that controls when native memory is freed. Every segment you allocate belongs to an arena, and closing the arena frees it all at once}}. The JDK offers four kinds, and JEP 442 describes them like this:[^jep442]

- **Global**: the memory lives forever and is never freed.
- **Automatic** (`Arena.ofAuto()`): freed by the garbage collector some time after the segment becomes unreachable, so you don't control when.
- **Confined** (`Arena.ofConfined()`): freed deterministically when you close it, and only the thread that opened it may touch its segments. Use after close throws an exception.
- **Shared** (`Arena.ofShared()`): any thread may access and close it, but closing needs extra synchronisation, so the memory may not be freed immediately.

A {{confined arena|an arena that only its creating thread may use, freed the moment you close it. Usually used with try-with-resources}} is the one you reach for around a single native call, because it's the cheapest to close and it pairs perfectly with try-with-resources. Here's a real example: calling the POSIX `open` function and reading `errno`, the C error code, if it fails. This needs a little scratch memory for the path string and for the captured error code.

```java
// JDK 22+ (final API). On JDK 21: --enable-preview, allocateUtf8String
Linker linker = Linker.nativeLinker();
StructLayout STATE = Linker.Option.captureStateLayout();
long ERRNO = STATE.byteOffset(PathElement.groupElement("errno"));
MethodHandle open = linker.downcallHandle(
    linker.defaultLookup().find("open").orElseThrow(),
    FunctionDescriptor.of(JAVA_INT, ADDRESS, JAVA_INT),
    Linker.Option.captureCallState("errno"));

try (Arena arena = Arena.ofConfined()) {
    MemorySegment state = arena.allocate(STATE);           // 4 bytes
    MemorySegment path  = arena.allocateFrom("/no/such/file"); // 14 bytes
    int fd = (int) open.invokeExact(state, path, 0);
    if (fd < 0) System.out.println("errno = " + state.get(JAVA_INT, ERRNO));
}
```

We compiled and ran the JDK 21 version of this (identical except for `allocateUtf8String` and the preview flag) on OpenJDK 21.0.12.1. It prints `errno = 2`, which is `ENOENT`, "no such file". The arena allocated 18 bytes in total.[^own] Minborg's post says this pattern is common precisely for handling `errno` in system calls.[^minborg] It's also everywhere in real libraries. **JLine**, a widely used Java library for console input, has an FFM terminal backend that opens 27 confined arenas across its main source, typically to hold one small C struct such as the 8-byte window-size record for an `ioctl` call, or a `pollfd` plus a captured `errno`.[^jline]

#### Why tiny allocations were expensive

Before JDK 28, every `arena.allocate(...)` on a confined arena took the general path. We read it in the JDK source: it calls `Unsafe.allocateMemory` (the JDK's wrapper around the C allocator, `malloc`), zeroes the memory, and then creates a small cleanup object and adds it to the arena's resource list. When you close the arena, the JDK walks that list and calls `freeMemory` for each allocation.[^segfac] So a 4-byte scratch value costs a `malloc`, a `free`, one extra Java object and some list manipulation. As Minborg puts it, for small values "this bookkeeping could cost more than accessing the memory".[^minborg]

We measured the shape of that overhead on JDK 21 in our sandbox (two vCPUs, a simple warmed-up loop, not a JMH benchmark, so treat it as indicative). Opening a confined arena, allocating one `int`, writing and reading it and closing the arena took about **134–141 ns per iteration**. Opening and closing an arena that allocates nothing took about **0.4 ns**, and writing and reading a reused segment took about **0.6 ns**.[^own] The cost isn't the arena or the memory access. It's the allocation round-trip. (Our numbers come from a different JDK and different hardware from Oracle's, so don't compare them directly. Oracle's non-pooled baseline on an Apple M4 is about 16 ns.[^minborg])

How small are typical allocations? Minborg instrumented a test-suite run. Some confined arenas allocated no native memory at all, and **more than 99.99% of those that did allocate used less than 64 bytes**. He stresses that a test suite isn't representative of every application, but the distribution favoured "a small, lazy pool".[^minborg] That's exactly what was built.

### How it works

#### A small per-thread cache of 64-byte pools

The new class's own documentation describes the design. Each platform thread lazily keeps a cache with a configurable number of fixed-size pools. A confined arena carves small allocations out of one pool, and anything that doesn't fit uses the regular allocator.[^commit] The defaults are set in the code: pools are **2^6 = 64 bytes** and the cache holds **4 pools per thread**.[^commit] The cache itself is just a `long[]` of native addresses stored in a new field of `java.lang.Thread`, where 0 means an empty slot.[^commit]

Here's the life of one arena, from the source of `ArenaImpl.OfConfined` and `ConfinedSegmentPool`:[^commit]

1. **Opening is free.** `Arena.ofConfined()` doesn't touch the pool. An arena that never allocates never acquires one, so the many arenas that allocate nothing pay nothing.[^minborg]
2. **The first small allocation acquires a pool.** If both the size and the alignment are at most 64 bytes, the arena takes the first available pool out of the thread's cache and removes it from the cache, so it now belongs exclusively to this arena. If the cache is empty (for example, the very first arena on a thread, or a fifth nested arena), the arena `malloc`s its own 64-byte "local" pool and zeroes it.
3. **Allocations are bump-pointer slices.** The arena keeps an offset into its pool. Each allocation aligns the offset up, checks the slice still fits in 64 bytes, and moves the offset forward. That's a few arithmetic instructions: no `malloc`, no cleanup object. If the slice doesn't fit, or the request is bigger than 64 bytes, it silently falls back to the regular path.
4. **Closing clears and returns the pool.** The arena first runs any ordinary cleanup actions, then zeroes only the part of the pool it used and puts the pool back in a free slot of the thread's cache. If the cache is full, the pool is freed instead.

The zeroing is how the JDK keeps a promise that FFM always made: newly allocated native segments contain zeroes, so one arena can never see bytes left behind by another.[^minborg] New pools are zeroed when created, and on release only the used prefix needs clearing. For pools of 64 bytes or less, the clearing code is an unrolled `switch` that writes up to eight 8-byte zeros without a loop.[^commit]

There's one more subtle rule in step 4. A cleanup action registered by your code might still read the pooled memory, so the pool is cleared and released only *after* all regular cleanup actions have run. The code comment says exactly this: "clear and release the pool only after they have run".[^commit]

#### Virtual threads borrow from their carrier

A per-thread cache is a problem for {{virtual threads|lightweight threads (final in JDK 21) managed by the JVM rather than the OS. Millions can exist at once, and each runs on top of an ordinary "carrier" platform thread}}. Giving every one of potentially millions of virtual threads its own cache would undo their small footprint.[^minborg] So a virtual thread takes its pool from the cache of the {{carrier thread|the platform thread a virtual thread is currently running ("mounted") on. A virtual thread can move to a different carrier whenever it blocks}} it's running on. In code, the arena briefly {{pins|stops a virtual thread from being unmounted from its carrier, so it stays on the same platform thread for a moment}} the virtual thread with `Continuation.pin()`, takes the pool from the carrier's cache, and unpins it.[^commit]

Because the pool is removed from the cache when acquired, it now belongs to the arena, not the carrier. The virtual thread can migrate to another carrier while the arena is open, and if the original carrier thread dies meanwhile, it can't free a pool that's still in use. On close, the pool goes back into the cache of whichever carrier the virtual thread is on *at that moment*.[^minborg] On Oracle's M4 numbers, a pooled 5-byte allocation from a virtual thread takes 3.2 ns against 1.05 ns from a platform thread, still about five times faster than the 15.7 ns non-pooled path.[^minborg]

The cache needs no locks. Only its owning platform thread ever touches it, either directly or while acting as a carrier, so acquire and release are plain array operations.[^commit] When a platform thread terminates, the JDK frees whatever pools are sitting in its cache. Minborg's commit also reorders thread shutdown so this happens *after* terminating thread-locals run, because those callbacks might themselves use confined arenas and return pools.[^commit]

The headline speedups for 5- and 20-byte allocations are 12.3x and 8.6x on Linux AArch64, 6.8x and 7.8x on Linux x64, 18.6x and 16.8x on macOS AArch64, and 16.8x and 18.9x on Windows x64.[^minborg] Above 64 bytes, the two paths perform the same. That's not a regression, it's the design: big allocations never touch the pool.[^minborg] The post also warns that microbenchmark speedups "do not translate directly" to whole applications. The gains matter most when allocating, creating the arena and cleaning up are a big share of a short native call.[^minborg]

#### Why the JDK deleted BufferStack

Before this change, the JDK's own native linker had worked around the cost internally. When a native call needed a temporary buffer (for example for some struct arguments or return values), the linker pushed a "frame" on `BufferStack`, a thread-local 256-byte recycling stack, sized by an internal property, `jdk.internal.foreign.LINKER_STACK_SIZE`.[^bufferstack] The 14 October commit deletes `BufferStack` and its tests and benchmarks. The linker's `newBoundedArena(size)` now simply opens an `Arena.ofConfined()`, allocates the requested size from it, and slices from that.[^bufferstack] The public, general-purpose mechanism replaced a private, special-purpose one. That's good news for everyone else: the JDK isn't keeping a faster path to itself.

### What it means for you

**If you don't call native code, nothing changes.** Most Spring and Jakarta EE developers never touch `java.lang.foreign` directly. You may benefit indirectly as libraries add FFM backends. JLine's `terminal-ffm` module is one example.[^jline]

**If you write FFM code, keep writing it the obvious way.** The safest pattern, a short-lived confined arena per call, is now also the fast one for small scratch values. You don't need hand-rolled thread-local buffer caches or long-lived arenas reused across calls to dodge allocation costs, and the JDK itself has just stopped doing that.[^bufferstack] Code generated by {{jextract|the OpenJDK tool that reads a C header file and generates the Java FFM bindings (layouts and method handles) for it}} and pointer "out-parameters" are among the cases Minborg says benefit most.[^minborg]

**Keep each arena's small allocations under 64 bytes if you can.** The pool is a single 64-byte block per arena. Two 40-byte structs don't both fit: the first comes from the pool and the second takes the regular path. One big allocation followed by small ones is fine, because the big one bypasses the pool and doesn't use it up.[^commit] Alignment matters too: a request aligned to more than 64 bytes always takes the regular path.

**Shared and automatic arenas are unchanged.** Only confined arenas pool.[^minborg] If you use `Arena.ofShared()` for per-call scratch space "just in case", switching to `ofConfined()` gets you the pool, as long as only one thread touches the memory.

**Memory overhead is tiny, but it's per thread.** Each platform thread that uses confined arenas can hold up to four cached 64-byte pools, which is 256 bytes. By our arithmetic, a server with 1,000 platform threads that all do native calls would hold about 250 KB in pools. Virtual threads don't add any, because they borrow from their carriers.[^commit]

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **`malloc` and `free` no longer match your arenas one to one.** Closing a pooled arena may return memory to the JDK's cache instead of the C allocator. Minborg says applications and diagnostic tools "must not assume" a one-to-one correspondence.[^minborg] If you track native memory with allocator hooks or `LD_PRELOAD` tools, expect fewer, longer-lived blocks.
- **The tuning knobs are internal and unsupported.** The source defines `jdk.internal.foreign.native.confined.pool.power.size` (log2 of the pool size, 3 to 20) and `...power.count` (log2 of the pools per thread, 0 to 3). A negative value disables pooling. The code comment says they come with "no behavioral or compatibility guarantees".[^commit] Use them for experiments, not production.
- **`-XX:+PageAlignDirectMemory` turns pooling off.** If direct memory must be page-aligned, slicing small segments from a shared pool would break that, so the pool disables itself.[^commit]
- **This is JDK 28 only.** It's in early-access builds from build 15 onwards and ships in March 2027.[^tags] There's no sign of a backport. It's an internal optimisation, not a fix.
- **Microbenchmarks aren't applications.** The 6.8x–18.9x figures are Oracle's development benchmarks for a single allocation.[^minborg] Measure your own workload before you attribute a speedup to this.
</div>

### What happens next

The code is in the JDK 28 main line, so the next step is simply JDK 28's release in March 2027. Until then you can try it in the early-access builds. Watch the Panama mailing list and JDK bug tracker for tuning of the defaults: the configuration hooks and tests for pool sizes from 8 bytes to 1 MB already exist, which makes it easy to adjust if real-world data argues for it.[^commit]

# Story 2 · Helidon 27 marches to the JDK's six-month beat

<div class="byline">Frameworks · Helidon · JEP 14 · Released with JDK 27 in September, InfoQ deep coverage 16 Oct 2026 · ~13 min read</div>

<p class="opener" markdown="1">Most Java libraries live by one rule: support the oldest JDK your users might still run. That's why so much of the ecosystem only recently left Java 8 behind. Helidon, Oracle's microservices framework, just did the opposite. Version 27 runs only on Java 27, will move up with every JDK release, and leaves its old version line as a slow, stable "tail" for everyone else. It's Helidon's first release under a model that three JDK architects proposed to the whole ecosystem two years ago, and how it goes will tell the rest of us a lot.</p>

### What happened

Helidon 27.0.0 shipped alongside JDK 27 in September. The release was tagged on 17 September, two days after JDK 27's release,[^changelog] and the Helidon team announced it on Inside.java as "the first release under the Tip-and-Tail model used by OpenJDK".[^insidehelidon] On 16 October, InfoQ published the first detailed walkthrough of what changed.[^infoq-helidon]

The changelog sets out the new rules in four sentences. Helidon releases "will now align with JDK releases and the minimum Java requirement will bump to match the corresponding JDK release". Helidon 27 is a feature release. **Helidon 4 is considered the LTS release, and Helidon 29 will be the next one.** And "a minimum of Java 27 is required to use Helidon 27".[^changelog]

The structural changes are just as large:[^changelog]<sup>,</sup>[^upgrade]

- **MicroProfile is out of the main release.** MicroProfile support moved into a separate project, Helidon MicroProfile, which "is not part of the Helidon 27 release" and will release independently. Until it does, the upgrade guide tells MicroProfile users to stay on Helidon 4.5.x.
- **Integrations become "Extensions"**, in their own repository with independent release cycles.
- **HTTP method names are now case-sensitive**: `GET` matches, `get` doesn't.
- **New modules**: Helidon Data JDBC (incubating), Helidon Messaging (preview), and a feature-complete Helidon Declarative (preview).

On the tail side, **Helidon 4.5.5** came out on 15 September. It requires Java 21, recommends Java 25, and is described as "strongly recommended for all users of Helidon 4".[^cl455]

### The background you need

#### What is Helidon?

{{Helidon|Oracle's open-source Java framework for microservices. It started in 2018 as a lightweight web server plus a MicroProfile implementation}} was introduced in September 2018 (its working name was J4C, "Java for Cloud") with two flavours. **Helidon SE** was a small set of libraries (web server, configuration, security) that you wire together yourself. **Helidon MP** implemented {{MicroProfile|a set of Eclipse Foundation specifications for enterprise Java microservices (config, health, metrics, fault tolerance, REST clients), built on Jakarta EE APIs such as CDI and JAX-RS}}.[^infoq-helidon] Helidon 3.0 (2022) moved to JDK 17. In October 2023, Helidon 4.0 replaced its Netty-based server with "Níma", a new web server written for {{virtual threads|lightweight JVM-managed threads, final in JDK 21, that make simple blocking code scale like asynchronous code}}.[^infoq-helidon]

In March 2026, Oracle put Helidon into its new **Java Verified Portfolio** (JVP), a curated set of Oracle-supported tools and libraries. JVP brought commercial Helidon support to "all Java SE subscribers and OCI customers at no additional cost". Before that, it was limited to WebLogic and Coherence customers.[^devops]

#### The problem Tip & Tail solves

Every library maintainer faces the same dilemma. Users who want stability ask for security fixes without new features. Users who want progress ask for new JDK features. Most libraries try to serve both from one release line, and that pleases neither.

In autumn 2024, Alex Buckley, Brian Goetz and Ron Pressler published **JEP 14, "The Tip & Tail Model of Library Development"**.[^jep14] It's an "informational" JEP: a recommendation to the ecosystem, not a feature of the JDK. It names four problems with the usual approach:[^jep14]

- **One size fits all**: every release mixes features and fixes, so stability-minded users must either take risky changes or forgo security patches. And libraries pin themselves to a lowest-common-denominator JDK, often JDK 8.
- **Semantic versioning doesn't fix it**: it labels the kind of change but doesn't let you take fixes without new features.
- **Cascades of change**: a library's bug-fix release often bumps *its* dependencies, dragging major changes through your dependency tree.
- **Multiple release trains are expensive** when lots of fixes are backported between them.

The proposed fix has two kinds of release train. The {{tip|in JEP 14, the single release line that gets new features, enhancements and fixes, and can target a recent JDK}} gets nearly all development. Each {{tail|in JEP 14, an older release line that gets only critical bug fixes and security patches, and targets an older JDK}} exists to "preserve the status quo".[^jep14] In the JEP's words, "the tip release of a library contains new features and bug fixes, while tail releases contain only critical bug fixes."[^jep14] The discipline lies in the rules: backport as little as possible, choose a JDK baseline per train (a recent JDK for the tip, JDK 17 or 21 for a tail), keep tails cheap so you can afford several, and decline backport requests.[^jep14]

#### Helidon's road to 27

Helidon announced the switch in April 2026 with version 4.4.0. InfoQ quoted the plan: Helidon "will change its familiar semantic versioning to match the OpenJDK six-month release cadence", and "Helidon 4.4.0 today will change to Helidon 27".[^infoq44] So the jump from 4 to 27 isn't 23 major releases. The version number now simply *is* the JDK version.

### How it works

#### Two lines, two JDK baselines

The practical result is two Helidon lines with different contracts:

- **Helidon 27 (the tip)** needs Java 27 and Maven 3.8 or later.[^getstarted] Per the changelog, the minimum Java version will bump with each release. InfoQ expects Helidon 28 alongside JDK 28 in March 2027.[^changelog]<sup>,</sup>[^infoq-helidon]
- **Helidon 4.5.x (the tail)** keeps Helidon's familiar version numbers, requires Java 21 and recommends Java 25.[^cl455] InfoQ describes it as focused on critical bugs, security fixes and selected backports, for teams that need a long-lived production base.[^infoq-helidon]

Even the tail is pointing users forward. Helidon 4.5.5 adds an opt-in `case-sensitive-methods: true` listener option and recommends enabling it "to align applications with future Helidon versions".[^cl455] That's a tail doing its job: no new features, but help with crossing to the tip.

#### One repository becomes three

The old Helidon repository contained everything. Now it's split into three projects:[^changelog]<sup>,</sup>[^upgrade]

```viz:layers
title: "What used to be one Helidon release"
layers:
  - {label: "Helidon Core (27.0.0)", sub: "imperative + declarative, needs Java 27", highlight: true}
  - {label: "Helidon MicroProfile", sub: "own repo, 'MP 5', not released yet"}
  - {label: "Helidon Extensions", sub: "per-extension versions (Kafka, OCI …)"}
note: "Helidon Core is InfoQ's name for what was Helidon SE. Repository state checked 17 Oct 2026: helidon-microprofile has no release tags yet; helidon-extensions has 27.0.0 tags for 13 extensions, including the Kafka, JMS and Pulsar messaging connectors."
```

**Helidon Core** replaces Helidon SE and offers two programming models: imperative ("plain Java", no injection or annotations) and declarative.[^infoq-helidon] **Helidon MicroProfile** now has its own repository, whose README says "Java 27 is required to use Helidon MicroProfile 5". So it's back on semantic versioning, starting at 5. When we checked on 17 October, it had no release tags yet.[^mp] **Helidon Extensions** holds the former integrations, each released on its own schedule. It already has 27.0.0 tags for 13 extensions, including Kafka, JMS and Pulsar messaging connectors, Neo4j, HashiCorp Vault and OCI.[^ext]

```viz:codecompare
title: "The same idea, two Helidon programming models"
left:
  title: "Imperative (wire it yourself)"
  code: |
    WebServer.builder()
        .routing(r -> r.get("/greet",
            (req, res) -> res.send("Hello!")))
        .build()
        .start();
right:
  title: "Declarative (generated at build)"
  code: |
    @RestServer.Endpoint
    @Http.Path("/greet")
    @Service.Singleton
    class GreetEndpoint {
        @Http.GET
        String greet() { return "Hello!"; }
    }
note: "Simplified from the Helidon 27 WebServer and Declarative docs. Declarative needs the helidon-bundles-apt annotation processor."
```

#### Declarative, without runtime magic

{{Helidon Declarative|Helidon's annotation-based programming model. You write annotated classes, and an annotation processor generates the plain Helidon code and wiring at build time}} gives you annotation-driven code without runtime reflection. Its documentation explains how: it generates all the necessary code at build time "to avoid reflection and bytecode manipulation at runtime", and the generated code uses Helidon's imperative APIs, so performance matches a hand-written imperative app.[^decl] It's now a {{preview feature|in Helidon's terms, production-ready and backward compatible within a major version, but allowed to change in a later major version without the usual deprecation cycle}}, and it covers HTTP endpoints, typed HTTP and gRPC clients, fault tolerance, scheduling, validation, security, metrics, tracing, WebSocket, GraphQL, CORS and health checks.[^decl]

The declarative app starts from a generated class rather than by scanning the classpath: `ServiceRegistryManager.start(ApplicationBinding.create())`, with a `@Service.GenerateBinding` annotation on `main` to "bypass discovery and runtime binding".[^decl]

#### Messaging without reactive streams

**Helidon Messaging** is new, and its design says a lot about where Java has gone since virtual threads. InfoQ notes that it uses ordinary blocking Java and avoids reactive APIs such as MicroProfile Reactive Messaging: you annotate a method, and it's called once per message.[^infoq-helidon]<sup>,</sup>[^msg]

```java
@Service.Singleton
final class OrderHandler {
    @Messaging.ReceiveFrom("orders")
    void receive(Order order) {
        // Process one order.
    }
}
```

Channels such as `orders` are logical names, bound through configuration to a connector (Kafka, JMS or Pulsar, from Helidon Extensions). The delivery contract is explicit: the default is "synchronous and at least once", so handlers "must tolerate duplicate delivery".[^msg] A handler can take the payload, a `Message<T>` envelope with headers, or a whole `MessageBatch<T>`.[^msg] {{At-least-once delivery|a messaging guarantee that every message is processed, but some may be processed more than once (for example after a crash), so handlers must be idempotent}} means your handlers must be idempotent, and it's good to see the guarantee written down so plainly.

#### Data: two different things with similar names

InfoQ describes "Helidon Data JDBC" as a repository API over ORM.[^infoq-helidon] Helidon's own docs show there are really two separate pieces, and the difference matters:[^data]

- The **Helidon Data Repository** (preview) is the ORM one. You write an interface annotated with `@Data.Repository`, extend `Data.CrudRepository<Pet, Integer>`, and declare methods like `Optional<Pet> findByName(String name)`, or add a `@Data.Query` with JPQL. The implementation is generated at compile time on top of {{Jakarta Persistence|the standard Java ORM API (formerly JPA). Hibernate and EclipseLink are implementations}}, with EclipseLink or Hibernate.
- **Helidon Data JDBC** (incubating, "not production ready") is the new one in 27. It has no entity management and doesn't derive queries from method names. You write the SQL in a `@Jdbc.Statement` annotation, map results onto a record, and Helidon generates the JDBC code at compile time. There's also an imperative `JdbcClient` for queries built at runtime.

```java
@SuppressWarnings(Api.SUPPRESS_INCUBATING)
@Data.Repository
@Data.Provider("jdbc")
@Jdbc.Client("contacts")
public interface ContactRepository {
    @Jdbc.Statement("""
        SELECT ID AS id, NAME AS name
        FROM CONTACT WHERE ID = :id""")
    Optional<Contact> findById(long id);
}
record Contact(long id, String name) {}
```

That `@SuppressWarnings` line points to another change in Helidon 27: **API stability is now enforced by the compiler**. Every public Helidon API is annotated as `@Api.Stable`, `@Api.Preview`, `@Api.Incubating` or `@Api.Internal`,[^api] and an annotation processor rejects uses of incubating APIs by default. You opt in per package, type or method with `Api.SUPPRESS_INCUBATING`, or project-wide with `-Ahelidon.api.incubating=warn`.[^data] It's the framework equivalent of the JDK's `--enable-preview`: you can't use something unfinished by accident.

### What it means for you

The upgrade guide is unusually direct, so let's follow it.

**If you run Helidon MP (CDI, JAX-RS, MicroProfile), stay on 4.5.x for now.** The guide says not to upgrade those workloads to Helidon 27 "unless you are also replacing the MP programming model with Helidon Core APIs", and to wait for the independent MicroProfile release.[^upgrade] Since Helidon 4 is the LTS line,[^changelog] staying there isn't a cop-out. It's the supported path.

**If you run Helidon SE and you're happy on Java 21 or 25, you can also stay put.** That's the tail's job. Just take patch releases such as 4.5.5, and start the preparation the guide recommends on 4.x: fix deprecation warnings and turn on `case-sensitive-methods: true`.[^cl455]<sup>,</sup>[^upgrade]

**If you want the tip, budget for a JDK upgrade every six months.** Helidon 27 needs Java 27, and the rule is that the minimum rises with each release.[^changelog] Your toolchains, CI images, container images and native-image builds all have to move with it, and the guide lists every one of them.[^upgrade] Remember that Java 27 isn't an LTS release: Oracle's roadmap, for example, shows JavaFX 27 support ending in March 2027, when JDK 28 arrives.[^jvproad] Running the tip means always running a recent JDK.

**Expect a checklist of breaking changes when you move:**[^upgrade]

- Remove dependencies on modules that no longer exist (`helidon-microprofile*`, `helidon-integrations*`, the Jaeger, Zipkin and OpenTracing providers, `helidon-metrics-prometheus`, `helidon-cors` and more), and use the replacements (for example `helidon-webserver-cors` and the OpenTelemetry tracing provider).
- Former integrations move from `io.helidon.integrations` to `io.helidon.extensions` coordinates, with a few exceptions (OCI becomes `oci.v3`, Vault becomes `hashicorp.vault`).
- `Config.global(config)` is gone. Use `Services.set(Config.class, config)`.
- `@Service.Provider` is removed. Use an explicit scope such as `@Service.Singleton`.
- Uppercase all HTTP method names in configuration (`GET`, not `get`).

<div class="box realworld" markdown="1">
**🌍 In the real world: who else works this way?**

JEP 14 itself names two precedents. The JDK has used tip and tail since JDK 10 in 2018, with 17.0.x and 21.0.x as fix-only tails. Spring Boot puts new features only into a six-monthly tip and keeps some releases, like 2.7, alive as longer tails.[^jep14] Helidon takes the model to its strictest form: a tip whose *minimum JDK* is the newest JDK itself. Whether users accept a six-month JDK treadmill in exchange for the newest features is the experiment Helidon is now running for everyone.
</div>

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **"27" isn't a sign of 23 missed releases.** It's the JDK version. Helidon 4.4.0 effectively *became* 27.[^infoq44]
- **No MicroProfile on 27 yet.** The new Helidon MicroProfile repository had no release tags when we checked on 17 October.[^mp] InfoQ's write-up says MicroProfile "continues to support" the specs, but the changelog and upgrade guide say it isn't part of 27 "at this time".[^infoq-helidon]<sup>,</sup>[^upgrade]
- **Stability labels are real now.** Data JDBC is incubating: "not production ready", and liable to change or be removed in any release.[^data] Messaging and Declarative are preview.[^msg]<sup>,</sup>[^decl] The compiler will reject incubating APIs until you opt in.[^data]
- **Messaging is at-least-once by default.** Make handlers idempotent. The `DROP` failure policy is an explicit opt-in to discarding messages.[^msg]
- **Extensions arrive on their own schedule.** The guide warns that not all extensions "might be available initially". Gson media support, for example, ships separately: the guide planned it for after Helidon 27, and a `gson/27.0.0` extension tag now exists.[^upgrade]<sup>,</sup>[^ext]
</div>

### What happens next

Three dates are worth watching. First, the Helidon MicroProfile 5 release, which unblocks MP users who want the tip.[^mp] Second, **Helidon 28 with JDK 28 in March 2027**, the first time the tip has to move to a new JDK on schedule.[^infoq-helidon] Third, **Helidon 29**, announced as the next LTS.[^changelog] JDK 29 is planned as the next Java LTS in September 2027.[^jvproad] If Helidon 29 lines up with it, Helidon users get a new tail on a new LTS JDK, which is the JEP 14 model working exactly as intended.

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **Helidon**: Oracle's open-source Java microservices framework, launched in 2018.
- **MicroProfile**: Eclipse Foundation specifications for enterprise Java microservices, built on Jakarta EE APIs like CDI and JAX-RS.
- **Virtual threads**: lightweight JVM-managed threads (final in JDK 21) that let blocking code scale.
- **Tip**: in JEP 14, the one release line that gets new features and can target a recent JDK.
- **Tail**: in JEP 14, an older line that gets only critical fixes and security patches, on an older JDK.
- **Helidon Declarative**: Helidon's annotation model, turned into plain Helidon code at build time.
- **Preview feature (Helidon)**: production-ready, compatible within a major version, but may change in the next major version without deprecation.
- **At-least-once delivery**: every message gets processed, but possibly more than once, so handlers must be idempotent.
- **Jakarta Persistence**: the standard Java ORM API (formerly JPA). Hibernate and EclipseLink implement it.
</div>
