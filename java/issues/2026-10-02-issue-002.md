# Part 1 · Learn

## ✂️ `var`, text blocks and switch expressions: small features, big readability wins

<span class="tag learn">CATCH-UP</span><span class="tag learn">~10 MIN</span><span class="tag learn">LEVEL 3</span>

**These three features change no architecture, but they touch almost every file you'll write.** That's exactly why they're worth ten minutes. Each one removes a class of noise, and each one has a rule that, ignored, gives you a bug the old syntax never could. Yesterday's map showed them in passing. Today we take each apart.

| Feature | Final in | JEP | Removes |
|---|---|---|---|
| `var` for local variables | 10 | 286 | Repeating a type the reader can already see |
| `var` in lambda parameters | 11 | 323 | The choice between annotations and short lambdas |
| Switch expressions (`->`, `yield`) | 14 | 361 | Fall-through bugs and "assign in every branch" |
| Text blocks (`"""`) | 15 | 378 | `+ "\n" +` chains and escaped quotes |

All four are in every LTS from 17 onward, so if you're on 17, 21 or 25 you can use them today. [(Oracle, language changes by release)](https://docs.oracle.com/en/java/javase/25/language/java-language-changes-release.html)

### 1 · `var`: inference, not dynamic typing

**`var` asks the compiler to write the type for you. It does not make Java dynamic.** The variable still has one static type, fixed at compile time, and the class file records that type exactly as if you'd written it. `var` is allowed for locals with an initializer, loop variables, try-with-resources and (since 11) lambda parameters. It is not allowed for fields, method parameters or return types. [(Oracle docs)](https://docs.oracle.com/en/java/javase/22/language/local-variable-type-inference.html)

The OpenJDK team published a style guide for it, and its first principle is the one to remember: **reading trumps writing.** Use `var` when the initializer already tells the reader the type, like a constructor or a well-named factory method. Skip it when the type *is* the information. [(OpenJDK LVTI style guide)](https://openjdk.org/projects/amber/LVTIstyle.html)

```viz:codecompare
title: "var: naive vs correct"
left:
  title: "Naive: compiles, then surprises"
  code: |
    // Diamond + var: infers Object!
    var queue = new PriorityQueue<>();
    queue.add("order-42");
    queue.add(42);   // compiles fine...
    // ...ClassCastException at runtime

    var total = 0;   // int, not long
    total += bigInvoice; // silently narrows

    var result = service.process(req);
    // Result? Optional? Future? Who knows.
right:
  title: "Correct: type on the right"
  code: |
    // Put the type argument on the right
    var queue = new PriorityQueue<String>();
    queue.add("order-42");
    queue.add(42);   // compile error. Good.


    var total = 0L;  // say long, get long
    total += bigInvoice;

    PaymentResult result =
        service.process(req); // type matters
note: "We compiled and ran the left pane on JDK 21: the second `add` throws `ClassCastException` from inside `PriorityQueue`. `total += bigInvoice` compiles because compound assignment includes an implicit cast. The pitfalls are guidelines G6 and G7 in the [OpenJDK style guide](https://openjdk.org/projects/amber/LVTIstyle.html)."
```

Three habits cover most of the guide:

- **Never pair `var` with `<>`.** With nothing on either side to infer from, the type argument becomes `Object`.
- **Watch numeric literals.** `var x = 0` is an `int`. Use `0L`, `0.0` or an explicit type when you mean something else.
- **Keep scopes small and names descriptive.** `var customers` in a 6-line method is clearer than `List<Customer> list` in a 60-line one. [(OpenJDK LVTI style guide)](https://openjdk.org/projects/amber/LVTIstyle.html)

### 2 · Text blocks: the compiler eats your indentation (on purpose)

**A text block is just a `String` constant with nicer syntax.** We checked with `javap`: it compiles to an ordinary `ldc` of a string in the constant pool, so there's zero runtime cost, and it's interned like any literal. What's new is how the compiler turns your source lines into that string. It runs three steps, in this order:

```viz:flow
title: "How javac turns a text block into a String"
headers: [Step 1, Step 2, Step 3]
columns:
  - - label: Normalize lines
      sub: "CRLF / CR become \\n"
  - - label: Strip whitespace
      sub: "common indent + trailing"
      style: accent
  - - label: Interpret escapes
      sub: "\\n, \\t, \\s, \\<newline>"
      style: soft
note: "Because escapes are processed *after* stripping, `\\s` (a space) survives at the end of a line, and `\\` at the end of a line joins it to the next. Source: [Oracle, Programmer's Guide to Text Blocks](https://docs.oracle.com/en/java/javase/21/text-blocks/index.html)."
```

**The closing `"""` sets the left margin.** The compiler finds the least-indented line (and the closing delimiter's line counts) and removes that much from every line. Put the closing delimiter at column 0 and you keep all the leading spaces. Trailing spaces on each line are always removed, so an editor that trims whitespace can't silently change your string. [(Oracle guide)](https://docs.oracle.com/en/java/javase/21/text-blocks/index.html)

```java
String sql = """
    SELECT id, total
    FROM orders
    WHERE city = ?
    """;           // == "SELECT id, total\nFROM orders\nWHERE city = ?\n"

String msg = """
    Dear %s, your order %d \
    has shipped.\s""".formatted(name, id);  // one line, trailing space kept
```

Oracle's guide adds two style rules worth adopting. **Don't use a text block for a one-line string**, and **don't mix tabs and spaces** in the indentation: each whitespace character counts as one, so a tab isn't eight spaces. `-Xlint:text-blocks` warns you about it. [(Oracle guide)](https://docs.oracle.com/en/java/javase/21/text-blocks/index.html)

### 3 · Switch expressions: `switch` that returns a value

**The arrow form (`case X ->`) never falls through, and a `switch` used as an expression must cover every case.** Those two rules kill the two classic `switch` bugs: the forgotten `break`, and the variable that one branch forgot to assign. Oracle's docs recommend the arrow form for new code. [(Oracle docs)](https://docs.oracle.com/en/java/javase/21/language/switch-expressions.html)

A few rules people trip over:

- **`yield`, not `return`, gives a block its value.** `return` inside a switch expression is a compile error, because it would leave the whole method. [(Oracle docs)](https://docs.oracle.com/en/java/javase/21/language/switch-expressions.html)
- **Leave out `default` on enum switches when you can.** If you cover every constant, the compiler adds a hidden one for you, and a new constant becomes a build error instead of a silent no-op. [(Oracle docs)](https://docs.oracle.com/en/java/javase/21/language/switch-expressions.html)
- **The arrow form also works as a plain statement.** You don't need to produce a value to get rid of fall-through.

This is the same exhaustiveness check that makes sealed types and pattern matching so useful. That's the topic a few issues from now.

```viz:codecompare
title: "Shipping fee: statement vs expression"
left:
  title: "Java 8: statement + fall-through"
  code: |
    int fee;
    switch (tier) {
      case FREE:
        fee = 99;
      case PLUS:          // no break above!
        fee = 0;          // FREE gets 0 too
        break;
      case PRO:
        fee = 0;
        break;
      default:
        throw new IllegalStateException();
    }
right:
  title: "Java 14+: expression, no fall-through"
  code: |
    int fee = switch (tier) {
      case FREE      -> 99;
      case PLUS, PRO -> 0;
      case ENTERPRISE -> {
        log.info("contract pricing");
        yield contract.fee();
      }
    }; // no default: the compiler checks
       // every enum constant is covered
note: "Illustrative. On the left, a missing `break` makes free-tier customers ship for free, and nothing warns you. On the right, `case PLUS, PRO` groups labels, and `yield` returns a value from a block. Forget a constant and the code doesn't compile."
```

<div class="box realworld" markdown="1">
**🌍 In the real world: the JDK team's own rules for `var`**

When `var` shipped in Java 10, the OpenJDK team didn't just add the keyword. Stuart Marks published a **style guide with four principles and seven guidelines**, because the team expected exactly the misuse we showed above. Its core point: code is read far more than it's written, and often **outside an IDE** (in code review, patches and docs), where nobody can hover to see a type. So `var` is right when the name and initializer carry the meaning, and wrong when they don't. [(OpenJDK LVTI style guide)](https://openjdk.org/projects/amber/LVTIstyle.html) It's a short read and a good thing to link from your team's code-review checklist.
</div>

<div class="box gotcha" markdown="1">
**💥 Gotcha: the enum constant you didn't compile against**

Exhaustive enum switches are checked at **compile** time. Say a shared library adds `Status.REFUNDED` and you upgrade the jar **without recompiling** your service. Your `switch` hits a constant it has never heard of. We tried it on JDK 21: the hidden `default` the compiler inserted throws **`java.lang.MatchException`**. Older releases (14–20) threw `IncompatibleClassChangeError` instead. The old switch *statement* would have silently skipped all branches. A loud failure is better than a silent one, but it means **an enum in a shared library is part of its public contract**. Recompile when you upgrade, and treat new constants as a breaking change.
</div>

<div class="box devs" markdown="1">
**🔬 Under the hood**

- **`var` leaves no trace.** The class file stores the inferred type, so `var list = new ArrayList<String>()` compiles exactly like `ArrayList<String> list = …`. It's not even a keyword: it's a *reserved type name*, so `var var = 1;` compiles, but a class named `var` doesn't. [(Oracle docs)](https://docs.oracle.com/en/java/javase/22/language/local-variable-type-inference.html)
- **Enum switches use a lookup table.** `javap` shows javac generating a synthetic class with a `$SwitchMap$Status` int array that maps each constant's `ordinal()` to a case. That indirection is why reordering an enum doesn't break compiled switches.
- **String switches hash first.** javac calls `hashCode()`, jumps to a bucket, then confirms with `equals()`. That's also why `switch` on a `null` String throws `NullPointerException` (unless you add `case null`, which needs Java 21's pattern switch).
</div>

<div class="box tryit" markdown="1">
**🧪 Try it (15 minutes, any JDK 17+)**

1. In `jshell`, run `var q = new java.util.PriorityQueue<>(); q.add("a"); q.add(1);` and read the exception. Then change it to `PriorityQueue<String>` and watch the second `add` become a compile error.
2. Paste a text block with the closing `"""` indented, then again with it at column 0. Compare `.length()` of the two.
3. The separate-compilation trap. Make `Status.java` (`enum Status { NEW, PAID }`) and a `Main.java` with an arrow switch over both constants and no `default`. Compile both and run. Then add `REFUNDED`, recompile **only** `Status.java`, and run `Main` again (have its `main` loop over `Status.values()`). You'll get the `MatchException` from the Gotcha box.
</div>

## Top story 1 · Update: Valhalla's value objects are coming to JDK 28

<span class="tag hot">BIG DEAL</span><span class="tag watch">PREVIEW IN 28</span>

**What happened.** Oracle's Java team announced that **JEP 401, Value Objects (Preview), is targeted to JDK 28**. [(inside.java)](https://inside.java/2026/09/20/jep401-target-jdk28/) Its companion, **JEP 539, Strict Field Initialization in the JVM (Preview)**, was targeted on 26 September. [(inside.java)](https://inside.java/) *A correction: yesterday's issue said value classes weren't officially targeted. They had been since 20 September. Sorry about that.*

JEP 401 adds a **`value` modifier** for classes and records whose instances have **no identity**, only their field values. Fields are implicitly final, and `==` compares two value objects by class and field values. [(InfoQ)](https://www.infoq.com/news/2026/08/jep401-value-objects-preview/)

```viz:codecompare
title: "Identity object vs value object"
left:
  title: "Today: every object has identity"
  code: |
    record Point(int x, int y) {}

    var a = new Point(3, 4);
    var b = new Point(3, 4);
    a == b;       // false: two objects
    a.equals(b);  // true
    synchronized (a) { … } // allowed
right:
  title: "JDK 28 preview: value record"
  code: |
    value record Point(int x, int y) {}

    var a = new Point(3, 4);
    var b = new Point(3, 4);
    a == b;       // true: same values
    a.equals(b);  // still true
    synchronized (a) { … } // not allowed
note: "Preview only: compile and run with `--enable-preview` on JDK 28. Syntax and semantics as described by [InfoQ's JEP 401 write-up](https://www.infoq.com/news/2026/08/jep401-value-objects-preview/)."
```

**Why it matters.** Without identity, the JVM is free to **scalarize** a value object (keep its fields in registers) or **flatten** it into the fields and arrays that hold it, instead of allocating a separate heap object behind a pointer. With preview enabled, the JDK also treats classes like `Integer` and `LocalDate` as value classes. [(InfoQ)](https://www.infoq.com/news/2026/08/jep401-value-objects-preview/) JEP 539 is the JVM-level groundwork: it lets the verifier insist that certain fields are set before a constructor finishes. [(InfoQ)](https://www.infoq.com/news/2026/08/jep401-value-objects-preview/)

The JEP is explicit that this is **not an invitation to drop `equals`**. And there are new failure modes: synchronizing on a value object or making a `WeakReference` to one fails, which matters if old code synchronizes on `Integer` instances. [(InfoQ)](https://www.infoq.com/news/2026/08/jep401-value-objects-preview/)

<div class="box care" markdown="1">
**👀 What to do.** Nothing in production: this is a preview in a non-LTS release. Two cheap moves now: **grep for `synchronized` on boxed types or `LocalDate`**, which was already discouraged and becomes an error under the preview. And when JDK 28 early-access builds include the feature, try a `value record` for a hot small type (money, coordinates) and measure allocation with JFR.
</div>

## Top story 2 · What got faster in JDK 27, with the receipts

<span class="tag dev">PERFORMANCE</span><span class="tag try">FREE WINS</span>

**What happened.** On 28 September, Per-Åke Minborg and Claes Redestad of Oracle published a roundup of **JDK 27's performance changes** across libraries, GC, the JIT compiler and runtime, each linked to its JBS issue. [(inside.java)](https://inside.java/2026/09/28/performance-update-jdk27/) The one most Spring apps will feel: **`HashMap.putAll()` and the `HashMap(Map)` constructor** got a fast path when the source is itself a `HashMap` or an unmodifiable map backed by one (JDK-8371656).

```viz:bars

    display: "≈10,593 ns"
  - label: JDK 27
    value: 1533
    display: "≈1,533 ns"
    highlight: true
note: "One JMH benchmark on AWS Graviton, from the pull request, as reported by [inside.java](https://inside.java/2026/09/28/performance-update-jdk27/). The gain ranged from 61% (5 entries) to 86% (this case). The authors stress these are **local effects**, not whole-application speed-ups."
```

**The rest of the list, briefly** [(inside.java)](https://inside.java/2026/09/28/performance-update-jdk27/):

- **Crypto:** AES/ECB throughput up about 37% on one Intel CPU, SHA-3 up 16–39% with AVX2, and ML-KEM up 9–17%.
- **GC:** fixes for pathological cases, including **G1 pauses of 90+ seconds** caused by per-region code-root sets, and a Parallel GC feedback loop that caused repeated Full GCs.
- **I/O:** a redundant `fstat` call removed when opening files on Unix, about 14% faster in a stress benchmark.
- **Runtime:** compact object headers on by default (12-byte headers become 8), plus an object-monitor table now on by default, with a fix for a 30% regression in synchronization-heavy code.

**Why it matters.** None of these need a code change. That's the quiet argument for staying close to current JDKs: you collect dozens of small wins like these every six months. It also shows why **micro-benchmarks need context**. A 7× faster map copy matters only if map copying shows up in your profile.

**Structured concurrency** has been a preview through seven rounds (JDK 27 had the seventh, JEP 533). JEP 543 proposes finalizing it in JDK 28 without further change. [(JVM Weekly)](https://www.jvm-weekly.com/p/jdk-27-is-here-jvm-weekly-vol-192) The implementation pull request by Alan Bateman removes the preview annotations and bumps `@since` to 28. **Why it matters.** Once structured concurrency is final, you can use it without `--enable-preview`. It will likely reach most teams through the next LTS, Java 29 in September 2027. The Mac change is about **build agents and laptops**. Intel Mac CI runners and older developer machines will eventually need an Apple Silicon or Linux replacement. JDK 25 LTS keeps working on them in the meantime.

<div class="box revision" markdown="1">
**📌 Revision card**

- **`var` is static typing.** The compiler writes the type; the class file records it. Locals only: no fields, parameters or return types.
- **Never `var x = new Foo<>()`.** The diamond infers `Object`. Put the type argument on the right.
- **`var n = 0` is an `int`.** Use `0L` or an explicit type when you mean `long`.
- **Text blocks: the closing `"""` sets the margin.** Trailing spaces are stripped; use `\s` to keep one and `\` to join lines.
- **Arrow `case` never falls through.** Switch expressions must be exhaustive, and blocks return with `yield`, not `return`.
- **No `default` on enum switches** turns a new constant into a compile error. Unrecompiled code gets a `MatchException`.
- **JDK 28 (Mar 2027):** value objects (JEP 401) in preview, structured concurrency proposed final (JEP 543), Intel Mac port deprecated (JEP 541).
