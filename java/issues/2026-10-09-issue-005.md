# Story 1 · Structured concurrency: Java's parallel tasks get a parent

<div class="byline">JDK 28 · OpenJDK · Project Loom · JEP 543 Candidate, implementation under review (Oct 2026) · ~16 min read</div>

<p class="opener" markdown="1">Here's a bug that has probably shipped in your codebase. A request handler fires off two calls in parallel: one for the user, one for their orders. The user call fails after 200 milliseconds. Your handler returns an error straight away, right? It doesn't. It waits, quietly, for the orders call to finish a full second later, and then throws away the result. Nobody wrote that behaviour on purpose. It's simply what Java's concurrency tools do when you don't tell them otherwise. After four years of experiments, Java is about to ship a standard fix.</p>

### What happened

In September, **JEP 543, "Structured Concurrency"**, was promoted from a draft to a {{Candidate|a JEP that the OpenJDK community has accepted as worth doing, but that hasn't yet been assigned to a specific release}}. InfoQ's roundup described its aim as letting Java "treat groups of related tasks running in different threads as a single unit of work", and reported that it would finalise the feature with no changes.[^infoq-sep07] An open-source project tracking the JEP noted it "was a Candidate as of 2026-09-17" and summarised the proposal as finalising structured concurrency "in JDK 28 without change from JDK 27".[^streamarr]

The implementation is already in review. Pull request #32602 in the OpenJDK repository, titled "8391460: Implement JEP 543: Structured Concurrency" and opened by Alan Bateman, makes the `StructuredTaskScope` API permanent: it removes the preview annotation, sets the `@since` tags to 28, and stops the tests from enabling preview features. Its other changes are documentation polish. As of this week the PR is still open, with a {{CSR|Compatibility and Specification Review: OpenJDK's formal sign-off for any change to a public Java API}} (JDK-8391461) not yet approved.[^pr32602]

One precise point on status: JEP 543 isn't yet *targeted* to JDK 28. It wasn't in InfoWorld's 24 September list of JDK 28 features, and Inside.java's "targeted to JDK 28" announcements up to 6 October don't include it.[^infoworld]<sup>,</sup>[^inside-jdk28] What has happened is that the proposal, the plan and the code all point at JDK 28, the non-LTS release due in March 2027.[^infoq-so-far]

Why is a status change on a library API a big deal? Because it ends one of the longest-running previews in Java's history. Once it's final, you can use it without the `--enable-preview` flag, which means libraries and frameworks can finally depend on it.

### The background you need

#### Threads, futures and the problem with "fire and forget"

A {{thread|an independent path of execution inside your program; several threads can run at the same time}} is how Java does several things at once. For years the usual way to run work on other threads has been an {{ExecutorService|a JDK object that owns a pool of threads and runs the tasks you submit to it}}. You `submit()` a task and get back a {{Future|a handle to a result that will be available later; get() blocks until it's ready}}.

That model has a hidden flaw: the executor has no idea that your two tasks belong together. Look at this code. It's the natural way to write "fetch two things in parallel" in Java 21:

```java
// Works on JDK 21+. Both tasks run on virtual threads.
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> user   = executor.submit(() -> findUser());
    Future<String> orders = executor.submit(() -> fetchOrders());
    return new Dashboard(user.get(), orders.get());
}
```

Now suppose `findUser()` throws after 200 ms and `fetchOrders()` takes a second. `user.get()` throws, so we leave the `try` block. But closing the executor waits for every task it started, so we're stuck there until `fetchOrders()` finishes, even though its result is now useless. We compiled and ran exactly this scenario on JDK 21: the method failed after **1,027 ms**, and the orders call ran to completion. If you swap the order of the two `get()` calls, the behaviour changes again, because you only notice a failure when you happen to ask for that particular result.

It gets worse without try-with-resources. If you use a long-lived shared executor (the Java 8 habit), nothing waits at all: the orphaned task keeps running in the background after your method has returned. That's a {{thread leak|a thread that keeps running or waiting after the code that started it has finished and forgotten about it}}. Multiply it by thousands of requests and you have wasted connections, wasted CPU and very confusing logs.

The HappyCoders guide to the feature lists the full set of problems: a failure in one subtask doesn't stop the others; cancelling the parent doesn't cancel the children; "first result wins" needs complicated code; and in a {{thread dump|a snapshot of what every thread in a running JVM is doing, used for debugging}} you just see generic `pool-X-thread-Y` names, with nothing linking a worker thread to the request that started it. The author calls this "unstructured concurrency".[^happycoders]

#### The idea: concurrency shaped like your code

{{Structured concurrency|a style of concurrent programming in which tasks started inside a block of code must finish before that block ends, just as a method call finishes before the caller continues}} borrows a principle you already rely on every day. When method A calls method B, B finishes before A continues. Errors from B flow back to A. You can read the code top to bottom and know what's running.

Structured concurrency applies the same rule to threads. You open a {{scope|a block of code that owns a group of concurrent tasks and doesn't end until all of them have ended}}, start some {{subtasks|the pieces of work forked inside a scope, each running on its own thread}} inside it, and wait for them at a single point. When the block ends, all of its threads have ended too. If one subtask fails, the scope can cancel the rest. The relationship between parent and children is visible in the code, and, as we'll see, in the thread dump as well.

#### Why it waited for virtual threads

This only became practical once threads got cheap. A classic Java thread, now called a {{platform thread|a Java thread backed one-to-one by an operating-system thread; expensive, so you typically pool a few hundred}}, is too expensive to create per subtask. {{Virtual threads|lightweight threads managed by the JVM rather than the OS; you can create millions, so you no longer need to pool them}} changed that. They became final in JDK 21 through JEP 444, as part of {{Project Loom|the OpenJDK project that delivered virtual threads, scoped values and structured concurrency}}.[^danvega] With a thread per subtask costing almost nothing, "start a thread for each piece of work and throw it away afterwards" becomes the obvious design. Structured concurrency gives that design rules.

#### Four years and nine rounds

Structured concurrency has been in the JDK for a long time, just never as a finished API. New Java features usually arrive first as an {{incubator|an experimental module, outside java.base, used to gather early feedback on an API}} and then as a {{preview API|a complete but not yet permanent API that you can only use with the --enable-preview flag, so it can still change}}. This one went through two incubator rounds and seven previews, and the design changed a lot along the way.[^happycoders]<sup>,</sup>[^infoq-sep07]

In the JDK 21 preview you created a scope with a constructor and chose its policy by picking a subclass. Oracle's JDK 21 guide shows `new StructuredTaskScope.ShutdownOnFailure()`, which "captures the first exception thrown by one of its subtasks, then invokes the shutdown method", and its sibling `ShutdownOnSuccess`, which stops everything once one subtask succeeds.[^oracle-guide21]

The fifth preview in JDK 25 (JEP 505) was the big redesign. Constructors were replaced by static factory methods: `new StructuredTaskScope<>()` became `StructuredTaskScope.open()`, and a custom completion policy is now passed in as a separate object, a `Joiner`.[^infoq-jep505] Then came two rounds of refinement. JDK 26 (JEP 525) renamed `anySuccessfulResultOrThrow()` to `anySuccessfulOrThrow()`, made `allSuccessfulOrThrow()` return a plain `List` and added a timeout callback.[^happycoders] JDK 27 (JEP 533), targeted in May, cleaned up exceptions and types, which we'll get to in a moment.[^inside-533]<sup>,</sup>[^infoq-533]

Not everyone loved every round. In September 2025, Adam Warski of SoftwareMill published a critique of the fifth preview. He praised its guarantee that scopes don't finish until their forks do, but argued that the scope's main body isn't interrupted when a subtask fails, that ending a scope early needs "tricks", and that `Subtask.get()` is confusingly named because, unlike `Future.get()`, it never blocks.[^warski] Some of that feedback is reflected in the later changes. Some of it, such as the `get()` name, is part of the API that's now proposed as final.

### How it works

#### The basic shape: open, fork, join, close

Here's the same dashboard method written with the API as it stands in JDK 27, which is exactly what JEP 543 proposes to make final. The first example in the JDK 27 Javadoc has the same shape.[^javadoc-sts]

```java
// JDK 27 with --enable-preview; proposed final, no flag, in JDK 28.
try (var scope = StructuredTaskScope.open()) {
    Subtask<String> user   = scope.fork(() -> findUser());
    Subtask<String> orders = scope.fork(() -> fetchOrders());
    scope.join();   // throws ExecutionException if either fails
    return new Dashboard(user.get(), orders.get());
}
```

Four things happen, and each has a rule.

1. **`open()`** creates the scope. The thread that opens it is its {{owner|the thread that opened a scope; only it may join and close it}}. The no-argument version uses the default policy: wait for all subtasks, and cancel the rest if any fails.[^happycoders]
2. **`fork()`** starts a subtask, by default in a brand-new virtual thread, and returns a `Subtask` handle straight away.
3. **`join()`** is the single place where the owner waits. If a subtask fails, the scope is cancelled: every unfinished subtask's thread is {{interrupted|sent Java's standard "please stop" signal, which blocking calls such as sleep() and most I/O respond to by throwing InterruptedException}}, and `join()` throws an `ExecutionException` whose cause is the original error.
4. **`close()`**, called automatically at the end of the {{try-with-resources|the try (var x = ...) form of a try block, which guarantees x.close() runs when the block exits, even on an exception}} block, makes sure nothing is left running.

Run it against the same failing user service and the difference is immediate. Dan Vega's comparison measured about 209 ms to fail with a scope, against a full second with plain futures.[^danvega] We saw the same thing on JDK 21 using the older preview API (`ShutdownOnFailure`, compiled with `--enable-preview`): 228 ms, with the orders call interrupted before it finished.

One subtlety: cancellation is {{cooperative|it works only if the code being cancelled checks for the signal; Java can't forcibly kill a thread}}. Interrupting a thread that's sleeping or waiting on most I/O makes it stop quickly. A task stuck in a tight CPU loop that never checks `Thread.interrupted()` will hold the scope open until it finishes.[^danvega]

#### Joiners: choosing the policy

The default policy suits "I need all of these". For other shapes you pass a {{Joiner|an object that decides when a scope is done and what join() returns or throws}} to `open()`. The JDK 27 Javadoc lists the built-in ones:[^javadoc-joiner]

- `Joiner.awaitAllSuccessfulOrThrow()`: the default behaviour. `join()` returns `null` and you read each `Subtask`.
- `Joiner.allSuccessfulOrThrow()`: `join()` returns a `List` of all the results, or throws if any failed.
- `Joiner.anySuccessfulOrThrow()`: returns the first successful result and cancels the rest. That's the "race several replicas, take the fastest" pattern. It throws only if every subtask failed.
- `Joiner.allUntil(predicate)`: waits until everything finishes or your predicate says "enough", and returns the list of `Subtask` handles so you can inspect each one.

```java
// Ask three mirrors; first good answer wins, the rest are cancelled.
try (var scope = StructuredTaskScope.open(
        Joiner.<Price>anySuccessfulOrThrow())) {
    mirrors.forEach(m -> scope.fork(() -> m.quote(sku)));
    return scope.join();
}
```

Each `Subtask` ends in one of three states: `SUCCESS`, `FAILED`, or `UNAVAILABLE` (it was cancelled, or didn't finish before a timeout).[^javadoc-joiner] You can also write your own joiner. It has callbacks `onFork()` and `onComplete()`, either of which can return `true` to cancel the scope, plus `result()` and `timeout()` to produce the outcome. The HappyCoders guide walks through a "best supplier price" joiner that only fails if every supplier fails. Note that a joiner holds state, so you create a fresh one for each scope.[^happycoders]

#### Exceptions and the third type parameter

The JDK 27 round changed two things you'll notice in real code.[^infoq-533]<sup>,</sup>[^veen]

First, failures now arrive as a {{checked exception|an exception the compiler forces you to catch or declare in a throws clause}}: `java.util.concurrent.ExecutionException`, the same wrapper `Future.get()` has always used. Earlier previews threw a preview-only, unchecked `FailedException`. If you tried an older preview, that `catch` clause is the one thing to update.

Second, `StructuredTaskScope` and `Joiner` gained a third {{type parameter|a placeholder type in a generic declaration, like the T in List<T>}}. The Javadoc declares the API as `sealed interface StructuredTaskScope<T, R, R_X extends Throwable>`, where `T` is the subtasks' result type, `R` is what `join()` returns and `R_X` is the exception `join()` throws.[^javadoc-sts] That lets `join()` declare exactly what it throws instead of a vague `throws Exception`. Application code usually never spells the types out, because the compiler infers them. It also lets you pick your own exception, which is handy in a service layer:

```java
var joiner = Joiner.<Quote, PricingException>allSuccessfulOrThrow(
        cause -> new PricingException("pricing failed", cause));
try (var scope = StructuredTaskScope.open(joiner)) {
    // fork...; join() now throws PricingException
}
```

That `esf` (exception supplier function) overload exists for all three `…OrThrow` joiners.[^javadoc-joiner] Because it's a {{sealed interface|an interface that lists exactly which types may implement it (Java 17+)}}, you can't write your own `StructuredTaskScope` implementation, only your own `Joiner`.

#### Timeouts and configuration

There's a second `open()` overload that takes a function to adjust the scope's `Configuration`: `withTimeout(Duration)`, `withName(String)` for monitoring, and `withThreadFactory(...)` if you need something other than default virtual threads.[^happycoders] Since JDK 27 you can configure a scope without supplying a joiner:

```java
try (var scope = StructuredTaskScope.open(
        cf -> cf.withTimeout(Duration.ofSeconds(2))
                .withName("checkout"))) {
    // fork, join...
}
```

The timer starts when the scope opens. If it expires, the scope is cancelled and `join()` returns whatever the joiner's `timeout()` method produces. For the built-in `…OrThrow` joiners that's an exception whose cause is a `CancelledByTimeoutException`. For `allUntil()` it's the subtasks collected so far.[^javadoc-sts]<sup>,</sup>[^happycoders]

#### The guard rails

Structured concurrency is a set of rules, and the API enforces them.[^javadoc-sts]

- Only the owner can call `join()` or `close()`. Other threads get a `WrongThreadException`.
- `join()` is called once. Closing a scope that forked but never joined throws `IllegalStateException`.
- Scopes nest. A subtask can open its own scope, and they form a tree. If you close an outer scope before an inner one, the inner ones are closed first and a `StructureViolationException` is thrown.
- Subtasks automatically inherit {{scoped values|a Java 25 feature for sharing an immutable value, such as a request ID, with everything a thread calls, without passing it as a parameter}}. If you bind a request ID before opening the scope, every forked subtask (and their children) can read it.[^happycoders]

#### You can see the tree

Because the JVM knows which scope owns which threads, it can show you. Run `jcmd <pid> Thread.dump_to_file -format=json dump.json` (with {{jcmd|the JDK's command-line tool for sending diagnostic commands to a running JVM}}) and subtasks appear nested under their scope and owner, instead of as an anonymous list of pool threads.[^happycoders]<sup>,</sup>[^danvega] For anyone who has tried to work out which of 400 threads belongs to a stuck request, that's a big quality-of-life change.

### What it means for you

**If you're on JDK 21 or 25 today, nothing breaks.** Your `ExecutorService` code keeps working. Structured concurrency isn't replacing executors. It's a better tool for one specific, very common job: "this request needs several things done in parallel, and they all belong to it." Dan Vega's guidance is a useful boundary: it fits subtasks that belong to one operation and should end together, not scheduled jobs, long-lived background work or CPU-heavy number crunching.[^danvega]

**The timing question.** JDK 28 is a non-LTS release due in March 2027, and the next LTS, JDK 29, follows in September 2027.[^infoq-so-far] If JEP 543 lands in JDK 28 as proposed, then JDK 29 will be the first LTS where structured concurrency is a normal, final API. Writing about the JDK 27 preview, Ron Veen predicted one more preview round in JDK 28 and finalisation only in JDK 29.[^veen] The proposal moved faster than that.

**Where you'll actually meet it.** Frameworks are the big multiplier. Spring's Brian Clozel already pointed out in 2025 that structured concurrency lets you compose blocking `RestClient` calls asynchronously without any further changes to the client (see Story 2).[^clozel] Once the API is final, expect framework helpers and libraries to build on it, because they no longer have to ask users to turn on preview features.

**How to try it today.** Install JDK 27, compile with `javac --release 27 --enable-preview` and run with `java --enable-preview`. Preview features only work on the exact JDK version they belong to, so JDK 27 preview code won't run on JDK 26 or 28 builds with the flag.[^happycoders] If JEP 543 lands unchanged, the same source compiles on JDK 28 without the flag.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **It's a Candidate, not a done deal.** JEP 543 isn't targeted to JDK 28 yet, and the CSR for the implementation hasn't been approved. "No changes" is the proposal, not a guarantee.
- **Old tutorials are wrong.** Anything showing `new StructuredTaskScope.ShutdownOnFailure()`, `FailedException`, `Joiner.awaitAll()` or `onTimeout()` describes an earlier preview. `awaitAll()` was removed in JDK 27; HappyCoders suggests `Joiner.allUntil(_ -> false)` as the equivalent.[^happycoders]
- **`Subtask.get()` doesn't wait.** Unlike `Future.get()` it never blocks; it behaves more like `Future.resultNow()`, so read results only after `join()`.[^warski]
- **Cancellation is cooperative.** Code that ignores interrupts can keep a scope open.
- **Don't share a joiner** between scopes, and don't reuse one after its scope closes.[^happycoders]
</div>

### What happens next

The next milestones are the JEP being proposed to target JDK 28 (followed by a short review period), approval of the CSR, and the PR being merged into the JDK mainline. You'll see it in a JDK 28 early-access build after that. The reviewers on PR #32602 are still debating wording, for example whether the docs should say the exception comes from the "earliest" or from "any" failed subtask, which tells you how settled the design is: they're polishing sentences, not semantics.[^pr32602]

# Story 2 · RestTemplate is deprecated for removal. Now what?

<div class="byline">Spring Framework 7.1 · Spring Boot 4.2 · GA in November 2026 · ~15 min read</div>

<p class="opener" markdown="1">If you learned Spring in the Java 8 days, `RestTemplate` was probably one of the first classes you typed. `restTemplate.getForObject(url, User.class)`, a `@Bean` method in a config class, and you were calling other services. It has outlived several generations of "the modern way", and the Spring team has been nudging people away from it, in one form or another, for years. This autumn they stopped hinting. In the Spring Framework 7.1 milestones, `RestTemplate` carries `@Deprecated(forRemoval = true)`, and from November your compiler will tell you so on every build.</p>

### What happened

On 31 March 2026, Brian Clozel of the Spring team opened issue #36574 in the Spring Framework repository, "Deprecate RestTemplate and related types". Its goal was to formally deprecate `RestTemplate` and related classes for removal, to send a stronger signal to the community, with removal planned for Spring Framework 8.0, which isn't scheduled yet. The issue was assigned to the 7.1.0-M1 milestone and is now closed.[^sf-36574]

We checked the source at the `v7.1.0-M2` tag. The class now reads:

```java
/**
 * ...
 * @since 3.0
 * @deprecated as of 7.1, in favor of {@link RestClient}.
 * For removal in 8.0.
 */
@Deprecated(since = "7.1", forRemoval = true)
public class RestTemplate extends InterceptingHttpAccessor
        implements RestOperations {
```

The "related types" are a long list. In the same package, `RestOperations`, `RequestCallback`, `ResponseExtractor`, `HttpMessageConverterExtractor`, `ResponseErrorHandler`, `DefaultResponseErrorHandler`, `ExtractingResponseErrorHandler` and `NoOpResponseErrorHandler` are all deprecated for removal as of 7.1, as are `RestGatewaySupport` and `RestTemplateAdapter` in the `support` subpackage.[^sf-src]

Spring Boot followed. The Spring Boot 4.2.0-M1 release notes, published with the milestone on 20 August, say that "with Spring Framework 7.1 deprecating `RestTemplate` for removal, Spring Boot's supporting infrastructure has been deprecated as well, in favor of `RestClient`". That covers `RestTemplateAutoConfiguration`, `RestTemplateBuilder`, `RestTemplateCustomizer` and the test helpers, and `TestRestTemplate` is deprecated too.[^boot-m1-notes]<sup>,</sup>[^boot-m1-blog] In the Boot source at `v4.2.0-M2`, `RestTemplateBuilder` and `TestRestTemplate` are both marked "deprecated since 4.2.0 for removal in 4.4.0".[^boot-src] Boot's own tracking issue, #51118, simply says that with `RestTemplate` being marked for removal, "our usage of it should be adapted accordingly".[^boot-51118]

Where are we on the calendar? Spring Boot 4.2.0-M2 shipped on 25 September.[^spring-blog] The draft 4.2.0-RC1 release notes were last updated on the project wiki on 8 October, but when we checked the repository on 9 October there was no RC1 tag yet.[^boot-rc1] Spring Boot ships new minor versions in May and November, on "the Thursday after the 3rd Monday of the month".[^boot-support] By that rule, Boot 4.2 and Framework 7.1 should land on **19 November 2026**. That's our calculation; the Spring team hasn't published the exact date.

### The background you need

#### Three clients, three eras

An {{HTTP client|code that sends HTTP requests to another service and turns the response into Java objects}} is something nearly every backend needs. Spring has shipped three, and it helps to see them side by side.

**`RestTemplate`** arrived in Spring Framework 3.0, more than 15 years ago, as Brian Clozel noted in 2025.[^clozel] It's a {{template-method API|an API style where one class offers a ready-made method for each common case, like getForObject or postForEntity, with the plumbing hidden inside}}, the same pattern as `JdbcTemplate`. That worked nicely at first. But every new option meant another overload. Arjen Poutsma, introducing its successor in 2023, said that exposing every HTTP capability through one template class led to "too many overloaded methods".[^poutsma]

**`WebClient`** came with Spring Framework 5 and the {{reactive|a non-blocking programming style where you describe a pipeline of operations that run when data arrives, instead of waiting on a thread}} stack. It used a {{fluent API|an API where you chain method calls, like client.get().uri(...).retrieve(), so each step only offers the options that make sense next}} and handled streaming well. At that point, Clozel recalls, the team declared `RestTemplate` "feature complete".[^clozel] The Javadoc spelled it out: "As of 5.0 this class is in maintenance mode, with only minor requests for changes and bugs to be accepted going forward."[^javadoc-53] For a while, the Javadoc went further. A note quoted in a Spring Cloud Netflix issue read: "The RestTemplate will be deprecated in a future version and will not have major new features added going forward."[^scn-3736] That wording was later dropped, and for years developers argued about whether `RestTemplate` was "really" deprecated.[^velog]

The trouble was that `WebClient` belonged to the reactive stack, and lots of teams with ordinary blocking Spring MVC apps simply kept using `RestTemplate`.

**`RestClient`** closed that gap. It shipped in Spring Framework 6.1, which went GA on 16 November 2023 alongside virtual-thread support.[^sf61] Poutsma described it as a synchronous client with a fluent API like `WebClient`'s, built on `RestTemplate`'s existing "message converters, request factories, interceptors, and other underlying components".[^poutsma] That last part is why migration is feasible: underneath, both clients use the same machinery.

```viz:layers
title: "RestTemplate and RestClient share the same engine room"
layers:
  - {label: "RestTemplate (deprecated) / RestClient", sub: "the API your code calls", highlight: true}
  - {label: "Interceptors + initializers", sub: "auth headers, tracing, logging"}
  - {label: "HttpMessageConverters", sub: "JSON ⇄ objects (Jackson), etc."}
  - {label: "ClientHttpRequestFactory", sub: "JDK HttpClient, Apache, Jetty, Reactor"}
  - {label: "The network", sub: "TCP/TLS to the other service"}
note: "From the RestTemplate Javadoc at v7.1.0-M2: both clients 'share the same infrastructure', but 'RestClient is the focus for new higher-level features'."
```

The current `RestTemplate` Javadoc says exactly this: the two share request factories, interceptors, initializers and message converters, "so any improvements made therein are shared as well. However, `RestClient` is the focus for new higher-level features."[^sf-src]

#### The plan, announced a year in advance

The timeline wasn't a surprise. On 30 September 2025, Clozel published "The state of HTTP clients in Spring" and laid out three steps: announce the intent with Spring Framework 7.0 in November 2025; formally mark `RestTemplate` `@Deprecated` for removal in 7.1 (provisionally November 2026); and remove it in 8.0, date to be decided. His reasons were that the template-style API can't close the feature gap with `RestClient`, can't easily take on features such as {{API versioning|sending a version number with each request (in a header, path or media type) so a server can evolve its API safely}}, and handles streaming and async composition poorly. He added that, at the current release pace, open-source support for `RestTemplate` would last until at least 2029.[^clozel] InfoQ's Spring 7 coverage in November 2025 reported the same plan.[^infoq-spring7]

```viz:timeline
  - {date: "Sep 2025", label: "Deprecation timeline announced"}

```

### How it works

#### What "deprecated for removal" does to your build

There are two kinds of deprecation in Java. A plain `@Deprecated` produces a warning only if you compile with `-Xlint:deprecation`; most builds never show it. `@Deprecated(forRemoval = true)` is louder: the compiler emits a {{removal warning|a compiler warning, on by default, that you're using an API its authors plan to delete}} on every use, with no extra flags. We checked this on JDK 21 with a dummy class carrying exactly Spring's annotation:

```text
Use.java:1: warning: [removal] Old in lib has been
  deprecated and marked for removal
```

Add `-Werror`, which many teams use to keep builds clean, and the same code fails with "warnings found and -Werror specified". So the practical effect of upgrading to Boot 4.2 is that a codebase full of `RestTemplate` either gets noisy or stops compiling until you add `@SuppressWarnings("removal")` or migrate. Nothing changes at runtime: `RestTemplate` works exactly as before.

#### The Boot side of the change

Spring Boot's {{auto-configuration|Boot's mechanism that creates sensible beans for you based on what's on the classpath}} gives you ready-made {{beans|objects that Spring creates and manages, and injects wherever you ask for them}} for both clients: a `RestTemplateBuilder` and a `RestClient.Builder`. The M1 notes give the direct mappings:[^boot-m1-notes]

- Building from the auto-configured `RestTemplateBuilder` → inject `RestClient.Builder` instead.
- A `RestTemplateCustomizer` bean → the equivalent `RestClientCustomizer`.
- `@RestClientTest` with `MockRestServiceServer` → configure a `RestClient.Builder` rather than a `RestTemplateBuilder`.
- `TestRestTemplate` in integration tests → `RestTestClient`, injected with `@AutoConfigureRestTestClient`. It can call a live server or use a mock transport depending on the test, and has built-in assertions.

The reference documentation section on calling REST services no longer covers `RestTemplate` at all.[^boot-m1-notes] Here's what the replacement integration test looks like in Boot's own documentation sources at `v4.2.0-M2`:[^boot-src]

```java
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
class MyRandomPortRestTestClientTests {
  @Test
  void exampleTest(@Autowired RestTestClient restClient) {
    restClient.get().uri("/")
        .exchange()
        .expectStatus().isOk()
        .expectBody(String.class).isEqualTo("Hello World");
  }
}
```

#### Translating the calls

For application code, the Spring Framework reference has an equivalence table. Each `RestTemplate` method becomes a short fluent chain.[^sf-docs]

```viz:codecompare
title: "The same two calls, before and after"
left:
  title: "RestTemplate (deprecated in 7.1)"
  code: |
    Pet pet = restTemplate.getForObject(
        url, Pet.class);

    ResponseEntity<Pet> res =
        restTemplate.postForEntity(
            url, newPet, Pet.class);
right:
  title: "RestClient (Spring 6.1+)"
  code: |
    Pet pet = restClient.get().uri(url)
        .retrieve().body(Pet.class);

    ResponseEntity<Pet> res =
        restClient.post().uri(url)
            .body(newPet).retrieve()
            .toEntity(Pet.class);
note: "Mappings from the Spring Framework reference documentation's RestTemplate-to-RestClient table."
```

A few more rows from that table: `exchange(URI, HttpMethod, HttpEntity, Class)` becomes `method(...).uri(...).headers(...).body(...).retrieve().toEntity(...)`; `delete(URI)` becomes `delete().uri(URI).retrieve().toBodilessEntity()`; and the low-level `execute(...)` with callbacks becomes `method(...).uri(...).exchange(...)`.[^sf-docs]

One important detail: calling `retrieve()` on its own does nothing. The docs say it "is a no-op and returns a `ResponseSpec`", and you have to call a terminal method such as `body()` or `toEntity()` for the request to happen.[^sf-docs]

#### Error handling moves too

With `RestTemplate`, you customised errors by setting a {{ResponseErrorHandler|RestTemplate's hook for deciding which responses count as errors and what to throw}}. That interface, and its default implementation, are deprecated in 7.1 as well, in favour of `RestClient.ResponseSpec.ErrorHandler`.[^sf-src] Even the `RestClient.Builder.defaultStatusHandler(ResponseErrorHandler)` overload, which exists to ease migration, is now deprecated for removal. The replacement takes a status predicate plus a handler.[^sf-src] Per request, you use `onStatus`:

```java
String body = restClient.get().uri(url)
    .retrieve()
    .onStatus(HttpStatusCode::is4xxClientError, (req, res) -> {
        throw new MyCustomRuntimeException(
            res.getStatusCode(), res.getHeaders());
    })
    .body(String.class);
```

By default, 4xx and 5xx responses throw a `RestClientException` subclass, as they did with `RestTemplate`. Status handlers aren't applied when you use `exchange()`, where you handle the raw response yourself.[^sf-docs] A developer migrating a project that started on Spring Boot 1.5.4 asked whether `HttpStatusCodeException` and `ResourceAccessException` still behave the same. Clozel checked and found no significant differences, because the two clients share the infrastructure that throws them.[^sf-35620]

#### The migration path the Spring team recommends

You don't have to rewrite every call at once. The reference docs describe a two-step path, and the key is a factory method that wraps an existing, fully configured `RestTemplate`.[^sf-docs]<sup>,</sup>[^clozel]

```viz:flow
title: "Migrating without a big-bang rewrite"
headers: [Today, Step 1, Step 2]
columns:
  - - label: "RestTemplate bean"
      sub: "interceptors, factory, converters"
  - - label: "RestClient.create"
      sub: "(restTemplate): same config"
      style: accent
    - label: "Move call sites"
      sub: "one class at a time"
      style: soft
  - - label: "RestClient.Builder"
      sub: "config moves here"
    - label: "Delete RestTemplate"
      sub: "warnings gone"
```

`RestClient.create(restTemplate)` copies the template's request factory, message converters, interceptors, initializers, URI template handler and error handler into a new `RestClient`.[^sf-src] You can switch call sites gradually, and once nothing calls the template directly, you move the configuration onto a `RestClient.Builder`.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **The default transport is different.** With no other HTTP library on the classpath, `RestClient` uses `JdkClientHttpRequestFactory` (the JDK's `HttpClient`), while `RestTemplate` uses `SimpleClientHttpRequestFactory` (`HttpURLConnection`). The docs warn that this can cause subtle differences in behaviour at the HTTP level.[^sf-docs] If you wrap with `RestClient.create(restTemplate)`, you keep the old factory.
- **Null bodies and headers.** One migrator found `body()` and `headers()` on the new builder don't accept `null`, and that `additionalInterceptors()` became `requestInterceptor()`/`requestInterceptors()`.[^sf-35620]
- **AMQP starter split.** Unrelated to HTTP, but in the same upgrade: Boot 4.2 adds AMQP 1.0 support, so `spring-boot-starter-amqp` users must move to `spring-boot-starter-rabbitmq` (to stay on AMQP 0.9) or `spring-boot-starter-amqp-rabbitmq` (for AMQP 1.0).[^boot-m1-notes]
- **Proxy headers.** Framework 7.1's `ForwardedHeaderFilter` now needs to know whether to use the standard `Forwarded` header or `X-Forwarded-*`. Boot defaults to `X-Forwarded-*` when `server.forward-headers-strategy=FRAMEWORK`.[^boot-m1-notes]
- **Tomcat redirects.** `server.tomcat.servlet.use-relative-redirects` now defaults to `true`, and three servlet-specific Tomcat properties moved under `server.tomcat.servlet`.[^boot-m2-notes]
</div>

#### Going declarative instead

For service-to-service calls, there's an option that skips most of this code: {{HTTP interface clients|Java interfaces annotated with @HttpExchange for which Spring generates the implementation at runtime, similar to Feign}}. You describe the remote API as an interface and Spring generates a {{proxy|an object generated at runtime that implements an interface by forwarding each call somewhere else}} backed by a `RestClient`:[^sf-docs]

```java
@HttpExchange(url = "/repos/{owner}/{repo}",
              accept = "application/vnd.github.v3+json")
public interface RepositoryService {
    @GetExchange
    Repository getRepository(@PathVariable String owner,
                             @PathVariable String repo);
}
```

Spring Framework 7.0 added HTTP interface groups via `@ImportHttpServices`, which declares and configures many such clients at once so they can share one `RestClient`.[^clozel]<sup>,</sup>[^infoq-spring7]

### What it means for you

**On Boot 3.x, 4.0 or 4.1, nothing is urgent.** The `@Deprecated` annotation only arrives with Framework 7.1, the class keeps working, and Clozel's estimate is open-source support until at least 2029.[^clozel] The pressure starts when you move to Boot 4.2 in November, because that's when the removal warnings appear.

**Write new code with `RestClient`.** It's been available since Spring Framework 6.1, so most teams can start today, before upgrading. The Spring team calls it the best long-term solution, and recommends `WebClient` only when you need reactive APIs or streaming.[^clozel]

**Look at your tests first.** `TestRestTemplate` is often the most widespread use in a codebase, and it's slated for removal from Boot in 4.4, earlier than Framework 8.0 drops `RestTemplate` itself.[^boot-src] By Boot's six-month cadence, 4.4 would be roughly November 2027, though that's our extrapolation and nothing has been announced.[^boot-support]

**Check your libraries.** Your own code is only part of it. Shared internal libraries, OAuth helpers and older Spring Cloud integrations often build their own `RestTemplate`. The Spring Cloud Netflix project, for example, had an issue asking to deprecate its `RestTemplate`-based Eureka client support in favour of `WebClient`.[^scn-3736] Those dependencies need to move before Spring Framework 8.0, or they'll break when you upgrade.

<div class="box realworld" markdown="1">
**🌍 In the real world**

Automated migration is becoming a product category. Moderne publishes a recipe, `io.moderne.java.spring.boot3.MigrateRestTemplateToRestClient`, that rewrites `new RestTemplate()` to `RestClient.create()`, changes declared types, converts `getForObject`, `postForEntity`, `exchange` and the other common calls, and folds setters like `setErrorHandler` into the `RestClient.Builder` "where safe". It's proprietary (it needs a Moderne subscription and runs from the Moderne CLI), so check the licence before you plan around it.[^moderne] Spring Boot itself is the biggest real-world migration: issue #51118 tracks removing its own internal use of `RestTemplate`.[^boot-51118]
</div>

### What happens next

The next step is Spring Boot 4.2.0-RC1, whose draft notes already list a new default buildpacks builder (`paketobuildpacks/ubuntu-resolute-builder`, so container images move from Ubuntu 24.04 to 26.04) and a properties-migrator option to fail the application on warnings.[^boot-rc1] GA follows in November along with Framework 7.1. After that, the open question is when Spring Framework 8.0 arrives. Until a date is set, `RestTemplate` sits in a well-signposted waiting room: still supported, still patched, and no longer something you should be writing new code against.

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **HTTP client**: code that sends HTTP requests and turns responses into Java objects.
- **Template-method API**: one class with a ready-made method per common case (`getForObject`, `postForEntity`).
- **Reactive**: a non-blocking style where you describe a pipeline that runs as data arrives.
- **Fluent API**: chained calls where each step offers only the options that make sense next.
- **API versioning**: sending a version with each request so a server can evolve its API safely.
- **Removal warning**: a compiler warning, on by default, for APIs marked `forRemoval = true`.
- **Auto-configuration**: Boot's mechanism for creating sensible beans based on the classpath.
- **Bean**: an object Spring creates, manages and injects for you.
- **ResponseErrorHandler**: `RestTemplate`'s hook for deciding what counts as an error and what to throw.
- **HTTP interface client**: an `@HttpExchange` interface whose implementation Spring generates.
- **Proxy**: a runtime-generated object that implements an interface by forwarding calls.
