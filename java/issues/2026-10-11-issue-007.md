# Story 1 · Oracle cuts the price of Java for small and mid-sized companies

<div class="byline">Licensing · Oracle Java SE Universal Subscription · Announced 8 Oct 2026 · ~13 min read</div>

<p class="opener" markdown="1">Imagine a 100-person company running a few Spring Boot services on Oracle JDK 21. Until this week, the published price for staying on Oracle's supported builds was about $18,000 a year. As of 8 October it's $1,000. Oracle hasn't changed what you get. It has changed how small companies are charged, at the very moment many of them have to decide whether to pay for Java at all. To see why the timing matters, and why the new price list has some odd edges, you need a short history of how Oracle charges for Java.</p>

### What happened

On 8 October 2026, Donald Smith, Oracle's Vice President of Product Management for Java, announced "simplified pricing and purchasing of the Java SE Universal Subscription" for organisations with fewer than 3,000 employees.[^smb] The stated aim is to "make the benefits of the Java SE Universal Subscription more accessible to small and medium businesses."[^smb] The new annual prices, in US dollars, are:[^smb]

| Organisation size | New annual price |
|---|---|
| 10 employees or fewer | $100 |
| 100 employees or fewer | $1,000 |
| 500 employees or fewer | $10,000 |
| 501 to 2,999 employees | $10,000, plus $147.20 for each employee above 500 |
| 3,000 employees or more | Unchanged (enterprise price list) |

Organisations with 500 or fewer employees can now buy the subscription themselves through the Oracle Store, without talking to a salesperson. Larger organisations are asked to contact Oracle Sales.[^smb] Oracle's subscription FAQ has already been updated with the same tiers, describing the 501–2,999 band as "$10,000 per year, plus $147.20 annually for each employee above 500", and the enterprise price as starting at $10.50 per employee per month.[^subfaq]

The post doesn't say what the old prices were. That's where the size of the cut becomes clear.

### The background you need

#### Oracle JDK is one Java among many

When people say "Java" they usually mean a {{JDK|Java Development Kit: the compiler, the JVM that runs your code, and the standard library, packaged as one download}}. Almost every JDK you can download is built from the same source code, {{OpenJDK|the open-source project, led by Oracle, where the Java platform is developed; its code is licensed under GPLv2 with the Classpath Exception}}. Different vendors then build, test and ship it as their own {{distribution|a vendor's packaged build of OpenJDK, with its own licence, update schedule and support offer}}: Eclipse Temurin, Amazon Corretto, Azul Zulu, Red Hat's builds, Microsoft's build, and Oracle's own.

Oracle actually ships two. Its OpenJDK builds on jdk.java.net use the open-source licence.[^jdkfaq] **Oracle JDK**, its commercial build, comes under Oracle's own licence terms, and those terms are what this story is about. If your servers run Temurin or Corretto, today's price change doesn't apply to you, though the rest of this story explains why many teams ended up on those distributions in the first place.

#### A decade of licence changes

For most of Java's history, Oracle's JDK was free for everyone under the {{BCL|Binary Code License: the licence Oracle JDK used until 2019, which allowed free commercial use}}. That changed in January 2019, when Oracle stopped publishing free public updates of Java SE 8 for commercial users and introduced a paid subscription instead.[^timeline] Later updates of Java 8, 11 and 17 came under the {{OTN licence|Oracle Technology Network License for Java SE: free for personal use, development, testing, prototyping and demos, but commercial production use needs a paid subscription}}.[^jdk21end]<sup>,</sup>[^jdkfaq]

Then, in September 2021, Oracle went the other way. It introduced the {{NFTC|Oracle No-Fee Terms and Conditions: a licence that allows free use of Oracle JDK, including commercial and production use, for a limited period}}, which "permits free use for all users – even commercial and production use."[^jdkfaq] The catch is the time limit. Each {{LTS|Long-Term Support release: a Java version that vendors keep patching for years; currently Java 8, 11, 17, 21 and 25}} release stays under the NFTC only until one year after the next LTS ships.[^jdkfaq] After that, updates move back to the OTN licence.

Updates matter because Oracle fixes security vulnerabilities through a scheduled {{Critical Patch Update|Oracle's quarterly security release (January, April, July, October) that bundles fixes across its products, including the JDK}} (CPU). A JDK that stops getting CPUs slowly collects known, unpatched vulnerabilities.

For JDK 21, the clock is about to run out. Oracle's August blog post says "all updates through and including September 2026 are available under the NFTC", and that from the October 2026 CPU, JDK 21 updates will be offered under the OTN licence.[^jdk21end] That CPU is due on 20 October. Oracle's suggested options are to migrate to JDK 25, which stays under the NFTC until October 2028, or to buy a subscription, which covers Java 21 until at least September 2031.[^jdk21end]

#### Why the old price hurt small companies

In January 2023, Oracle replaced its older subscriptions with the **Java SE Universal Subscription**.[^subfaq] The big change was the unit of pricing. The old subscriptions were priced per processor (servers) or per named user (desktops).[^upperedge] The new one uses an {{employee metric|pricing based on your organisation's total headcount, not on how many people or machines use Java}}. It counts everyone, not just developers: full-time and part-time workers, temporary employees, and the "contractors, outsourcers, agents, and consultants that support your internal business operations."[^upperedge]

The published price ladder started at $15 per employee per month for organisations with up to 999 employees, then fell with size: $12 up to 2,999, $10.50 up to 9,999, and so on down to $5.25 at 40,000–49,999.[^redress] So a 100-person company running one small Java service owed the same per-head price as one running hundreds: 100 × $15 × 12 = $18,000 a year.

That's why many teams treated the NFTC deadline as a migration deadline. Azul, which sells a competing JDK and support, warned in July that customers moving to the Universal Subscription could see licensing costs rise "by 2-5x", and described a "six- or seven-figure annual subscription" for enterprises that had never paid for Java before.[^azul] Azul is a competitor, so treat that as a vendor's view, but it shows how the 2023 model was seen.

### How it works

#### Bands instead of a per-head rate

Below 500 employees, the new model no longer multiplies headcount by a rate. It puts you in one of three **bands** and charges a flat price for the band. Between 501 and 2,999, it goes back to a per-employee charge on top of a $10,000 base. Here's what that does to the list price at a few sizes. The "old" column is our calculation from the published 2023 ladder;[^redress] the "new" column applies Oracle's 8 October tiers.[^smb]

| Employees | Old list price per year | New price per year | Change |
|---|---|---|---|
| 10 | $1,800 | $100 | −94% |
| 100 | $18,000 | $1,000 | −94% |
| 500 | $90,000 | $10,000 | −89% |
| 1,000 | $144,000 | $83,600 | −42% |
| 2,000 | $288,000 | $230,800 | −20% |
| 2,999 | $431,856 | $377,853 | −13% |
| 3,000 | $378,000 | $378,000 | unchanged |

The smaller you are, the bigger the cut.

#### The odd number has a reason

Why $147.20 per extra employee, and not a round number? Do the sum at the top of the band. At 3,000 employees the enterprise rate applies: 3,000 × $10.50 × 12 = $378,000. Subtract the $10,000 base and divide by the 2,500 employees between 500 and 3,000, and you get exactly $147.20. In other words, the middle band is a straight line that runs from $10,000 at 500 employees to precisely the enterprise price at 3,000. Oracle doesn't explain the number, but the arithmetic shows it was chosen so there's no jump at the 3,000 boundary.

That fixes a strange feature of the old ladder. Because the rate fell from $12 to $10.50 at 3,000 employees, a company with 2,999 people paid about $54,000 a year *more* than one with 3,000. The same happened at 1,000: 999 employees cost $179,820, while 1,000 cost $144,000.

#### The new edges

Flat bands create their own edges. Ten employees pay $100, but eleven pay $1,000. A hundred pay $1,000, but 101 pay $10,000. Per employee per month, that's about 83 cents at exactly 10 or 100 people, and about $8.25 at 101. Even at those worst points it's still cheaper than the old $15, but if your headcount sits just above a boundary, it's worth knowing that contractors count too, and that the count is your organisation's, not your Java team's.

#### What the subscription includes

The price changed, but the product didn't. Oracle says the subscription gives "a commercial license for all versions of Oracle Java", access to Oracle's support and its performance, stability and security updates, and tools for managing and securing Java deployments.[^smb] The FAQ adds desktop, server and cloud use, My Oracle Support, and commercial support for components in the **Java Verified Portfolio**, Oracle's set of supported Java libraries and tools.[^subfaq] One example is Jipher, Oracle's FIPS-validated cryptography provider for regulated environments, whose new version 20 is included in that portfolio.[^jipher] Oracle Java workloads running on Oracle Cloud Infrastructure get the subscription features at no extra cost.[^smb]

### What it means for you

First, find out whether you're affected at all. The question isn't "do we use Java?" but "do we run **Oracle JDK** in production?" You can see which build a machine uses from its properties:

```text
$ java -XshowSettings:properties -version 2>&1 | grep -E 'runtime.name|java.vendor ='
    java.runtime.name = OpenJDK Runtime Environment
    java.vendor = Ubuntu
```

That's our sandbox, which runs Ubuntu's OpenJDK 21 build, so Oracle's commercial terms don't apply. Note that Oracle's open-source builds from jdk.java.net also name Oracle as the vendor, so where the JDK came from matters as much as the vendor string. Check container base images too, not only servers.

If you do run Oracle JDK 21 in production, you have four realistic paths before or soon after 20 October:

1. **Move to Oracle JDK 25.** It's the current LTS and stays free under the NFTC until October 2028.[^jdk21end] You'd face the same decision again then, after Java 29 ships in September 2027.[^jdkfaq]
2. **Switch to another OpenJDK distribution.** Eclipse Temurin promises JDK 21 builds until "at least Dec 2029",[^temurin] and Amazon Corretto 21 until October 2030, with Amazon stating it "does not charge for its use or distribution."[^corretto] These are built from the same OpenJDK code, so for most server applications the switch is a base-image change plus a test run.
3. **Buy the subscription.** This is the option the announcement changes. For a company of 100, the choice is now between $1,000 a year and the engineering time to test a JDK swap across every service, base image and build pipeline. For many small teams, that time costs more than $1,000. The subscription also brings Oracle support, which free distributions don't include unless you buy it from their vendor.
4. **Stay on 21.0.12.1, the last NFTC build Oracle has published, and stop patching.** This is the option to avoid. Every quarter without updates means more publicly known, unpatched vulnerabilities.

There's also a less obvious group: companies that never noticed they were using Oracle JDK in production. Licensing consultancies say Oracle stepped up Java compliance checks after the 2023 change and that the employee metric made under-licensing expensive. One describes Oracle reps' "routine account review" calls as "discovery exercises."[^redressaudit] Those are claims by firms that sell audit defence, not Oracle statements, but the practical point holds: a $100 or $1,000 subscription is a cheap way for a small company to make that risk go away.

For mid-sized companies, between 1,000 and 3,000 employees, the cut is real but smaller: 20–42% off list at the sizes in our table. The free distributions remain a much bigger saving, so the decision there still depends on whether you value Oracle's support enough to pay for it.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Headcount means the whole organisation.** The employee metric counts part-timers, temporary staff and contractors who support your business, not only people who use Java.[^upperedge]
- **Band edges.** Eleven employees cost ten times as much as ten; 101 cost ten times as much as 100.[^smb]
- **These are list prices.** Oracle's post doesn't mention contract length, minimum terms or discounts, and online purchase is only for organisations of 500 or fewer.[^smb]
- **Development use is still free under OTN, but read it carefully.** Oracle's FAQ says the OTN licence covers "personal use, development, testing, prototyping, demonstrating", but also that using Java on a work laptop "as part of any business operations" is not personal use.[^jdkfaq]
- **Nothing changes at 3,000+.** Large enterprises keep the existing per-employee ladder.[^smb]
</div>

### What happens next

The October CPU on 20 October brings the first JDK 21 update under the OTN licence.[^jdk21end] JDK 25 stays under the NFTC until October 2028, a year after Java 29 LTS.[^jdk21end] Oracle hasn't said whether this pricing is permanent or how it will treat existing contracts at renewal. If you have a renewal coming up and fewer than 3,000 employees, it's worth asking.

# Story 2 · IntelliJ's Java engine moves into VS Code and Cursor

<div class="byline">Tooling · JetBrains, Oracle, Red Hat · RC released 7 Oct 2026 · ~13 min read</div>

<p class="opener" markdown="1">For as long as most Java developers can remember, if you wanted IntelliJ IDEA's Java refactorings and inspections, you had to use IntelliJ IDEA. That's changing. On 7 October, JetBrains released the final test build of an extension that runs IntelliJ's Java and Kotlin engine inside VS Code and Cursor. In the same fortnight, Oracle and Red Hat shipped new versions of their own Java extensions for VS Code. The editor you type in and the engine that understands your code are separating, and AI coding agents are one of the reasons JetBrains says this matters.</p>

### What happened

JetBrains' extension is called **Java and Kotlin by IntelliJ IDEA**. It reached release candidate on 7 October 2026.[^jbrc] The announcement, by Andrei Kogun, says the RC "is part of the Early Access Program and can be used for 30 days without a license", that the stable release "will arrive very soon", and that afterwards "new users will receive a 30-day free trial", after which the extension requires an IntelliJ IDEA Ultimate subscription.[^jbrc] JetBrains hasn't given a GA date.

The extension was first released as a preview two months earlier. In that announcement, Marco Behler wrote that "IntelliJ IDEA's Java and Kotlin intelligence is available in a preview extension for third-party editors", naming "VS Code and its forks (such as Cursor)".[^jbpreview] Since then, JetBrains says, it has been downloaded more than 20,000 times from the Visual Studio Marketplace and the Open VSX Registry, and the team has tested it on the very large repository used to build IntelliJ-based IDEs themselves.[^jbrc] The RC offers completion, navigation, inspections and quick-fixes, project-wide refactorings, debugging, Maven, Gradle and Bazel projects, built-in test running, and "Spring tooling interoperability."[^jbrc]

The other two Java extensions for VS Code also had releases:

- **Red Hat's Language Support for Java**, version 1.57.0, came out on 1 October. It adds Java 27 support, faster startup, and a bundled JDK upgraded to 25.[^rh157] It now needs Java 25 or later to run its language server.[^rhreadme]
- **Oracle's Java Platform Extension**, version 27.0.0, was merged on 6 October and announced on Inside Java on 8 October.[^oraclerel]<sup>,</sup>[^insidejava] It moves to NetBeans 31 for "improved support and tooling for JDK 27", adds breakpoints inside individual lambdas, and now needs JDK 21 or newer to run, while still working with projects on JDK 8 and above.[^oraclechg]

### The background you need

#### What your IDE actually knows about your code

When you press "Go to definition" in a Spring project, your editor has to answer a hard question: which of the thousands of classes on the {{classpath|the list of directories and JAR files where Java looks for classes when compiling and running}} does this name refer to? To answer it, an IDE does most of what a compiler does. It reads your `pom.xml` or `build.gradle` to work out the dependencies, parses every file into an {{abstract syntax tree|a tree-shaped representation of source code, in which each node is a construct such as a class, method call or variable}}, resolves every name to a type, and keeps all of that up to date as you type. Completion, error highlighting, "find usages", refactoring and inspections are all built on top of that model.

Building that model well is years of work, and for a long time each IDE had its own. Eclipse has the **Eclipse JDT** (Java Development Tools). Oracle's NetBeans-based tooling builds on `javac`, the JDK's own compiler. IntelliJ IDEA has JetBrains' own engine, which is the thing many Java developers pay for.

#### The Language Server Protocol

The problem with every editor having its own engine is multiplication. If there are *m* editors and *n* languages, someone has to write *m × n* integrations. Microsoft's answer was the {{Language Server Protocol|LSP: a standard way for an editor to ask a separate program questions about code, such as "where is this defined?" or "what are the errors in this file?"}}. As the community site langserver.org puts it, LSP "creates the opportunity to reduce the *m-times-n* complexity problem": each language builds one server, each editor builds one client.[^langserver] The protocol's public GitHub repository was created by Microsoft in 2015.[^lsprepo]

A {{language server|a background program that holds the model of your code and answers the editor's LSP requests}} "runs as a separate process and development tools communicate with the server using the language protocol over JSON-RPC," according to the official overview.[^lspoverview] {{JSON-RPC|a simple convention for calling functions on another process by sending JSON messages that name a method and its parameters}} keeps the messages simple. When you open a file, the editor sends `textDocument/didOpen`. As you type, it sends `textDocument/didChange`, and the server replies with `textDocument/publishDiagnostics` (your red squiggles). "Go to definition" is a `textDocument/definition` request.[^lspoverview] This is the request from the LSP overview, with the file path shortened:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "textDocument/definition",
  "params": {
    "textDocument": { "uri": "file:///.../use.cpp" },
    "position": { "line": 3, "character": 12 }
  }
}
```

The server answers with another file URI and a line-and-character range. The point is what the protocol *doesn't* contain: no syntax trees, no types, no compiler symbols. The overview explains that standardising "a text document URI or a cursor position" is much simpler than standardising "an abstract syntax tree and compiler symbols across different programming languages."[^lspoverview] All the language knowledge stays inside the server. That's what makes it possible to move a whole IDE engine behind the protocol.

Debugging has a similar standard, the {{Debug Adapter Protocol|DAP: a standard protocol editors use to talk to debuggers, the debugging counterpart of LSP}}, which JetBrains' extension uses for its debugger.[^jbpreview]

#### How Java got three language servers

Red Hat was first. The {{Eclipse JDT Language Server|JDT LS: an open-source Java language server built from the Eclipse IDE's Java tooling, used by Red Hat's VS Code extension}} was committed to the Eclipse Foundation in February 2017.[^jdtls] Its README says it's built from Eclipse JDT for Java support, M2Eclipse for Maven and Buildship for Gradle.[^jdtls] Red Hat's VS Code extension runs it.

Oracle followed in October 2023 with its Java Platform Extension, which builds, runs and debugs Java in VS Code.[^infoq2023] Its selling point is the compiler underneath: Oracle says it "is based on the OpenJDK javac compiler for code editing and compilation."[^oracle2m] Because the editor uses the same compiler as the JDK, it can understand new language features as soon as `javac` does. By January 2025 it had passed 2 million downloads.[^oracle2m] The extension's source shows it's built from the Apache NetBeans language server.[^oraclerepo]

JetBrains held out longest. Its IDE business depends on people choosing IntelliJ, and DevClass noted in 2025 that the company considered its own language API better than LSP and faced a dilemma: an LSP server might reduce demand for its IDEs, while not having one could hurt Kotlin in a world where VS Code is popular.[^devclass] Back in 2011, JetBrains had said it expected Kotlin "to drive the sales of IntelliJ IDEA."[^devclass] Its first step was a pre-alpha Kotlin language server in May 2025, meant for "toy projects."[^devclass] This month's RC covers Java as well, and it's built for real projects.

### How it works

All three extensions follow the same pattern. A thin piece of code inside VS Code (the client) starts a language server process on your machine, using a JDK you provide or one it bundles. The server imports your build, which is why each extension needs to understand Maven and Gradle, builds its model of the code, and answers the editor's requests. What differs is the engine inside the server.

#### Why AI agents care

The new part of this story is who else is asking questions. An AI coding agent working in your repository needs the same answers an IDE does: where is this method called, what type is this variable, will this rename break anything? Without a language server, an agent mostly searches text. That's how you get a rename that misses an overload, or "usages" that are really a method with the same name in another class.

JetBrains says that when its extension is installed in Cursor, "Cursor Agent can use the same language server for semantic code search, navigation, and code analysis, leading to faster and more deterministic results."[^jbrc] The August post went further, saying internal trials suggest the same LSP functionality can significantly improve terminal-based agents such as Claude Code or Codex, with results to be published "soon."[^jbpreview] Those numbers haven't been published yet, so treat this as a direction rather than a measured result. But it explains the timing: a language server that answers precise questions about code is useful to people and to agents alike.

### What it means for you

**If you already write Java in VS Code or Cursor**, you now have three serious engines to choose from. Red Hat's is free, open source and updated roughly monthly.[^rh157] Oracle's is free, tracks `javac` closely, and is a good fit if you want new language features early. JetBrains' brings IntelliJ's inspections and refactorings, but costs an Ultimate subscription once it's stable. You can try the RC now for 30 days: it's listed as `JetBrains.intellij-server` on the Visual Studio Marketplace and `JetBrains/intellij-server` on Open VSX.[^jbrc] Disable the other Java extensions first.

**If your company already pays for IntelliJ IDEA Ultimate**, this is mostly good news. JetBrains says the same licence covers IntelliJ's Java and Kotlin features in the desktop IDE, VS Code-based editors and other supported environments.[^jbpreview] A developer who prefers Cursor for AI work no longer has to give up IntelliJ's analysis to use it, and a team that mixes editors can get the same inspections across all of them.

**If you check upgrade prerequisites**, note the JDK requirements. Oracle's extension needs JDK 21 or newer to run its server and Red Hat's needs Java 25, although Red Hat bundles a runtime in its platform-specific builds.[^oraclechg]<sup>,</sup>[^rhreadme] Your *project* can still target Java 8: the server's JDK and your project's JDK are separate settings in both extensions.

**If you're evaluating AI coding tools**, ask whether the agent uses a real language server or text search. With Java, the difference shows up in refactorings across a large codebase.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **It's still a release candidate.** The RC works for 30 days without a licence, and there's no GA date beyond "very soon."[^jbrc]
- **It's not free after the trial.** Unlike Red Hat's and Oracle's extensions, and unlike JetBrains' Apache 2.0 Kotlin-only language server, it needs IntelliJ IDEA Ultimate.[^jbpreview]
- **One Java server at a time.** JetBrains recommends disabling the Red Hat and Oracle extensions to avoid overlapping analysis.[^jbpreview]
- **Agent gains aren't measured yet.** JetBrains' terminal-agent results haven't been published.[^jbpreview]
- **Resource use isn't documented.** JetBrains' documentation doesn't say how much memory the background server needs, or which JDK it runs on.[^jbhelp]
</div>

### What happens next

JetBrains says the stable release is close, and that future posts will cover "fully agentic, terminal-based workflows."[^jbrc] Red Hat's extension has been shipping roughly monthly, and Oracle's version numbers track JDK releases, so both will need updates when JDK 28 arrives in March 2027. The bigger question is commercial: will a good-enough free language server keep developers in VS Code, or will IntelliJ's engine in VS Code pull more of them into paying for Ultimate? We'll know more once JetBrains publishes its agent results and its stable release.

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **Classpath**: the directories and JAR files where Java looks for classes when compiling and running.
- **Abstract syntax tree**: a tree representation of source code, with a node for each construct.
- **Language Server Protocol (LSP)**: a standard way for an editor to ask a separate program questions about code.
- **Language server**: a background program that holds the model of your code and answers LSP requests.
- **JSON-RPC**: calling functions on another process by sending JSON messages that name a method and its parameters.
- **Debug Adapter Protocol (DAP)**: a standard protocol editors use to talk to debuggers.
- **Eclipse JDT Language Server (JDT LS)**: the open-source Java language server built from Eclipse's Java tooling, used by Red Hat's extension.
</div>
