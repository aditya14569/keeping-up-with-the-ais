# Story 1 · JEP 540: the JDK gets a JSON API, twelve years late

<div class="byline">JDK 28 · OpenJDK · core-libs · Targeted to JDK 28 (2 Oct 2026) · ~13 min read</div>

<p class="opener" markdown="1">Try this the next time you start a small Java project. You want to call a REST endpoint and read one number from the response. Python does it with a module that ships with the language. Go does it with a package in its standard library. In Java, your first step is to open the build file and add a dependency, because the platform that runs a huge share of the world's back ends has never been able to read JSON on its own. JEP 540 changes that. It's a deliberately small API, and the story of why it's small is as interesting as the API itself.</p>

### What happened

On 2 October, Oracle's Inside.java site announced that **JEP 540, "Simple JSON API (Incubator)", is targeted to JDK 28**.[^inside-home] The JEP had been Proposed to Target since mid-August, when InfoQ described it as an API that "will ship in the incubating `jdk.incubator.json` module, where it can change incompatibly or be removed based on developer feedback."[^infoq-json] InfoQ's JDK 28 overview sums up its purpose as "a simple, standard API for parsing and generating JSON documents without the need for an external library."[^infoq-jdk28]

JDK 28 is the next feature release, scheduled for general availability in March 2027.[^infoq-jdk28] So this isn't something you can put in production next week. But it's now on the plan, and the shape of the API is settled enough to understand.

### The background you need

#### JSON, and how Java has always handled it

{{JSON|JavaScript Object Notation: a text format for structured data, made of objects, arrays, strings, numbers, booleans and null}} is the default format for web APIs, configuration files and messages between services. Its rules are written down in {{RFC 8259|the internet standard that defines exactly what valid JSON text is}}.

The JDK can read XML, ZIP files and HTTP responses, but not JSON. For more than two decades, Java developers have instead relied on third-party libraries such as Jackson, Gson, JSON-P and JSON-B.[^adtmag] Those libraries mostly offer two styles of work. The first is {{data binding|automatically converting JSON into instances of your own Java classes and back, for example a JSON user record into a User object}}, which is what Spring does with your `@RequestBody` parameters. The second is a {{tree model|an in-memory representation of a JSON document as a tree of nodes (objects, arrays and plain values) that you navigate by key or index}}, where you parse the text and walk through it. Big libraries also offer {{streaming parsing|reading JSON token by token without building the whole document in memory, which is needed for very large inputs}}.

The JVM Weekly newsletter put the situation bluntly: "For twelve years the platform couldn't decide whether parsing JSON was any of its business, and in that time Jackson and Gson became part of Java in every sense except the formal one."[^jvmweekly]

#### The first attempt, and why it was shelved

The twelve years start in June 2014, when Mike Duigou created **JEP 198, "Light-Weight JSON API"**, reviewed by Brian Goetz. Its goals were broad: parsing and generation per the JSON standard of the time, several parsing styles (token streams, event streams and immutable trees), a builder API, a generator API and even a "transformer" for making modified copies of trees.[^jep198]

In December 2014, Mark Reinhold, the chief architect of the Java platform, proposed dropping it from JDK 9. A JSON API would be useful, he wrote, but "it's not as important as the other features that Oracle is funding, or considering funding, for JDK 9." He added that it could be reconsidered later, especially if future language features such as value types and generics over primitive types made a simpler and more capable design possible.[^reinhold2014]

That last remark turned out to be the key. The Java language of 2014 had no records, no sealed types and no pattern matching. The Java of 2026 has all three, and they change what a JSON API needs to look like.

#### The restart: "batteries included"

On 15 May 2025, Paul Sandoz of Oracle posted "Towards a JSON API for the JDK" to the core-libs-dev mailing list. His argument was that Java follows a "batteries included" philosophy, so developers should be able to handle common data formats without third-party dependencies, while existing libraries remain the right tool for heavier work.[^sandoz]

The design he described is the ancestor of JEP 540. JSON is modelled as an {{algebraic data type|a type defined as a fixed set of alternatives, e.g. "a JSON value is exactly one of: object, array, string, number, boolean or null"}}: a family of interfaces called `JsonValue`, `JsonArray`, `JsonObject`, `JsonNumber`, `JsonString`, `JsonBoolean` and `JsonNull`. Anything fancier would be built on top: "Advanced features, such as data binding or path-based traversal should be possible to implement as layered features, but for simplicity are not included in the core API."[^sandoz] The prototype lived in a `json` branch of the JDK sandbox repository and, Sandoz reported, passed all but two cases of the JSONTestSuite conformance tests. The two failures were deliberate: the API rejects objects with duplicate member names.[^sandoz]

A year later, in July 2026, JEP 540 appeared as a formal proposal.[^adtmag] InfoQ describes it as narrower than the JEP 198 plan, concentrating on an immutable, in-memory tree of values and leaving object mapping, streaming, schema validation and advanced customisation to existing libraries.[^infoq-json]

### How it works

#### One entry point, one tree of values

Everything starts with the `Json` class. `Json.parse(...)` takes a `String` (or a `char[]`) and gives you back a `JsonValue`: the root of an {{immutable|cannot be changed after it's created, so it's safe to share and cache}} tree. Instances are also {{thread-safe|safe to use from several threads at once without extra locking}}.[^infoq-json]

`JsonValue` is a {{sealed interface|an interface that lists exactly which types may implement it, so the compiler knows every possible case (Java 17+)}}. It permits six subinterfaces, one for each kind of JSON value. Those six are themselves non-sealed, which leaves room for alternative implementations, an idea Sandoz mentioned in 2025 for efficient non-text encodings.[^infoq-json]<sup>,</sup>[^sandoz]

#### Navigating: get, tryGet and the as… methods

You walk the tree with `get(String)` for an object member and `get(int)` for an array element. When you reach the value you want, you convert it with `asInt()`, `asLong()`, `asDouble()`, `asBoolean()` or `asString()`. Whole containers convert with `asMap()` and `asList()`. Here is the example from the JEP, as shown by InfoQ, reading a temperature from a weather-forecast response (right), next to the tree-model route most teams use today (left). The left pane uses Jackson 2's `ObjectMapper`, which needs the `jackson-databind` dependency; the right pane needs nothing but the JDK.[^infoq-json]

```viz:codecompare

```

The interesting design decisions are in how the API behaves when the data isn't what you expect.

**Missing vs null.** JSON makes a difference between a member that isn't there and a member that is there with the value `null`. The API keeps that difference. `tryGet(String)` returns an {{Optional|java.util.Optional: a box that either holds a value or is empty, used instead of returning null}} that's empty when the member is absent, and holds a `JsonNull` when the member is explicitly null. A second method, `tryValue()`, turns `JsonNull` into an empty `Optional` too, for when you don't care about the distinction.[^infoq-json]

**Numbers are strict.** JSON has a single "number" type with no size limit and no difference between integers and decimals. Java has `int`, `long`, `double` and `BigDecimal`. The API refuses to guess: "`asInt()` and `asLong()` require an exact integral value within the destination type's range." So `3.5`, or a value bigger than `Integer.MAX_VALUE`, won't quietly become something else. `asDouble()` is the exception: it converts any number to a finite `double`, "but may round or lose precision."[^infoq-json] Sandoz flagged numbers as a known source of interoperability problems in 2025, and his prototype also exposed the raw text of a number and a `BigDecimal` conversion.[^sandoz] Numeric conversions are one of the areas where the JEP explicitly asks for feedback.[^infoq-json]

**Two kinds of failure.** Broken JSON text throws `JsonParseException`. It's an {{unchecked exception|an exception that extends RuntimeException, so the compiler doesn't force you to catch or declare it}}, and it records the zero-based line and position of the error. Asking for the wrong type, say `asInt()` on a string, throws `JsonValueException` instead.[^infoq-json]

#### Strict by design

The parser accepts exactly what RFC 8259 allows, and nothing else. There are no comments, no trailing commas and no other syntax extensions. Duplicate member names, such as `{"id": 1, "id": 2}`, are always an error.[^infoq-json]<sup>,</sup>[^newscast114] A duplicate key is ambiguous (which value wins?), and two systems reading the same document might answer differently. Rejecting duplicates outright is, as InfoQ puts it, meant to mitigate those interoperability risks.[^infoq-json]

#### Building and writing JSON

To produce JSON, you build values with factory methods and turn them into text:[^infoq-json]

```java
JsonObject document = JsonObject.of(Map.of(
    "service", JsonString.of("web_server"),
    "id", JsonNumber.of(3),
    "active", JsonBoolean.of(true)
));
String compact = document.toString();
String pretty  = Json.toDisplayString(document);
```

`toString()` produces compact JSON; `Json.toDisplayString(...)` produces a formatted version meant for humans.[^infoq-json] The JEP itself calls construction ergonomics "one likely area for feedback", which is a polite way of admitting that wrapping every value in `JsonString.of(...)` is wordy.[^infoq-json]

#### Pattern matching does the rest

Because `JsonValue` is sealed, it works naturally with {{pattern matching for switch|a switch that branches on the type of a value and binds it to a variable in one step (Java 21+)}}. This is how you handle a field that might arrive as a number or a string:[^infoq-json]

```java
long id = switch (json.get("id")) {
    case JsonNumber number -> number.asLong();
    case JsonString string -> Long.parseLong(string.asString());
    default -> throw new JsonValueException("Unexpected id type");
};
```

Sandoz's 2025 post explains why the API looks so minimal: it's betting on the language. As {{deconstruction patterns|a planned pattern-matching feature that pulls the components out of an object in a single pattern, the way record patterns do for records}} mature, extracting data from JSON should get more elegant without needing extra convenience methods in the API.[^sandoz]

#### Switching it on

Incubator modules aren't visible by default. On the {{class path|the traditional list of JARs and directories the JVM loads classes from, as opposed to the module path}}, you add the module explicitly, when compiling and when running:[^infoq-json]<sup>,</sup>[^jep11]

```bash
javac --add-modules jdk.incubator.json App.java
java  --add-modules jdk.incubator.json App
```

The JVM prints a warning whenever an incubator module is resolved, at compile time, link time and run time, and the run-time warning can't be suppressed.[^jep11]

### What it means for you

**It won't replace Jackson in your Spring Boot service, and it isn't meant to.** The JEP leaves out data binding, streaming, lenient parsing and syntax extensions on purpose. Its target is "common tasks such as reading a configuration file, inspecting a REST response, or generating a small JSON payload."[^infoq-json] Spring will keep turning request bodies into your DTOs with its own machinery. Nothing in your existing code changes.

**Where it will matter is in the places where a dependency feels excessive.** Think of a build script, a small CLI tool, a test helper that checks one field in a response, a library that wants to read one config file without pulling Jackson into every user's dependency tree, or the JDK's own tools. Each of those today either adds a library or hand-rolls string parsing. A JDK-provided parser removes that choice. It also removes a dependency you have to keep patching, which matters when a widely used JSON library has a security advisory and every project that uses it has to upgrade.

**The reception has been mixed.** The JEP justifies itself by saying, in JVM Weekly's quotation, that "the Python or Go code for these tasks is simple and the Java code should be equally simple." One Hacker News commenter answered that "the examples actually show a lot of ceremony", and JVM Weekly notes that this critique stings precisely because of that goal.[^jvmweekly] Look at the construction example above and you can see the point. That's exactly why it's an incubator: the shape can still change.

<div class="box tryit" markdown="1">
**🧪 Try it when it lands**

Once a JDK 28 early-access build includes the module, a single-file program is the quickest way to get a feel for the API. Save a JSON file, parse it with `Json.parse(Files.readString(path))`, walk it with `get(...)`, and then deliberately break it: add a trailing comma, a comment, a duplicate key, or a `3.5` where you call `asInt()`. Seeing which exception you get, and where it points, tells you more about the API's philosophy than any summary. Feedback goes to the core-libs-dev mailing list.
</div>

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Incubator means unstable.** The API can change incompatibly or be removed in a later release.[^infoq-json] Incubator APIs live under `jdk.incubator.*`, never in `java.*`, so they're not part of the Java SE standard yet.[^jep11] Don't build a public library API on top of it.
- **Startup warnings.** Every run with the module resolved prints an incubator warning that you can't switch off at run time.[^jep11] Fine for tools, awkward for anything that parses its own console output.
- **Strictness can bite.** If your config files contain comments or trailing commas, or if an upstream API sends duplicate keys, this parser will throw where a more lenient one wouldn't have.[^infoq-json]
- **Big numbers.** `asDouble()` may round; `asInt()`/`asLong()` throw unless the value fits exactly.[^infoq-json] For money or very large IDs, check the final API for an exact (text or `BigDecimal`) route before you rely on it.
- **Not for huge files.** There's no streaming. The whole document is parsed into memory.[^infoq-json]
</div>

### What happens next

The JEP asks for feedback in four areas: the navigation model, exception semantics, numeric conversions and construction ergonomics.[^infoq-json] Incubator APIs normally stay in incubation for "a small number of feature releases" before they're either made permanent or removed.[^jep11] JDK 28 itself is due in March 2027.[^infoq-jdk28] So the realistic timeline is that you'll be able to experiment in 2027, and a final, standard `java.*` JSON API is a few releases beyond that, if the feedback is good. After twelve years, a few more releases to get it right doesn't seem like much to ask.

# Story 2 · Oracle's Java patches go monthly

<div class="byline">Oracle JDK · OpenJDK distributions · Security · First CSPU 18 Aug, next 17 Nov 2026 · ~12 min read</div>

<p class="opener" markdown="1">For years, Java security had a rhythm you could put in a calendar: four times a year, on a Tuesday in January, April, July and October, Oracle published its Critical Patch Update and every JDK vendor followed. Ops teams planned their quarters around it. That rhythm just broke. In July, Oracle's quarterly update across all its products contained more patches than ever before. In August, Java got its first monthly security release. And the reason, according to Oracle, is the same one that pushed Spring onto a monthly train: AI is finding vulnerabilities faster than a quarterly calendar can absorb.</p>

### What happened

On 20 July, Donald Smith, Oracle's vice president of product management, published on the Java blog "Transitioning Java to more frequent security updates". Its summary is short: "Oracle intends to provide Java security updates more frequently than the current quarterly CPU cadence of January, April, July, and October."[^oracle-blog]

The new releases are called **Critical Security Patch Updates (CSPUs)**. They're "intended to provide an opportunity every month for targeted fixes that address high-priority vulnerabilities, instead of having to wait until the next quarterly CPU."[^oracle-blog] The first one shipped on **18 August 2026**. Oracle updated the post on 10 September to say the next planned Java CSPU is on **17 November 2026**, alongside the regular October and January quarterly updates, with "multiple" monthly updates planned for 2027.[^oracle-blog]

The August Java CSPU covered six release lines at once: 26.0.2.1, 25.0.4.1, 21.0.12.1, 17.0.20.1, 11.0.32.1 and 8u503.[^jms-notes] Oracle's advisory listed six new security patches for Java SE, four of them exploitable remotely without authentication, with a highest CVSS base score of 8.2.[^cspu-aug] Tenable's scanner entry for it names the affected components as the installer, {{JSSE|the Java Secure Socket Extension: the JDK's implementation of TLS, the protocol behind HTTPS}} and networking.[^tenable-plugin]

The rest of the ecosystem moved with it. Azul had already committed on 23 July to monthly CSPUs for its builds, starting in August, on the third Tuesday of each month.[^azul-news] Amazon released Corretto CSPU builds the same day as Oracle, 18 August.[^corretto] Eclipse Temurin, the Adoptium project's free OpenJDK build, followed on 2 September with what it called "a security-only, out-of-band release addressing vulnerabilities disclosed by Oracle."[^temurin]

### The background you need

#### CPUs: Java's quarterly heartbeat

A {{Critical Patch Update (CPU)|Oracle's quarterly, cumulative security release for all its products, on the third Tuesday of January, April, July and October}} bundles every security fix Oracle has ready for its products into one release.[^azul-blog] For Java, a CPU comes out as a new update version of each supported JDK line. Each fix is tracked as a {{CVE|Common Vulnerabilities and Exposures: a public ID such as CVE-2026-61308 that names one specific security flaw}} and scored with {{CVSS|Common Vulnerability Scoring System: a 0–10 severity score, where 7.0+ is "high" and 9.0+ is "critical"}}.

Why does this matter to OpenJDK builds that aren't Oracle's? Because security fixes for OpenJDK are coordinated privately among vendors and released on the same day. That's why Microsoft's July OpenJDK update, for example, points to the "OpenJDK Vulnerability Advisory July 2026" and shipped as 25.0.4, 21.0.12, 17.0.20 and 11.0.32: the same update numbers as Oracle's.[^microsoft] When Oracle's calendar changes, the whole ecosystem's calendar changes.

#### The fourth digit

Java version numbers have four parts, defined by JEP 322 back in JDK 10: `$FEATURE.$INTERIM.$UPDATE.$PATCH`. The `$UPDATE` counter is "incremented for compatible update releases that fix security issues, regressions, and bugs". The fourth, `$PATCH`, is "the emergency patch-release counter, incremented only when it's necessary to produce an emergency release to fix a critical issue."[^jep322] So `21.0.12` is the twelfth update of JDK 21. Most developers have rarely seen a fourth digit at all.

CSPUs turn that rarity into routine. As JVM Weekly put it, the fourth digit was "previously reserved for emergency releases but is now used for CSPUs."[^jvmweekly] `21.0.12.1` means "21.0.12 plus one round of urgent security fixes".

#### Why now: the AI patch flood

Oracle's explanation is that "the latest generation of AI is transforming how software vulnerabilities are identified and fixed, increasing the speed and scale of discovery and remediation."[^oracle-blog] Azul's CEO Scott Sellers made the same point when announcing its monthly programme: "As AI sharply increases the volume of threats enterprises face, enterprises shouldn't have to choose between the two", meaning speed and stability.[^azul-news]

The numbers across Oracle's whole product portfolio show the pressure. According to Tenable, Oracle introduced monthly CSPUs for its other products in May 2026. The April CPU contained 481 patches; the July CPU, 1,449. Even the "small" monthly releases are big: 245 patches in June and 943 in August.[^tenable-aug] JVM Weekly compared July's total with 309 patches a year earlier.[^jvmweekly]

Java is a small slice of those totals. But Java security fixes are released as part of Oracle's programme, so Java inherits its calendar.

### How it works

#### A CSPU is a small branch off the last CPU

A CSPU isn't a mini-CPU with everything in it. Azul's Frank Delporte describes CSPUs as containing security fixes and stability patches only: no new features, no API changes and no behaviour changes beyond fixing the vulnerability. They branch from the last quarterly release tag, apply the fixes with minimal scope, then merge back, "leaving the regular quarterly cycle unaffected."[^azul-blog] Oracle's own advisory calls a CSPU a release that "provides targeted, high-priority security fixes in a smaller, more focused format, making them easier to apply with minimal disruption", which complements the quarterly cumulative CPUs.[^cspu-aug] Temurin describes it the same way: "a security update based off of the quarterly 'CPU' releases."[^temurin]

### What it means for you

**Your patch cadence probably needs to become monthly.** Oracle says it plainly: "Users need to patch their Java installations more often to remain on the Java security baseline. Organizations that deliver applications bundled with a JDK or JRE may also need to assess how a faster update cadence affects their build, test, release, and deployment processes."[^oracle-blog] If you build container images on a base JDK image, that means rebuilding and redeploying on the CSPU dates too, not just four times a year.

**Treat a CSPU like any other patch.** Azul's advice is to handle CSPUs exactly as you handle quarterly CPUs: let your dependency tooling pick them up, run the existing test suite, and push them through your normal pipeline.[^azul-blog] Because they are security-only and narrow, they're low-risk to apply. The real work is making your pipeline cheap enough that monthly runs don't hurt.

**One shared patch week.** This lines up neatly with the story from our previous issue. Spring's monthly "Patch Thursday" falls on "the Thursday after the third Monday of the month";[^spring-train] Oracle's CSPU falls on the third Tuesday. In October that's 20 October for Oracle's CPU and 22 October for Spring's first train; in November, 17 November for the next Java CSPU and 19 November for Spring.[^cspu-sep]<sup>,</sup>[^spring-train] For a typical Spring Boot service, the third week of the month becomes "patch week" for both the JDK and the framework.

**Check anything that parses Java versions.** Code and scripts that assume a version has three numbers will trip on `21.0.12.1`, and Corretto's longer strings stretch that further.[^corretto] In Java code, use `Runtime.version()`, which already exposes all four parts, including `patch()`, as defined by JEP 322.[^jep322] In shell scripts, Dockerfiles and monitoring dashboards, look for regular expressions such as `\d+\.\d+\.\d+$`.

<div class="box realworld" markdown="1">
**🌍 In the real world: the installer that didn't upgrade**

The first Temurin CSPU produced a small, instructive bug report. A user on an Apple Silicon Mac installed the `jdk-25.0.4.1+1` package and found the JDK still reported `25.0.4+7`. The cause: the existing 25.0.4 installation was still present and the package didn't overwrite it cleanly; removing the old directory and reinstalling fixed it. Maintainers also noted they hadn't published an official GA build for that configuration because of test failures.[^temurin-issue] The lesson for monthly patching: after every rollout, check what `java -version` actually reports, rather than trusting that the package manager did its job.
</div>

**JDK 21 users on Oracle's free licence: this is the moment.** Oracle's August blog says JDK 21 updates "through and including September 2026" are available under the free {{NFTC|Oracle's No-Fee Terms and Conditions licence, which allows free production use of Oracle JDK builds for a limited period}}, and that updates beginning with the October 2026 CPU are planned under the {{OTN|the Oracle Technology Network licence, which allows free development use but generally requires a paid subscription for production}} licence.[^oracle-21] Since September brought no Java CSPU, the August CSPU build 21.0.12.1 looks to be the last Oracle JDK 21 update under NFTC. From 20 October, staying patched on Oracle JDK 21 means a subscription, moving to JDK 25 (whose NFTC updates are planned until October 2028[^oracle-21]), or switching to another vendor's build. Issue #1 covered those options in detail.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **"Monthly" isn't guaranteed.** September had a CSPU date but no Java SE release.[^cspu-sep] Subscribe to your vendor's advisories instead of assuming a fixed rhythm.
- **Vendors don't all ship on the same day.** Temurin's first CSPU came two weeks after Oracle's.[^temurin] If you rely on a specific distribution, watch its release page, not Oracle's.
- **Version strings differ by vendor.** `21.0.12.1` (Oracle), `21.0.12.9.1` (Corretto), `21.0.12.1+1` (Temurin) are all the same security level.[^jms-notes]<sup>,</sup>[^corretto]<sup>,</sup>[^temurin]
- **Non-LTS lines get CSPUs too, briefly.** August's release included JDK 26 (26.0.2.1),[^jms-notes] but Oracle's roadmap ends JDK 26 support in September 2026.[^roadmap] If you're on a non-LTS release, you still need to move to the next one.
- **The quarterly CPU still matters most.** CSPUs are narrow. Bug fixes and broader changes still arrive in the quarterly CPUs, the next on 20 October.[^azul-blog]<sup>,</sup>[^cspu-sep]
</div>

### What happens next

The next dates to circle are **20 October** (the quarterly CPU, and the switch of Oracle JDK 21 updates to the OTN licence) and **17 November** (the next planned Java CSPU), followed by 15 December and the 19 January 2027 CPU.[^cspu-sep]<sup>,</sup>[^oracle-blog] Oracle expects "multiple" monthly Java updates in 2027.[^oracle-blog] The open question is how often Java will actually need its monthly slot. If AI-assisted vulnerability research keeps accelerating, the honest answer may soon be "most months", and the teams that automated their JDK upgrades this autumn will be glad they did.

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **Critical Patch Update (CPU)**: Oracle's quarterly, cumulative security release, on the third Tuesday of January, April, July and October.
- **Critical Security Patch Update (CSPU)**: Oracle's new monthly, targeted security release between CPUs, versioned with a fourth digit (e.g. 21.0.12.1).
- **CVE**: Common Vulnerabilities and Exposures, a public ID naming one specific security flaw.
- **CVSS**: Common Vulnerability Scoring System, a 0–10 severity score.
- **JSSE**: the Java Secure Socket Extension, the JDK's implementation of TLS.
- **$PATCH**: the fourth part of a Java version number, defined by JEP 322 as the emergency patch-release counter.
- **NFTC**: Oracle's No-Fee Terms and Conditions licence, allowing free production use of Oracle JDK for a limited period.
- **OTN**: the Oracle Technology Network licence, free for development but generally requiring a subscription for production use.
