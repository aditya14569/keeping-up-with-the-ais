# Story 1 · Structured concurrency graduates in JDK 28

<div class="byline">JDK 28 · OpenJDK · Project Loom · JEP 543 integrated 17 Oct 2026 · ~15 min read</div>

<p class="opener" markdown="1">Ten days ago, in issue #5, we described structured concurrency as a feature that was "about to" become a normal part of Java: a Candidate JEP with an open pull request and a review still to come. That "about to" is over. Early on Saturday morning, a 12-file commit removed the word "preview" from `java.util.concurrent.StructuredTaskScope` for good. After four years, two incubators and seven previews, the API that lets you treat a bundle of threads as a single task is finished. Here's what happened, what quietly changed in the last mile, and what it means for code you write today.</p>

### What happened

On 17 October 2026 at 06:06 UTC, Oracle's Alan Bateman integrated **"8391460: Implement JEP 543: Structured Concurrency"** into the JDK main line, reviewed by Viktor Klang.[^commit] It changes 12 files (612 lines added, 434 removed). The headline changes are short: the `@PreviewFeature` annotation is removed from `StructuredTaskScope` and from `StructureViolationException`, their `@since` tags become `@since 28`, and the JDK's internal list of preview features no longer marks structured concurrency as "Seventh Preview".[^commit]

This is the last step of a process we followed in issue #5. {{JEP 543|the JDK Enhancement Proposal to make structured concurrency a final, permanent feature}} proposed to finalise the API "without change, after seven rounds of preview". InfoQ reported that it moved from Candidate to {{Proposed to Target|the stage where a JEP is formally proposed for a specific JDK release, followed by a short public review period}} for JDK 28, with the review "expected to conclude on Tuesday, October 13, 2026".[^infoq-oct05] Four days after the review window closed, the code was in. (As of 19 October, Inside.java hadn't yet posted a "targeted to JDK 28" announcement for JEP 543, as it did for JEP 545 on 16 October.[^inside])

To be precise about where this lives: it's in the {{main line|the master branch of the openjdk/jdk repository, from which the next JDK release is built}}, not yet in a downloadable build. The newest JDK 28 {{early-access build|a weekly pre-release JDK binary published so developers can test upcoming features}} we found, build 20, was tagged on 15 October and predates the commit, so you'll need the next build to try it.[^tags] JDK 28 itself is a non-{{LTS|Long-Term Support: a JDK release that vendors support for years (21, 25, the planned 29); the releases in between get about six months}} release due in March 2027.[^infoworld]

### The background you need

#### What structured concurrency is, in one paragraph

If you read issue #5, skip ahead. If not, here's the idea. A {{thread|an independent path of execution inside your program}} that starts other threads normally has no relationship with them: if one fails, the others keep running, and nothing guarantees they've finished when your method returns. {{Structured concurrency|a style of concurrent programming in which tasks started inside a block of code must finish before that block ends, just as a method call finishes before its caller continues}} fixes that. You open a {{scope|a block of code that owns a group of concurrent tasks and doesn't end until all of them have ended}}, `fork()` some {{subtasks|the pieces of work started inside a scope, each running in its own thread}}, wait for them at one point with `join()`, and when the block ends, every thread it started has ended too. If a subtask fails, the others are cancelled. The thread that opened the scope is its {{owner|the thread that opened a scope; only it may fork, join and close it}}.

It only became practical once Java got {{virtual threads|lightweight threads managed by the JVM rather than the operating system, cheap enough to create one per task}} in JDK 21, because a scope typically starts a brand-new thread for every subtask.

#### Why "final" matters so much

New Java APIs usually arrive as a {{preview API|a complete but not yet permanent feature that only works if you pass --enable-preview to javac and java, so it can still change}} first. Previews are deliberately awkward to use in production, and the awkwardness is enforced in the class file itself. We tried it on JDK 21: we compiled a tiny program that uses the JDK 21 structured concurrency preview with `javac --release 21 --enable-preview`, and `javap` shows the class file version as **65.65535**.[^own] That 65535 {{minor version|the second half of a class file's version number; 65535 (all 16 bits set) marks a class that uses preview features}} is the marker. Running the class without the flag fails immediately:

```text
java.lang.UnsupportedClassVersionError: Preview features are not enabled
for Dash (class file version 65.65535). Try running with '--enable-preview'
```

The rules are spelled out in the original JVM work for preview features: a preview class file loads only if `--enable-preview` is given **and** its major version is the current release. Preview class files from an earlier release fail even with the flag.[^jdk8200440] So a library compiled against the JDK 27 preview simply won't load on JDK 28. That's why frameworks and library authors have largely stayed away from structured concurrency: depending on it meant forcing every user onto one exact JDK version, with a scary flag.

Now that it's final, code that uses `StructuredTaskScope` compiles to an ordinary class file, runs without flags and keeps running on every later JDK. That's the real news.

The JEP numbers above come from a JDK 28 overview by Japanese blogger mammb, which lists the path from JEP 428 (JDK 19, incubator) through JEP 533 (JDK 27, seventh preview) to JEP 543.[^mammb] The design changed a lot on the way. In the JDK 21 preview you created a scope with a constructor and picked a policy by choosing a subclass such as `ShutdownOnFailure`. JDK 25 (JEP 505) replaced that with static `open()` methods and a separate policy object, the `Joiner`. JDK 26 and 27 then polished exceptions and types: JEP 533, for example, made the standard joiners throw the familiar checked `ExecutionException` instead of a preview-only `FailedException`, and added a third type parameter for the exception `join()` throws.[^infoq-533]

### How it works

#### The API you get is the JDK 27 API, exactly

We compared the public declarations in `StructuredTaskScope.java` before and after the commit: all 27 of them (the interface, its nested `Subtask`, `Joiner` and `Configuration` types, every factory method, `fork`, `join` and so on) are identical.[^commit] So JEP 543 kept its promise of "no change". If your code compiles against the JDK 27 preview, it will compile against JDK 28 without the flag.

Here's the shape of the final API, written the way the JDK's own Javadoc examples are:[^commit]

```java
// JDK 28: final API, no --enable-preview needed.
Response handle() throws InterruptedException, ExecutionException {
    try (var scope = StructuredTaskScope.open()) {
        Subtask<String> user  = scope.fork(() -> findUser());
        Subtask<Integer> order = scope.fork(() -> fetchOrder());
        scope.join();   // waits; throws if either subtask failed
        return new Response(user.get(), order.get());
    }
}
```

`open()` uses the default policy: wait for all subtasks to succeed, and if any fails, cancel the others and make `join()` throw an `ExecutionException` whose cause is the failure. Other policies come from {{Joiner|an object you pass to open() that decides when a scope is done and what join() returns or throws}} factory methods: `allSuccessfulOrThrow()` returns a `List` of results, `anySuccessfulOrThrow()` returns the first success and cancels the rest, and `allUntil(predicate)` lets you decide when enough is enough.[^commit] A second `open()` overload takes a {{UnaryOperator|a function that takes a value and returns a value of the same type; here, it takes the default configuration and returns your adjusted one}} to configure a timeout, a name or a custom {{ThreadFactory|an object that creates the Thread objects a scope runs subtasks in; the default creates virtual threads}}.

#### What actually changed in the last commit

"No API change" doesn't mean nothing changed. Most of the 671 lines touched in `StructuredTaskScope.java` are Javadoc rewrites: the usage rules are now a bulleted list (only the owner may fork, join and close; `join()` must be called after forking; neither `fork` method may be called after `join()`), and the cancellation section now says explicitly that cancelling interrupts the threads running unfinished subtasks.[^commit] But the commit also fixes three edge cases in the implementation class, `StructuredTaskScopeImpl`, and adds tests for each. If you write your own `Joiner`, the first one matters.

**1. A fork that can't start a thread now counts as a failed subtask.** Before, if the scope's `ThreadFactory` threw an exception or returned `null`, `fork()` threw and the subtask was left in limbo with no result. And if the underlying thread group refused to start the thread (for reasons other than cancellation), that was silently ignored. Now, in all of those cases, the subtask is marked `FAILED` with the exception, the joiner's `onComplete()` callback is called **on the owner thread** so the policy sees the failure, and only then does `fork()` rethrow. If `onComplete()` itself throws, that exception is attached to the original as a {{suppressed exception|an extra exception attached to the main one with addSuppressed(), so it isn't lost}}.[^commit] New tests named `testOnCompleteAfterForkFails` and `testOnCompleteThrowsAfterForkFails` pin this down.

**2. A joiner can read the failure from inside that callback.** Normally `Subtask.exception()` throws `IllegalStateException` unless you're the subtask's own thread or the owner has already joined. Because of change 1, the owner can now be inside `onComplete()` before any join, so the implementation records which thread is making the callback and lets exactly that thread call `exception()`.[^commit]

**3. "Closed" now remembers whether you joined.** The scope's internal state used to have a single `CLOSED` value, and its "has join completed?" check was `state >= JOIN_COMPLETED`, which was also true for a scope that had been **closed without ever joining**. The commit splits it into `CLOSED_BEFORE_JOIN` and `CLOSED_AFTER_JOIN`.[^commit] The new tests check that after closing a scope that never joined, a subtask's result is still unavailable, even after repeated `close()` calls. In other words, you can't sneak a result out of a scope you abandoned.

#### Under the hood: a "flock" of threads

How does a scope know which threads are its own, and how does it make the guarantee that nothing outlives it? Reading the implementation answers that, and it's worth knowing because the Loom team has hinted that this machinery may become public one day.

Every scope is backed by a {{ThreadFlock|an internal JDK class (jdk.internal.misc.ThreadFlock) that groups threads running closely related tasks and waits for all of them}}. Its Javadoc describes it as "a grouping of threads that typically run closely related tasks", where threads started in a flock stay in it until they terminate. It has the operations you'd expect: `open`, `start(thread)`, `awaitAll()`, `wakeup()` (to make `awaitAll()` return early, used for cancellation), `shutdown()` (no new threads) and `close()`, which "blocks until all threads in the flock finish".[^flock]

Here's how the scope's operations map onto it, from the source:[^commit]<sup>,</sup>[^flock]

- **`open()`** creates a flock owned by the current thread. The flock captures the owner's {{scoped value|an immutable value bound for a bounded stretch of code and visible to everything it calls, including child threads in a scope (final since JDK 25)}} bindings at that moment, so every subtask inherits them. That's what JEP 506 means when it says scoped values "in the parent thread are automatically inherited by child threads created with StructuredTaskScope".[^jep506]
- **`fork()`** asks the `ThreadFactory` for a new, unstarted thread and starts it *inside* the flock. If the owner's scoped-value bindings have changed since the scope opened, starting the thread throws a `StructureViolationException`.
- **`join()`** calls the flock's `awaitAll()`. Each finishing thread decrements a counter, and when it reaches zero the owner is woken with `LockSupport.unpark`. Then the scope asks the joiner for the result, or calls the joiner's `timeout()` method if the timer fired.
- **Cancellation** (a failed subtask, a joiner saying "done", or a timeout) shuts the flock down, interrupts every thread in it and wakes the owner. A subtask that finishes *after* the scope has been cancelled has its result dropped and stays `UNAVAILABLE`.
- **Timeouts** are a scheduled task on the common `ForkJoinPool` that cancels the scope when it fires.
- **`close()`** cancels the scope if you never joined, then closes the flock, which waits for every thread. If you close an outer flock while an inner one is still open, the inner ones are closed first (newest first) and a `StructureViolationException` is thrown.

The flock also registers a {{thread container|the JDK's internal record of which threads belong to which group, used by tools such as jcmd's JSON thread dump}}, which is why a JSON thread dump can show subtasks nested under the scope that owns them. ThreadFlock's own documentation says flocks are "conceptually nodes in a tree": a thread in flock A that opens flock B makes A the parent of B.[^flock]

That's the "lower-level" layer. At Devoxx Belgium this month, Alan Bateman and Viktor Klang gave a talk called "Structured Concurrency Looms". Its Inside.java description says they look at "a new lower-level API behind the latest design", and that this work is "expected to form the basis of a future lower-level structured concurrency API".[^looms] The talk description doesn't name ThreadFlock, so we can't say for sure that's what they mean. But it's a clear signal that `StructuredTaskScope` is the friendly front door, and more building blocks may follow.

### What it means for you

#### If you're on JDK 21 or 25 LTS

Nothing changes for you today. The final API will be part of every JDK from 28 onwards, and the next LTS that includes it is planned to be **JDK 29, in September 2027**, according to Oracle's support roadmap (which notes LTS designations "are subject to change").[^roadmap] Until then, `ExecutorService` and `CompletableFuture` remain the production tools on LTS releases.

If you experimented with the preview on an LTS release, be aware that the API you used is **not** the final one. The JDK 21 preview (constructors, `ShutdownOnFailure`) is entirely different, and the JDK 25 preview is close but not compatible. We checked the JDK 25 source: there, `StructuredTaskScope` has two type parameters, `allSuccessfulOrThrow()` returns a `Stream` of subtasks, the "first success" joiner is called `anySuccessfulResultOrThrow()`, failures arrive as an unchecked `FailedException`, and `open(joiner, ...)` takes a `Function` rather than a `UnaryOperator`. JDK 25 also had an `awaitAll()` joiner, which is gone.[^jdk25]<sup>,</sup>[^commit]

#### If you're on the six-monthly train

If you run JDK 27 with `--enable-preview` for structured concurrency (and nothing else), moving to JDK 28 means **removing the flag** from your compiler settings, test runner, run scripts and container images. That's the whole migration. In issue #5 we described how the open-source media server streamarr was planning exactly that: its tracking issue lists the build, the tests, the Procfile, the container image and CI.[^streamarr]

#### If you maintain a library

This is the group the change really unlocks. Until now, a library that used `StructuredTaskScope` would only load on one JDK version, with a flag. From JDK 28, you can use it the way you use `CompletableFuture`. One small project already shows the pattern for bridging the gap: **velo/structured-concurrency** repackages the final JDK 28 API under its own package name as a plain library "for JDK 21 or later, without `--enable-preview`", built from the public Javadoc and JEP text rather than OpenJDK's code. It ships an {{OpenRewrite|an open-source tool that applies automated, rule-based refactorings ("recipes") to source code}} recipe that renames the package to `java.util.concurrent` once you move to JDK 28. Its README lists known gaps, for example subtasks don't inherit scoped-value bindings.[^velo] It's a tiny project (no stars when we looked), so treat it as an illustration of the migration path, not an endorsement.

#### If you write custom joiners

Read the three changes above. In particular, `onComplete()` can now be called on the owner thread, during `fork()`, for a subtask that never ran. A joiner that assumed `onComplete()` always runs on a subtask's own thread, or that every completed subtask actually executed, should be checked.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **It's in the main line, not in a build yet.** JDK 28 early-access build 20 (15 October) predates the commit. Wait for the next build before testing.[^tags]
- **Preview code doesn't carry over automatically.** Classes compiled with `--enable-preview` on JDK 27 won't load on JDK 28. You must recompile, even though the source is the same.[^jdk8200440]
- **JDK 21 and JDK 25 preview code needs real changes**, not just a recompile (see the comparison above). Old tutorials using `ShutdownOnFailure`, `FailedException` or `awaitAll()` describe earlier previews.
- **Cancellation is still cooperative.** Cancelling a scope interrupts the subtask threads; a task that ignores interrupts can still hold `close()` open.[^commit]
- **`Subtask.get()` never blocks.** It throws unless the owner has joined and the subtask succeeded. Call it after `join()`.[^commit]
</div>

### What happens next

The next JDK 28 early-access build should be the first one with the final API. JDK 28 enters {{Rampdown Phase One|the point in a JDK release's schedule when the feature set is frozen and only bug fixes go in}} later in its schedule and ships in March 2027.[^infoworld] Meanwhile, keep an eye on the Loom project for the "lower-level structured concurrency API" that Bateman and Klang previewed at Devoxx.[^looms] For most application developers, though, the decision point is JDK 29: the first planned LTS where you can use structured concurrency with no flags and no caveats.[^roadmap]

# Story 2 · Jakarta EE gets a standard for instant startup

<div class="byline">Jakarta EE · Eclipse Foundation · Jakarta CRaC 1.0 · Creation and plan review approved 13 Oct 2026 · ~14 min read</div>

<p class="opener" markdown="1">Imagine your application server booting the way your laptop wakes from sleep. No scanning JARs, no wiring thousands of beans, no waiting for the JIT compiler to warm up: just pick up exactly where a previous run left off. That's the promise of checkpoint and restore, and several Java runtimes already offer it, each in its own way. Last week the Jakarta EE community voted to turn it into a standard. Here's what a JVM snapshot actually is, why it's harder than it sounds, and what the new Jakarta CRaC specification sets out to fix.</p>

### What happened

On 13 October 2026, the Jakarta EE Specification Committee's ballot on a new specification, **Jakarta CRaC 1.0**, "concluded successfully". It was a combined {{creation review|the Eclipse Foundation vote that approves starting a new specification project}} and {{plan review|the vote that approves what a specification's next release intends to deliver}}, with +1 votes from the representatives of Fujitsu, IBM, Oracle, Payara, Tomitribe and others, and no votes against.[^cracballot] Eclipse Foundation's Ivar Grimstad merged the specification's page into the official Jakarta EE specifications repository on 14 October.[^cracpr]

The spec's description is a single sentence: Jakarta CRaC "defines how Jakarta EE runtimes take part in JVM checkpoint and restore, so that an application can be restored from a snapshot instead of starting from scratch." Its stated goal is "to cut startup time substantially while keeping applications correct and portable across compliant application servers".[^cracspec]

The project proposal was published on 17 September. Its project lead is Gerrit Grunwald of Azul, the company behind the original CRaC work,[^deck] and its initial committers are Ivar Grimstad, Steve Butler, Rustam Mehmandarov and Thomas Watson. Azul and IBM are listed as interested parties.[^proposal] Grimstad's weekly "Hashtag Jakarta EE" column announced the community review on 27 September.[^hashtag352]

This is a brand-new specification, so there's no code to download yet. It's a commitment, approved by the vendors who build Jakarta EE servers, to standardise something they each currently do differently.

### The background you need

#### Jakarta EE in two minutes

{{Jakarta EE|the open, vendor-neutral set of enterprise Java specifications (formerly Java EE) run by the Eclipse Foundation: CDI, Persistence (JPA), REST, Servlet and many more}} isn't a product. It's a set of {{specifications|documents plus an API JAR plus a test suite that define what a feature must do, so several vendors can implement it compatibly}}. Products such as GlassFish, Open Liberty, WildFly or Payara become "Jakarta EE compatible" by passing the {{TCK|Technology Compatibility Kit: the official test suite an implementation must pass to claim compatibility}}. Even if you only use Spring, you use Jakarta EE specs every day: `jakarta.persistence`, `jakarta.servlet` and `jakarta.validation` are all Jakarta specifications.

The platform comes in three sizes. The {{Core Profile|the smallest Jakarta EE profile, aimed at microservices and smaller runtimes: CDI Lite, REST, JSON and annotations}}, the **Web Profile** (adds Servlet, Persistence, Security, Faces and more) and the full **Platform**.[^ee12]

#### Why Java starts slowly

When a Java application starts, the JVM loads and links thousands of classes, your framework scans for components and wires them together, and the code runs in the slow {{interpreter|the JVM's mode for running bytecode one instruction at a time, before it has compiled anything}} until the {{JIT compiler|the just-in-time compiler that turns frequently used bytecode into optimised machine code while the program runs}} has seen enough to optimise the hot paths. That last stage is called {{warm-up|the period after startup during which the JVM is still collecting profiles and compiling hot code, so performance is below its peak}}. For a long-running server, a few seconds of startup hardly matters. For a container that scales from zero, or a serverless function, it's the whole problem.

There are three broad ways to attack it, and they're all live in the Java world today:

1. **Do the work ahead of time, at build time.** GraalVM's {{native image|an ahead-of-time compiler that turns a Java application into a standalone native executable that starts almost instantly, with some restrictions on dynamic features}} compiles everything before you ship.
2. **Cache the work from a training run.** {{Project Leyden|the OpenJDK project improving startup and warm-up by shifting work into an AOT cache produced by a training run}} records what a training run loaded, linked (and, from JDK 28, compiled) into a cache file that the next run reuses. We covered its JDK 28 step, JEP 544, in issues #2 and #10.
3. **Snapshot the running process itself.** That's {{CRaC|Coordinated Restore at Checkpoint: an OpenJDK project that saves a running JVM to disk and restores it later, after giving the application a chance to prepare}}.

#### CRaC: save the whole JVM, then come back

CRaC began as an OpenJDK project sponsored by the HotSpot Group. Its goal is to "develop a new standard mechanism-agnostic API to notify Java programs about the checkpoint and restore events".[^openjdkcrac] The idea is simple. You start your application, let it boot (and optionally warm up), then take a {{checkpoint|a snapshot of a running JVM process, including its heap and compiled code, written to disk}}. Later you {{restore|start a new process from a checkpoint instead of running main() from scratch}} from those files and continue as if nothing had happened, already booted and already warm. Introducing the project on foojay.io in 2022, Grunwald credited Azul's Anton Kozlov with the proposal and described the result as cutting startup "from hundreds of seconds to tenths of milliseconds".[^foojay]

On Linux, the snapshot is typically taken with {{CRIU|Checkpoint/Restore In Userspace: a Linux tool that can freeze a running process and save its full state to files}}. You opt in with JVM flags and trigger the snapshot with {{jcmd|the JDK's command-line tool for sending diagnostic commands to a running JVM}}:[^azul]

```bash
# 1. Run normally, but allow checkpoints to be written to ./cr
java -XX:CRaCCheckpointTo=./cr -jar app.jar
# 2. From another terminal, take the checkpoint (the process exits)
jcmd app.jar JDK.checkpoint
# 3. Later, and as many times as you like: restore
java -XX:CRaCRestoreFrom=./cr
```

The "coordinated" part is the clever bit, and the reason a specification is needed. A process image can't contain things that only make sense at the moment it was taken: an open database connection, a listening socket, a file handle, a cached hostname or a random seed. So CRaC gives applications callbacks. You implement the {{Resource interface|org.crac.Resource: two methods, beforeCheckpoint() and afterRestore(), that let code close and reopen external resources around a snapshot}} and register it:[^aws]

```java
// org.crac:crac library; works with a CRaC-enabled JDK
public class Pool implements Resource {
    public Pool() { Core.getGlobalContext().register(this); }

    @Override public void beforeCheckpoint(Context<? extends Resource> c) {
        closeAllConnections();   // nothing external in the image
    }
    @Override public void afterRestore(Context<? extends Resource> c) {
        reconnect();             // fresh connections after restore
    }
}
```

If something is still open when you ask for a checkpoint, the JVM refuses: the foojay introduction notes the implementation "throws exceptions if resources such as open sockets are still open at checkpoint time".[^foojay] The `org.crac` library has a nice escape hatch, too: on a normal JDK it falls back to a dummy implementation, so your app runs normally and only checkpoint requests fail.[^azul]

#### Everybody already does it, differently

That's the problem Jakarta CRaC is trying to solve. Its proposal opens by noting that "many of the Jakarta EE implementations support checkpoint and restore today."[^proposal] Some examples:

- **Open Liberty InstantOn** (IBM) checkpoints a Liberty server using the {{OpenJ9|Eclipse OpenJ9, an alternative JVM originally developed by IBM, used by IBM Semeru runtimes}} JVM and CRIU. Its 2022 announcement reported startup savings "up to 90%", depending on the application, and offered checkpoint points such as `beforeAppStart` and `afterAppStart`.[^instanton]
- **Spring Framework** integrates with Project CRaC: before a checkpoint it stops all running beans through `Lifecycle.stop`, restarts them after restore, and with `-Dspring.context.checkpoint=onRefresh` it can take a checkpoint automatically during startup.[^spring]
- **AWS Lambda SnapStart** for Java uses the same `org.crac` hooks so your function can prepare for its snapshot and clean up after restore.[^aws]
- **Helidon** publishes a CRaC extension: its separate extensions repository has a `crac/27.0.0` release tag.[^helidonext]

Each of these speaks to the JVM through the same low-level `Resource` callbacks, but each defines its own rules for **when** the server takes the snapshot and **how** the application's components are told about it. If you write a Jakarta EE application that holds a {{JMS|Jakarta Messaging (formerly Java Message Service), the standard API for message queues and topics}} connection or a scheduled timer, you currently have to know which server you're on.

### How it works

#### What Jakarta CRaC will specify

The specification page, approved last week, describes two ways of creating a checkpoint:[^cracspec]

- **Automatic checkpoint.** "The checkpoint is taken without user involvement, directly after the application server has been loaded and right before the application is loaded." Later starts restore from that snapshot, "so the server initialization cost is paid only once."
- **Manual checkpoint.** "The user triggers the checkpoint from outside the JVM, for example with `jcmd`." Here the application server "implements the CRaC Resource interface and acts as the single entry point for the JVM."

That second sentence is the key design decision. Instead of every library and every bean registering its own low-level CRaC `Resource`, the **server** registers once. When the JVM calls the server's `beforeCheckpoint()`, the server "informs all of its own critical resources, such as file handles and socket connections, so they can move into a safe state". The spec says this happens "through CDI events and annotations". After a restore, the JVM calls the server's `afterRestore()` and the server notifies the same resources "through the same mechanism".[^cracspec]

{{CDI|Jakarta Contexts and Dependency Injection: the Jakarta EE standard for beans, dependency injection, scopes and events}} events are a natural fit. You already observe lifecycle events in CDI, such as the application scope being initialised or destroyed. Grimstad and Mehmandarov's 2025 Devnexus talk "Duke on CRaC with Jakarta EE" showed exactly that kind of bridge: an `@ApplicationScoped` CDI bean implementing `org.crac.Resource`, alongside CDI's `@Initialized` and `@Destroyed` lifecycle events, with a slide floating Jakarta CRaC as "an idea".[^deck] Eighteen months later, the idea is an approved project.

```viz:layers
title: "Who talks to whom under Jakarta CRaC (as proposed)"
layers:
  - {label: "JVM with CRaC support", sub: "calls beforeCheckpoint / afterRestore"}
  - {label: "Application server", sub: "the single registered CRaC Resource", highlight: true}
  - {label: "CDI events and annotations", sub: "standard notifications, with ordering"}
  - {label: "Your beans and server resources", sub: "close sockets/files, then reopen"}
note: "Based on the Jakarta CRaC 1.0 specification page (jakarta.ee specifications repository, Oct 2026). The exact annotation and event names aren't defined yet."
```

The plan lists six deliverables: define the automatic checkpoint ("when it occurs in the server lifecycle and what state it may contain"); define the manual flow; define the server's obligation to implement the CRaC `Resource` interface and delegate to its own resources; define "the CDI events and annotations used to notify resources before a checkpoint and after a restore, including ordering"; define what happens "when a checkpoint or restore fails or is unavailable"; and provide a TCK.[^cracspec]

Just as important is what it **won't** do. It "does not mandate a particular checkpoint/restore implementation", so CRIU-based CRaC, OpenJ9's approach and future mechanisms can all qualify.[^cracspec] And the proposal states that it "does not seek to replace the existing CRaC API", and aims to work with both CRaC and InstantOn.[^proposal] Like the rest of the next generation of Jakarta specs, it requires **Java SE 21 or higher**.[^cracspec]

#### CRaC versus Leyden: rivals or partners?

If you followed our Leyden coverage, you might wonder why Jakarta EE needs this when the JDK itself is getting faster at starting. The two approaches make different trade-offs, and InfoQ's 2025 comparison lays them out clearly.[^infoq-leyden]

```viz:versus
left:
  emoji: 📸
  title: "CRaC (checkpoint/restore)"
  points:
    - "Snapshots the whole running process"
    - "Restores already booted and warm"
    - "App must close and reopen files and sockets"
    - "Linux only; needs a CRaC-enabled JDK"
    - "Image may hold secrets in clear text"
right:
  emoji: 🗄️
  title: "Leyden AOT cache"
  points:
    - "Caches classes (and, in JDK 28, compiled code)"
    - "Every start still runs main() normally"
    - "No application code changes"
    - "Cross-platform, part of standard OpenJDK"
    - "Smaller gains than a full snapshot"
```

In InfoQ's numbers, the Java 24 AOT cache started Spring PetClinic "up to 40% faster", and Helidon measured 67% and 62% speed-ups for Helidon SE and MP. CRaC, by contrast, gave Helidon 95% and 98%. But CRaC needs applications to close "all files and network connections" before the snapshot, "only runs on Linux", and its snapshot "may pose security risks, as it contains passwords and credentials in clear text".[^infoq-leyden] Spring's own documentation carries the same warning: checkpoint files "may contain secrets and other sensitive data".[^spring]

So they're partners as much as rivals. Leyden is the low-risk default that every app gets almost for free. CRaC is the high-reward option for workloads where startup time is the product, such as scale-to-zero services and serverless functions, and it's exactly the kind of option that benefits from a standard, because getting resource handling right is what makes it safe.

### What it means for you

#### Today: nothing to change, something to watch

Jakarta CRaC 1.0 has no API, no implementation and no release date yet. Its "compatible implementations" section simply says "TBD".[^cracspec] It also isn't on the list of possible new specifications for Jakarta EE 12, which names Jakarta Config, HTTP, MVC, NoSQL and Query.[^ee12] Our reading is that it will start life as a standalone specification that servers can adopt, rather than a required part of the EE 12 platform, but the spec page doesn't say either way.

If you already use checkpoint/restore, the practical advice is the same as before: make your resource handling explicit. Close connections, files and sockets before a checkpoint and reopen them afterwards, avoid caching things that go stale (hostnames, credentials, timestamps) and never ship a checkpoint image somewhere you wouldn't ship your secrets. Spring adds one subtle gotcha: tasks scheduled with `@Scheduled(fixedRate = 5000)` will run every missed execution at once after a restore, so it recommends `fixedDelay` or cron expressions instead.[^spring]

<div class="box realworld" markdown="1">
**🌍 In the real world**

The most common place Java developers meet CRaC today isn't an application server at all, it's **AWS Lambda SnapStart**. SnapStart snapshots your initialised function and restores it later, and your code uses the standard `org.crac` hooks (the docs use `org.crac:crac:1.4.0`), and AWS sets hard limits: restoring plus your `afterRestore()` hooks must finish within 10 seconds, or the invocation fails with a `SnapStartTimeoutException`. The docs also warn that the global context only keeps a weak reference to your `Resource`, so if you don't hold on to it yourself, it can be garbage-collected and its hooks will silently never run.[^aws] That's exactly the kind of sharp edge a server-level standard can hide from application code.
</div>

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Approved doesn't mean available.** Jakarta CRaC is a newly created project with no API, TCK or implementation yet.[^cracspec]
- **Not part of EE 12 (as listed).** It doesn't appear among the EE 12 candidate specifications. Don't plan an EE 12 upgrade around it.[^ee12]
- **CRaC still needs a CRaC-capable JVM and Linux.** A standard at the Jakarta level doesn't change what the JVM underneath has to support.[^azul]<sup>,</sup>[^infoq-leyden]
- **Snapshots contain memory.** Treat checkpoint images like secrets.[^spring]
- **CDI 5.0 renamed its Maven artifact.** If you depend on the CDI API directly, update the coordinates when you move to it.[^cdi5]
</div>
