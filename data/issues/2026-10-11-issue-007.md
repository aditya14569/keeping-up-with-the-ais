# Story 1 · Iceberg 1.12 cleans up after streaming writers

<div class="byline">Apache Iceberg 1.12.0 · Tagged 30 Sep 2026 · Release post 5 Oct · ~20 min read</div>

<p class="opener" markdown="1">Here's an awkward truth about the modern lakehouse: the files at the bottom of it can never be changed. Every "update" or "delete" you run against an Iceberg table is really a note stuck on the side of an immutable file saying "ignore row 4,812" or "ignore anything where id = 42". Streaming writers love the second kind of note because it's cheap to write. Readers hate it because every query has to check it against every row. Iceberg 1.12.0 finally ships a built-in janitor that rewrites the expensive notes into cheap ones while your pipeline keeps running.</p>

### What happened

The Apache Iceberg project released **Iceberg 1.12.0**. The GitHub release tag `apache-iceberg-1.12.0` is dated 30 September, and the release was announced on the dev mailing list on 1 October after the second release candidate passed its vote with 4 binding and 10 non-binding approvals.[^gh]<sup>,</sup>[^digest] The project's own release post followed on **5 October 2026**. It counts **777 commits from 142 contributors** since 1.11.0.[^blog]

The release post groups the changes into a handful of themes:[^blog]

- **Streaming deletes:** a new Flink maintenance task, `ConvertEqualityDeletes`, "resolves the equality deletes produced during streaming ingest into row-position deletion vectors". It needs table format version 3 or later and runs on Flink 1.20, 2.1, 2.2 and 2.3.
- **Variant and geospatial types:** the semi-structured `variant` type gets vectorized Parquet reads in Spark 4.0 and 4.1 and "shredded" writes from Flink, the Kafka Connect sink and the generic writer. The `geometry` and `geography` types can now be read and written in Parquet and Avro, but only Spark 4.1 has an end-to-end path.
- **Data layout:** Hilbert-curve clustering joins Z-order as a way to sort data files in Spark 4.1.
- **REST catalog:** new endpoints (list and load functions, unregister a table), remote-signing configuration, labels, and a spec for "read restrictions" that no reader enforces yet.
- **Format v4 groundwork:** manifest readers and writers for the v4 layout and relative paths in metadata. The post is blunt that "Iceberg 1.12.0 cannot read or write a V4 table".
- **Breaking changes:** Spark 3.4 and Flink 2.0 support are removed, a batch of deprecated APIs is gone, Java writers no longer produce an old style of delete file, and the default AWS SDK HTTP client moves to Apache HttpClient 5.

It also fixes two HIGH-severity `jackson-databind` CVEs (CVE-2026-54512 and CVE-2026-54513).[^blog]

None of these is a single flashy feature. But together they mark the point where Iceberg's v3 format, ratified in 2025, starts to work properly for the messiest workload there is: a stream of upserts landing in a table that analysts are querying at the same time. To see why that's hard, we need to start with how Iceberg deletes anything at all.

### The background you need

#### A table made of files that never change

{{Apache Iceberg|an open table format: a specification for describing a database-style table as a set of data files plus metadata files in object storage, so many engines (Spark, Flink, Trino, Snowflake, Redshift…) can read and write the same table}} doesn't store data itself. Your rows live in ordinary {{Parquet|a columnar file format: values of each column are stored together, compressed, with min/max statistics so readers can skip chunks they don't need}} (or Avro or ORC) files in a bucket. Iceberg adds a tree of metadata on top: a table metadata file points to {{snapshots|immutable versions of the table; every commit creates a new one, which is how Iceberg offers time travel and isolation}}, each snapshot points to a manifest list, and each {{manifest|a metadata file listing a batch of data or delete files along with per-column statistics, so a query planner can skip files without opening them}} lists the files that make up the table at that moment.

The data files are never edited in place. That's a deliberate design choice: object stores like S3 don't support in-place edits anyway, and immutable files make caching, concurrent readers and time travel simple.

The spec describes the format's evolution in one line per version. Version 1 "defines how to manage large analytic tables using immutable file formats". Version 2 "adds row-level updates and deletes for analytic tables with immutable files". Version 3 "extends data types and existing metadata structures to add new capabilities". Version 4 "restructures metadata", but it "is under active development and has not been formally adopted".[^spec]

#### Deleting from an immutable file: two kinds of notes

So how do you delete one row from a 500 MB Parquet file you're not allowed to touch? You have two options.

**Copy-on-write:** rewrite the whole file without that row. Readers stay fast, but a one-row delete costs a 500 MB rewrite.

**Merge-on-read:** leave the data file alone and write a small {{delete file|a separate file that records which rows of the table's data files should be treated as deleted; readers merge it with the data at query time}} next to it. The write is cheap; the reader pays later by applying the deletes as it scans.

Format v2 introduced two flavours of delete file for merge-on-read, and the spec defines them in one sentence each:[^spec]

- **Position deletes** "mark a row deleted by data file path and the row position in the data file". In other words: "in file `a.parquet`, row 4,812 is gone".
- **Equality deletes** "mark a row deleted by one or more column values, like id = 5". In other words: "any row, in any older file, whose `id` is 5 is gone".

These look similar, but they put the cost in completely different places.

To write a position delete, the writer first has to **find** the row: which file is it in, and at what position? For a batch job that just scanned the table, that's free. For a streaming job receiving "customer 42 changed their address" from a {{CDC|change data capture: streaming every insert, update and delete from a source database's log so another system can mirror it}} feed, it's expensive, because the job would need to look up where customer 42 currently lives among thousands of files.

An equality delete skips that lookup entirely. The writer simply records "id = 42 is deleted" and appends the new version of the row to a fresh data file. That's why streaming engines like {{Apache Flink|a distributed stream-processing engine that runs continuous jobs over unbounded data, often used to write CDC streams into lakehouse tables}} use equality deletes for {{upserts|an "update or insert" operation: if a row with this key exists, replace it; otherwise add it}}.

The bill arrives at read time. A reader can't skip anything: it has to compare every row it scans against the set of deleted key values. Alex Merced of Dremio puts it well: equality deletes "convert reads into join-like work".[^merced] And the work accumulates. Every commit can add more delete files, so a table fed by a busy stream gets slower to read with every checkpoint, until someone runs {{compaction|a maintenance job that rewrites many small data and delete files into fewer, larger, clean data files}}.

#### Sequence numbers: which notes apply to which files?

There's one more subtlety. An equality delete for `id = 42` must remove the *old* row with id 42, but not the *new* row the same commit just wrote. Iceberg handles this with {{data sequence numbers|a counter assigned to each file at commit time, increasing with every commit, used to decide which delete files apply to which data files}}.

The spec's scan-planning rules are precise about it. An equality delete applies to a data file only when "the data file's data sequence number is *strictly less than* the delete's data sequence number". A position delete or deletion vector applies when the data file's number is "*less than or equal to*" the delete's, because it names exact positions and so can safely target rows written in the same commit.[^spec2] Equality deletes written with an unpartitioned spec "are applied as global deletes", meaning to every older data file in the table.[^spec2] That last rule is what makes them so expensive: a single equality delete file can force a check against the whole table.

#### What v3 changed: deletion vectors

Position delete files had their own problem. Each commit could add another one, so a single data file could end up with dozens of small delete files pointing at it, all of which a reader had to open and merge.

Format v3, whose ratification Snowflake's engineering blog celebrated in June 2025, replaced them with {{deletion vectors|a compact bitmap, one per data file, in which bit N set means "row N of that file is deleted"}}.[^snowv3] They're stored as {{Roaring bitmaps|a compressed bitmap format that splits the number space into chunks and picks the most compact encoding (array, bitmap or run-length) for each chunk}} inside {{Puffin|Iceberg's sidecar file format for blobs of auxiliary data such as statistics sketches and deletion vectors}} files.[^snowv3]<sup>,</sup>[^d110] Several vectors can share one Puffin file, and a data file has at most one vector per snapshot, so a writer adding deletes must merge them into the existing bitmap.[^merced] The spec reflects this: a newly added vector "must contain all deletes from existing position delete files" for that data file, and manifests must record its exact offset and length within the Puffin file.[^spec2]

The effect is that the read cost per data file stays bounded: one small bitmap, no matter how many commits have deleted rows from it. Iceberg 1.10.0 (September 2025) brought deletion vectors, row lineage, Variant and geospatial types to the Java library.[^d110] Iceberg 1.11.0 followed in May 2026, adding, among other things, Flink support for v3's nanosecond, variant and unknown types.[^g111] Since then the big engines have followed: Snowflake made v3 generally available on 7 May 2026, including deletion vectors, Variant and geospatial types (though external engines can't yet write to Snowflake-managed v3 tables),[^snowga] and Amazon Redshift added v3 support, with deletion vectors, row lineage and default values, on 31 August 2026.[^redshift]

But notice what v3 didn't fix. Deletion vectors replaced *position* deletes. *Equality* deletes are still there in v3, because streaming writers still can't afford to look up row positions. So a Flink upsert pipeline writing to a shiny v3 table was still producing the expensive kind of note.

### How it works

#### The janitor: converting equality deletes into deletion vectors

`ConvertEqualityDeletes` is a task for Iceberg's Flink {{TableMaintenance|Iceberg's framework for running table upkeep (expiring snapshots, compacting files, removing orphans) as part of a long-running Flink job instead of as separate batch jobs}} framework. In the release post's words, it "resolves the equality deletes produced during streaming ingest into row-position deletion vectors". It pairs with Flink's `IcebergSink`, and "the converter resolves those into deletion vectors and commits to the target branch, or converts in place".[^blog] The GitHub changelog shows it arriving as a set of pieces: conversion operators, a planner, a committer and the integration itself.[^gh]

Conceptually, "resolving" an equality delete means doing the lookup the streaming writer skipped. For a delete that says `id = 42`, the converter has to find which older data files contain a row with `id = 42` and at which positions, then set those bits in each file's deletion vector. Once that's committed, the equality delete file is no longer needed, and every subsequent reader gets the cheap, bounded bitmap instead of the join-like key comparison. (This description of the mechanics is our explanation of what "resolving into row-position deletion vectors" has to involve; the release post doesn't spell out the algorithm.)

```viz:flow

```

This is the classic trade-off in log-structured systems, the same one databases make with {{LSM trees|log-structured merge trees: storage engines (RocksDB, Cassandra) that make writes cheap by appending, then pay with background compaction to keep reads fast}}: make the hot path cheap by deferring work, then do that work in the background before it hurts anyone. Before 1.12, Iceberg users had to build that background step themselves, usually with a periodic Spark compaction job that rewrote whole data files. The new task does a lighter job, rewriting deletes rather than data, inside the same Flink deployment that's doing the writing.

The branch option matters more than it looks. Iceberg tables support {{branches|named, independent lines of snapshots within one table, like Git branches, so a writer can commit to a branch and publish it to main later}}. Converting on a branch lets you resolve deletes away from `main` and publish the clean result, rather than having the converter's commits race with the streaming writer's commits on the same branch.[^blog]

#### Variant: JSON that the engine can see inside

The second big theme is the {{Variant|a v3 column type for semi-structured, JSON-like data whose shape can vary from row to row}} type. The spec describes it as a value that "stores semi-structured data", "similar to JSON with a wider set of primitive values".[^spec]

Why not just store JSON as a string? Because to read one field from a JSON string, an engine has to parse the whole thing, row after row. Variant, which Parquet added as a logical type in August 2025, stores two binary fields instead: a `metadata` field holding a dictionary of field names, so a name repeated in every row is stored once, and a `value` field holding the data in a compact binary encoding that lets engines "navigate nested structures and extract only the fields they need". Types survive too: "timestamp values are stored as integers rather than being stored as strings".[^pqblog]

{{Shredding|pulling frequently used fields out of a Variant into their own typed Parquet columns, while keeping the rest as binary}} goes a step further. If most rows have an `event_ts` field that's a timestamp, the writer can store it as a real `int64` timestamp column inside the Variant's Parquet group. Parquet's shredding spec gives exactly this example:[^shred]

```viz:codecompare
title: "A Variant column in Parquet, unshredded vs shredded"
left:
  title: "Unshredded: one opaque blob"
  code: |
    optional group event (VARIANT) {
      required binary metadata;
      required binary value;
    }
    # every query on event_ts
    # decodes the whole value
right:
  title: "Shredded: typed sub-columns"
  code: |
    optional group event (VARIANT) {
      required binary metadata;
      optional binary value;
      optional group typed_value {
        required group event_ts {
          optional binary value;
          optional int64 typed_value
            (TIMESTAMP(true, MICROS));
        }
      }
    }
note: "Right pane simplified from the Parquet Variant Shredding spec; the spec's example also shreds event_type."
```

The payoff, per the spec: a query like `variant_get(event, '$.event_ts', 'timestamp')` reads only the `event_ts` column; statistics on a shredded column can skip files, row groups and pages; and a filter on a shredded field can run first, so the rest of the Variant is loaded only for matching rows.[^shred]

Iceberg 1.12 adds one important rule: "a field is shredded into a typed column only when all of its values fall into a single type family".[^blog] That sounds fussy, but it protects the statistics. Parquet's spec notes that data skipping only works "when `value` is always null", meaning every value actually landed in the typed column,[^shred] and the Iceberg spec says bounds "must not be written to describe values with mixed Variant types (other than null)".[^spec2] Shredding a field whose values are sometimes strings and sometimes numbers would give you a typed column full of holes and no usable min/max statistics.

#### Geospatial, Hilbert curves and v4 groundwork

The `geometry` and `geography` types (stored as {{WKB|Well-Known Binary, the standard binary encoding for points, lines and polygons}}) can now be written and read in Parquet and Avro. But the limits are real: "Support is limited to Spark 4.1 (not Spark 3.5 or 4.0, Flink, or ORC)", reads use the row-based reader, and "there are no spatial predicates yet, so filters are expressed against non-geospatial columns".[^blog] In other words, you can store and round-trip spatial data, but Iceberg won't yet skip files based on a bounding box in your `WHERE` clause.

For data layout, Spark's `rewrite_data_files` procedure can now cluster by a {{Hilbert curve|a space-filling curve that maps multi-dimensional values to one dimension while keeping nearby points close together, so data sorted along it clusters well on several columns at once}}, alongside the existing {{Z-order|another space-filling curve used to sort data by several columns at once; simpler than Hilbert but with more "jumps" between distant regions}}. The release post's example:[^blog]

```sql
CALL system.rewrite_data_files(
  table => 'db.tbl',
  strategy => 'sort',
  sort_order => 'hilbert(c1, c2)'
);
```

Why bother? If your queries filter on two columns, say `lat` and `lon`, or `tenant_id` and `event_date`, a plain sort on the first column leaves the second one scattered. A space-filling curve keeps rows that are close on *both* columns physically close, so the per-file min/max statistics become tight on both, and more files can be skipped. Hilbert curves generally preserve locality better than Z-order; that's the reason to offer both. It ships for Spark 4.1 only.[^blog]

Finally, v4. The 1.12 release includes a v4 manifest reader and writers, an adapter so v4 files can surface through today's `ManifestFile` and `DataFile` interfaces, **relative paths in metadata** (a step towards tables you can move between buckets without rewriting metadata), a content-statistics addition to the spec, and a read-only implementation of the "Mumbling bitmap", a bounded-size compressed bitmap based on Roaring. But again: 1.12.0 "cannot read or write a V4 table".[^blog] Merced notes that v4 discussions aim to retire equality deletes entirely.[^merced] The converter in 1.12 is the practical bridge until then.

### What it means for you

**If you run Flink upsert or CDC pipelines into Iceberg**, this is the release to evaluate. The pattern the community has been recommending, using equality deletes only as a short-lived landing format and resolving them quickly,[^merced] now has a built-in implementation. The catch is that it needs **format v3** tables. Before you move a table to v3, remember that, as the Snowflake and Redshift notes show, not every engine that reads your table supports every v3 feature in the same way yet.[^snowga]<sup>,</sup>[^redshift] Check every reader before you flip `format-version`.

**If you run Spark 3.4 or Flink 2.0**, 1.12 is not for you yet. There's no 1.12 build of `iceberg-spark-runtime-3.4`; supported lines are Spark 3.5, 4.0 and 4.1, and Flink 1.20, 2.1, 2.2 and 2.3.[^blog]<sup>,</sup>[^dremio]

**If you use Kafka Connect's Iceberg sink**, the upgrade fixes something nasty: the sink now "surfaces commit failures instead of swallowing them", "adds bounded retry for transient commit exceptions" and adds "a metric for partial commit failures".[^blog] If you've ever had a connector that looked healthy while silently not committing, this is for you. Dremio also flags that custom transforms using removed members of `TableReference` and `IcebergWriterResult` may stop compiling.[^dremio]

**If you manage the AWS SDK on your own classpath**, you "must switch from `software.amazon.awssdk:apache-client` to `software.amazon.awssdk:apache5-client`".[^blog]

Dremio's upgrade guide has a sensible rule of thumb: "upgrade by table behavior, not by dependency file". Keep three decisions separate: the Java library version, the engine runtime, and the table format version. It suggests upgrading stateless readers first, then low-volume writers, then streaming writers, and maintenance jobs last.[^dremio]

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Old-style position deletes are now read-only.** Java writers no longer create "position delete files with row data" (delete files that also carry a copy of the deleted row). Existing ones stay readable, but `rewrite_position_delete_files` and `rewrite_table_path` reject them. Dremio suggests checking the `position_deletes` metadata table for non-null `row` values before upgrading.[^dremio]
- **Read restrictions are spec-only.** A REST catalog can now return column masks and row filters in `loadTable`, and the contract says a reader "must fail the query rather than return raw, partial, or empty rows". But today such a response "is silently ignored by every consumer".[^blog] Don't rely on it for access control yet.
- **REST path encoding changed** to follow RFC 3986, which can affect proxies or custom catalogs that decode paths differently.[^dremio]
- **Don't enable v4.** It's groundwork only; `format-version=4` is not a supported path.[^dremio]
- **Geospatial is Spark 4.1-only** and has no spatial predicates yet.[^blog]
</div>

### What happens next

Release planning for 1.13 has already started on the dev list, with an early-January target proposed and a volunteer already lined up to manage 1.14.[^digest] Work on v4 continues in the weekly syncs, including file and vector types and a proposal to make Vortex an Iceberg file format.[^digest] For streaming users, the thing to watch is how quickly managed platforms (Snowflake, Redshift, S3 Tables, Databricks' Iceberg support) pick up 1.12's converter or build their own equivalent, and whether v4 really does retire equality deletes.

# Story 2 · Grab's billion-a-day counter, rebuilt around one map per key

<div class="byline">Architecture case study · Grab Counter Service → Aerospike · Grab blog 3 Jul 2026, InfoQ 7 Oct · ~16 min read</div>

<p class="opener" markdown="1">How many times has this card failed a payment in the last fifteen minutes? How many rides has this account requested today? Questions like these sit in the path of almost every transaction at Grab, Southeast Asia's ride-hailing, delivery and payments company, because the answers feed its fraud checks. The service that answers them handles about a billion requests a day. Grab just halved its worst-case latency, and the most interesting part is that the new database wasn't what did it.</p>

### What happened

Grab moved the storage behind its **Counter Service** from a wide-column database to **Aerospike**, redesigned the data model on the way, and migrated live traffic with no downtime. The engineering team (Jia Long Loh, Md Riyadh, Runze Cui and Yuanzhe Liu) described the project on Grab's tech blog on **3 July 2026**,[^grab] and InfoQ brought it to a wider audience on **7 October 2026**.[^infoq]

Counter Service answers time-windowed count queries for Grab's anti-fraud platform, such as recent ride requests by a user or failed payment attempts on a card. It handles "tens of thousands" of queries per second, about a billion requests per day, with strict latency and reliability requirements.[^grab]

Grab reports these results:[^grab]<sup>,</sup>[^infoq]

- Production **p99 read latency down by roughly 50%** across read paths.
- **On-disk data down from about 3 TB to about 1 TB.**
- **Cost per node down by roughly 45–50%.**
- Every counter update became **one atomic operation** instead of a read-modify-write.
- **Replication factor reduced from 3 to 2**, saving about a third of storage and index memory.
- Zero downtime and no data-integrity issues during the migration.

These are Grab's own numbers; InfoQ attributes them to Grab and didn't verify them independently.[^infoq] The team's own conclusion is the most useful line in the post: most of the gains came from the schema redesign, collapsing rows into maps, not from the database swap alone.[^grab]

### The background you need

#### What a counter service does, and why it's hard

A fraud rule might say "block if this card has more than five failed payments in the last hour". To evaluate it, you need a fast, always-up-to-date answer to "how many failed payments in the last hour?". You can't scan an event log at query time with a billion requests a day, so you keep pre-aggregated counts in time buckets: one count per 15 minutes, one per hour, one per day. A one-hour window becomes "add up four 15-minute buckets", and a seven-day window becomes "add up seven daily buckets".

Every new event has to increment the right buckets, and every query has to sum the right ones, quickly, while both happen tens of thousands of times a second.

#### The old design: rows sorted by time

Grab doesn't name the old database. It describes it as a **wide-column database**, with data in three tables (15-minute, hourly and daily), each keyed by a {{partition key|the part of the primary key that decides which node stores a row; all rows with the same partition key live together}} plus a timestamp {{clustering column|a primary-key column that sorts rows within a partition on disk, so a range of them (say, a time window) can be read in one go}}.[^grab] That's the classic Cassandra-style layout: Cassandra's docs describe the partition key as the column by which "the data is divided and stored", and `CLUSTERING ORDER BY` as a way to "order rows storage to make use of the on-disk sorting of columns".[^cass]

It's a perfectly reasonable design for time series. Reading "the last hour for card X" is a range scan within one partition. The problem was the write path. Each counter event triggered a {{read-modify-write|reading a value, changing it in application memory, then writing it back; three steps where other writers can interleave}}: three parallel `SELECT`s (one per granularity), an increment in memory, then a batch write. That's **four network round trips per event**.[^grab]

Read-modify-write has a second cost besides latency. Between the read and the write, another event for the same card can do its own read, and one of the two increments can be lost unless the database or the application adds some form of locking or conditional write. For a fraud counter, an undercount is exactly the wrong failure.

#### Aerospike in five minutes

{{Aerospike|a distributed key-value database designed for predictable low latency at high throughput, typically keeping its index in RAM and its data on SSDs}} is built around a few ideas that matter for this story.

**Records, bins and namespaces.** Data is stored as {{records|Aerospike's unit of storage: a key plus a set of named fields, roughly a row}}, each identified by a key and made up of {{bins|Aerospike's name for the named fields inside a record}}. A bin can hold a scalar or a {{collection data type|a list or map stored inside a single bin, which the server can modify in place with dedicated operations}} such as a map.

**The primary index lives in RAM.** In the default {{Hybrid Memory Architecture|Aerospike's default layout: the primary index in memory, the record data on SSD}}, "the primary index is stored in memory, and data is stored on the SSD".[^hma] Looking up a key is an in-memory tree lookup followed by a read of the record from flash. Under the hood, keys are hashed into "a total of 4096 partitions" spread across the cluster, and each partition's index is a set of in-memory {{red-black trees|self-balancing binary search trees that keep lookups, inserts and deletes logarithmic}} Aerospike calls *sprigs*.[^pidx] Enterprise Edition can also put the index on persistent memory or an NVMe SSD; Community Edition keeps it in process memory.[^pidx] Remember that option; Grab tried it.

**Every record costs index memory, no matter how small it is.** This is the fact the whole redesign turns on. Each record carries a fixed cost of "64 bytes of metadata", including "the 20-byte digest, generation counter, void-time (expiration), last-update time", and the total is "multiplied by the replication factor for the namespace".[^rsize] A record holding a single 8-byte counter still costs 64 bytes of RAM per copy.

To make that concrete with an illustrative number (ours, not Grab's): one billion records at 64 bytes each is 64 GB of index, and at a {{replication factor|how many copies of each record the cluster keeps on different nodes}} of 3 that's 192 GB of RAM across the cluster, before storing a single byte of actual data.

**Many children? Use one record with a map.** Aerospike's own data-modelling guide makes consolidation the default: "store one record per parent entity with a Map or List bin holding the children".[^rsize] It caps record size, though: the namespace `max-record-size` defaults to 1 MiB and can go up to 8 MiB.[^rsize]

### How it works

#### Step 1: the data model, three attempts

Grab's first instinct was to keep the old shape: **one record per time bucket**. The team rejected it, along with a variant that also needed a {{secondary index|an extra index on a non-key field, letting you query by that field at the cost of more memory and write work}}. The reason was the 64-byte index entry. With billions of records, index memory, not disk or CPU, became the constraint.[^grab]

The design they chose (their "approach 3") is **one record per counter per granularity**, holding a {{sorted map|a map whose entries are kept ordered by key, so lookups use binary search and key ranges can be addressed directly}} from bucket timestamp (in milliseconds) to count.[^grab] Aerospike's docs describe a key-ordered map as one where "elements are maintained in key order. Key lookup uses binary search."[^mapops]

Grab says this cut the number of records by more than 10x and reduced disk use, since the long counter key is now stored once per record rather than once per bucket.[^grab]

```viz:codecompare
title: "One card's hourly counts: rows vs one map (illustrative)"
left:
  title: "One record per bucket"
  code: |
    card:X|h|09:00  -> 3
    card:X|h|10:00  -> 1
    card:X|h|11:00  -> 4
    ... one 64 B index entry
        per bucket, per replica
    long key stored every time
right:
  title: "One record, sorted map"
  code: |
    key: card:X|hourly
    bin counts (key-ordered map):
      { 09:00 -> 3,
        10:00 -> 1,
        11:00 -> 4, ... }
    one 64 B index entry
    key stored once
note: "Key formats are invented for illustration. The record-per-counter-per-granularity design and the 64-byte index cost are from Grab and Aerospike's docs."
```

#### Step 2: one atomic write instead of four round trips

With a map per counter, an event becomes a single server-side operation on each affected record. Grab's write combines three things in one atomic call: a **map increment** on the current bucket, **pruning of stale entries by key range**, and a put of the counter key.[^grab]

Aerospike makes that safe because `operate` "executes multiple bin operations atomically and in isolation as a single record command".[^single] The map increment "increments values by `delta-value` for all items identified by `key`", and the range removal deletes "all `{key: value}` pairs where `map.key >= keyStart` and `map.key < keyStop`".[^mapops] Put together, the logic is roughly this (pseudocode, not Grab's code):

```text
operate(key = "card:X|hourly", [
  map_increment(bin = "counts", key = bucket(now), by = 1),
  map_remove_by_key_range(bin = "counts",
                          from = 0, to = now - retention),
  ...  # Grab also writes the counter key
])
```

Two things fall out of this design. The lost-update problem disappears, because the increment happens on the server inside one record-level atomic command, so there's nothing to interleave with. And the map prunes itself on every write, so it never grows without bound. Grab still sets a record-level {{TTL|time to live: an expiry time after which the database deletes a record automatically}}, but only as a safety net for counters that stop receiving writes, because one record now spans many timestamps.[^grab]

#### Step 3: reads, batched per granularity

On the old backend, each sub-query was a prepared statement run concurrently and returning paginated row streams, so one request could make many round trips. On Aerospike, Grab groups the sub-queries by granularity and issues one `BatchOperate` per granularity, so a request makes **at most three round trips**.[^grab] Each read fetches the record and sums the map entries in the requested window on the client side; InfoQ points out that this replaces the server-side range filtering the wide-column store used to do.[^infoq]

There's a trade here too. The old backend streamed rows; Aerospike's batch either succeeds or fails as a unit, and there's no streaming.[^grab] For counters that's fine, because each record is small. It would matter more if a map grew towards the 1 MiB record limit.

#### Step 4: migrating a live fraud system without a gap

You can't take the fraud platform offline for a weekend. Grab's requirements were a gradual traffic ramp with rollback through a configuration change, monitoring of both storage paths to verify data before switching, and zero downtime.[^grab]

The service is written in Rust, and the team prepared it in three stages.[^grab]

1. **Isolate the driver.** All storage code moved behind a `LegacyStorage` wrapper, so business logic no longer imported the database driver directly. No behaviour changed.
2. **Add a facade with modes.** A storage facade dispatches over Legacy, Aerospike and Mock backends. Grab used Rust {{enum dispatch|choosing an implementation with a `match` on an enum value, which the compiler can inline, instead of calling through a trait object on the heap}} rather than trait objects, to avoid a heap allocation per query. Configuration picks one of three modes: **Single** (one backend serves), **WithShadow** (the primary serves responses while the secondary runs asynchronously for parity checks) and **WithSplit** (a deterministic percentage of live traffic goes to each backend).
3. **Tag the metrics.** Every metric was tagged by backend, role and mode, so existing dashboards kept working and could compare the two paths side by side. Shadow calls were fire-and-forget, so a slow Aerospike couldn't slow down real responses.

{{Shadow traffic|sending a copy of real requests to a new system without using its answers, so you can compare results and performance under production load}} is what made the cutover low-risk. The example ramp in the post goes from shadow reads at 5% → 20% → 50% → 100%, then live split traffic at 5% → 30% → 70% → 100%, then Aerospike only.[^grab] On the write side, the old backend stayed primary while Aerospike received asynchronous shadow writes under the same deterministic rollout logic.[^grab]

#### The experiment that didn't work: index on NVMe

Remember that Enterprise Edition can store the primary index on an NVMe SSD instead of RAM.[^pidx] Grab tried it to raise the memory ceiling. It caused p99 spikes that tracked I/O on **hot keys** rather than overall request rate, and adding nodes didn't help. The team went back to an in-memory index on memory-optimised instances.[^grab]

That result makes sense once you think about what a {{hot key|a single key that receives a disproportionate share of traffic, such as a very active account}} does. Adding nodes spreads *different* keys across more machines, but every request for one hot key still lands on the same partition and, with the index on disk, the same device. With the index in RAM, the hot key's index lookup is a memory access; on NVMe, it competes for the same device queue as everything else. The post's lesson: hot-key I/O can dominate latency when the index is on disk.[^grab]

Today the primary index uses about 50 GB of roughly 100 GB usable memory per node, which is the headroom the map redesign bought back.[^grab]

#### Two client-library surprises

The first Aerospike Rust client Grab used was synchronous, so calls were wrapped with `spawn_blocking` to keep them off the async runtime's worker threads. When the official async client shipped, they removed the bridge and saw p50 and p99 improve.[^grab]

The second was subtler: the client resolved seed hostnames only once, at start-up. After a staging cluster was replaced with new IP addresses, the service kept trying the old IPs until it was restarted. Grab reported it upstream, a later client release fixed it, and the team now reproduces the scenario in a Docker-based end-to-end test and in staging drills.[^grab] It's a reminder to test infrastructure replacement, not just node failure, before you depend on a new client library.

### What it means for you

**Design for the per-record cost of your database.** In Aerospike, every record costs 64 bytes of RAM per replica.[^rsize] Grab's lesson generalises to any store with a fixed cost per key: when a database charges you per key, shaping the data so you have fewer, fuller keys can matter more than which engine you pick. Aerospike's own docs default to consolidation for exactly this reason, while warning against letting a single record grow too large.[^rsize]

**Push read-modify-write to the server.** If your counter, rate limiter or quota service reads a value, changes it in application code and writes it back, look for a server-side atomic operation instead (Aerospike map increments, Redis `INCRBY`/`HINCRBY`, Cassandra counters, DynamoDB `UpdateItem` with `ADD`). It's usually both faster and more correct.

**Copy the migration pattern even if you never touch Aerospike.** A storage facade with Single, Shadow and Split modes, metrics tagged by backend and role, and ramps controlled by configuration is a reusable template for any storage swap.[^grab]

**Know which risk you're accepting when you cut replicas.** Going from three copies to two saved a third of storage and index memory, and Grab explicitly accepts the risk of a simultaneous multi-zone failure because the counts can be rebuilt from the event stream.[^grab] That justification only holds if you really have a durable source to rebuild from.

<div class="box realworld" markdown="1">
**🌍 In the real world**

Daniel Lim, an engineering leader at Grab, summed up the approach as "combining dual read-write paths for traffic shadowing and data parity validation with gradual traffic migration".[^infoq] The other number worth remembering is the one Grab chose *not* to chase: putting the index on NVMe would have raised the memory ceiling, but it made tail latency depend on hot keys, so they bought memory-optimised instances instead.[^grab]

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **These are Grab's numbers.** The 50% p99, 3 TB → 1 TB and 45–50% cost figures come from Grab's post; InfoQ didn't verify them independently, and the post doesn't name the old database or give its configuration.[^grab]<sup>,</sup>[^infoq]
- **Maps move filtering to the client.** The wide-column store filtered by time range on the server; with maps, the whole record comes back and the client sums the window.[^infoq] That's cheap for small maps and expensive for large ones.
- **Record size limits are real.** `max-record-size` defaults to 1 MiB (ceiling 8 MiB), and writes over the limit fail.[^rsize] Pruning on every write is what keeps Grab's maps small.
- **Index-on-flash is not free memory.** It can tie tail latency to hot-key I/O, as Grab found.[^grab]
</div>

**📖 Words from this story**

- **Partition key**: the part of the primary key that decides which node stores a row.
- **Clustering column**: a primary-key column that sorts rows within a partition on disk.
- **Read-modify-write**: read a value, change it in the app, write it back; other writers can interleave.
- **Aerospike**: a distributed key-value database with its index in RAM and data on SSD by default.
- **Record**: Aerospike's unit of storage, a key plus named fields.
- **Bin**: a named field inside an Aerospike record.
- **Collection data type**: a list or map inside one bin that the server can modify in place.
- **Hybrid Memory Architecture**: Aerospike's default layout, index in memory and data on SSD.
- **Red-black tree**: a self-balancing binary search tree.
- **Replication factor**: how many copies of each record the cluster keeps.
- **Secondary index**: an extra index on a non-key field.
- **Sorted map**: a map kept in key order, so lookups and key ranges are efficient.
- **TTL (time to live)**: an expiry time after which a record is deleted automatically.
- **Enum dispatch**: choosing an implementation via a `match` on an enum instead of a heap-allocated trait object.
- **Shadow traffic**: copying real requests to a new system without using its answers, to compare.
- **Hot key**: one key receiving a disproportionate share of traffic.
