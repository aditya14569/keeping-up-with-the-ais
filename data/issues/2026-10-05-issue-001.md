# Story 1 · PostgreSQL 19: the release that got smaller on purpose

<div class="byline">PostgreSQL 19 · Beta 4 on 24 Sep 2026 · RC due early October · ~18 min read</div>

<p class="opener" markdown="1">In June, the PostgreSQL 19 Beta 1 announcement promised graph queries written in standard SQL, the ability to switch on data checksums without a restart, and `UPDATE ... FOR PORTION OF` for time-ranged data. On 24 September, Beta 4 shipped without any of them. Nothing broke in production and nobody shipped a buggy release. The project read its own bug tracker, decided those features weren't ready, and took them out. That decision tells you a lot about why people trust Postgres with their data. And what survived is still a release worth planning for.</p>

### What happened

PostgreSQL 19 Beta 4 came out on **24 September 2026**. Its announcement lists features that were **reverted**, meaning their code was removed from the release branch: SQL/PGQ property graph queries, online enabling and disabling of data checksums, temporal `UPDATE`/`DELETE ... FOR PORTION OF`, `ALTER TABLE ... MERGE PARTITIONS` and `SPLIT PARTITIONS`, and three functions that generate DDL (`pg_get_role_ddl()`, `pg_get_tablespace_ddl()` and `pg_get_database_ddl()`).[^b4]

The project explained the cuts plainly: Postgres "must be reliable", so the community removed some features from 19 "so they can be potentially be included in a later major release after more time working through the community development and review process."[^b4]

On timing, Beta 4 says the next release is the release candidate, which "should occur in early October", and that GA "may also occur in October".[^b4] The project roadmap lists PostgreSQL 19 as "planned for October 2026".[^roadmap] The draft release notes still show the release date as `2026-??-??`.[^rn]

That makes 19 a little later than usual. PostgreSQL 18 shipped on 25 September 2025, three weeks after its first release candidate.[^rc18]<sup>,</sup>[^versioning] But October isn't unheard of: PostgreSQL 15 came out on 13 October 2022.[^versioning]

### The background you need

**How a Postgres release is made.** The PostgreSQL Global Development Group ships one {{major version|a release with new features that can change on-disk formats, so upgrading needs `pg_upgrade` or a dump and restore}} about once a year, and supports each one for **five years** with {{minor releases|bug- and security-fix releases such as 18.6 that you can install by just swapping binaries}} at least every three months.[^versioning] New features land in the development branch all year. After the feature freeze, the branch goes through public **betas**, then a **release candidate (RC)** that's meant to be identical to the final release unless a bug turns up, and then **general availability (GA)**.

The betas exist so that people outside the core team can find bugs before the features reach production. When a feature keeps needing fixes after it has been committed, the community can **revert** it: undo its commits and try again in a later release. That's what happened in 19, on an unusual scale.

**How the cuts happened.** On 25 August, core developer Robert Haas asked on the `pgsql-hackers` mailing list whether six heavily patched features should be removed before 19 shipped.[^cp2] Over the next three weeks, committers removed them one by one:

```viz:timeline

  - {date: "27 Aug", label: "MERGE/SPLIT PARTITIONS out (14 commits)"}
  - {date: "7 Sep", label: "SQL/PGQ reverted (47 commits)"}
  - {date: "10–13 Sep", label: "Casefolding, CREATE SCHEMA, DDL functions"}
  - {date: "15 Sep", label: "FOR PORTION OF reverted (23 commits)"}
  - {date: "16 Sep", label: "Online checksums reverted"}
  - {date: "24 Sep", label: "Beta 4 ships without them", highlight: true}
note: "Dates, commit counts and committers from Command Prompt's reports ([1](https://www.commandprompt.com/blog/two-features-just-left-postgresql-19/), [2](https://www.commandprompt.com/blog/postgresql-19-sept-08-sept-16-2026/)) and the [Beta 4 announcement](https://www.postgresql.org/about/news/postgresql-19-beta-4-released-3386/)."
```

The reasons were concrete. SQL/PGQ and the partition commands had "multiple design issues which are too late to address in this release cycle".[^cp2] Online checksums had "a number of postcommit fixes", which raised the risk that more bugs would surface after release.[^cp6] Two `CREATE SCHEMA` changes were dropped because the "compatibility breakage" outweighed the gain, and a change to how identifiers are case-folded caused an "unintended behaviour difference" with some locales.[^cp6]

**What the pulled features were.** These are worth knowing, because several will probably come back in PostgreSQL 20:

- **SQL/PGQ** is the SQL standard's syntax for {{property graph queries|queries that treat rows as nodes and relationships as edges, so "friends of friends who bought X" becomes a path pattern instead of a chain of self-joins}}. It would have let you query relational tables as a graph without a separate graph database.
- **Online data checksums.** A {{data checksum|a small fingerprint Postgres stores in each data page and verifies on read, so silent disk corruption shows up as an error instead of wrong data}} catches storage corruption. Since PostgreSQL 18, `initdb` enables checksums by default for new clusters.[^crunchy] Older clusters don't have them, and turning them on means running the `pg_checksums` tool with the server stopped. That means downtime and a restart, which is painful for big databases.[^crunchy] There's a second snag: `pg_upgrade` requires the old and new clusters to have the **same** checksum setting.[^crunchy] The online feature would have removed that downtime. For now, the usual workaround remains: enable checksums on a replica and fail over to it.[^crunchy]
- **Temporal `FOR PORTION OF`** would have let you update or delete only part of a row's validity period (for example, "this price applies from 1 to 15 March") and have Postgres split the row for you.
- **`MERGE`/`SPLIT PARTITIONS`** would have combined or divided partitions of a {{partitioned table|one logical table stored as several physical child tables, each holding a range or list of keys}} with one `ALTER TABLE` command.

### How it works: what's still in PostgreSQL 19

The official release notes list six headline features.[^rn] Here are the ones you're most likely to use, and how they work.

#### 1. REPACK: VACUUM FULL and CLUSTER, renamed and made concurrent

Postgres uses {{MVCC|multi-version concurrency control: an UPDATE writes a new row version and leaves the old one in place for transactions that may still need to see it}}. Old versions become {{dead tuples|row versions no transaction can see any more}}. Regular `VACUUM` marks their space reusable but rarely shrinks the file, so a table that once held a lot of data can stay large on disk. That extra space is called {{bloat|disk space a table or index occupies beyond what its live rows need}}.

Until now there were two tools for rewriting a table compactly: `VACUUM FULL` and `CLUSTER` (which also sorts rows by an index). Both take an {{ACCESS EXCLUSIVE lock|the strongest table lock in Postgres: it blocks every other read and write on the table until it's released}} for the whole rewrite, so on a big table they mean downtime.

PostgreSQL 19 merges both into one command, `REPACK`. The commit message says this functionality is "completely different from regular VACUUM", so giving it its own name should make it easier to understand.[^dbi] The old commands remain for compatibility.[^rn]

```sql
-- Rewrite one table compactly, without blocking reads and writes for most of the run
REPACK (CONCURRENTLY, VERBOSE) orders;

-- Rewrite and physically order rows by an index (what CLUSTER did)
REPACK orders USING INDEX orders_created_at_idx;
```

Plain `REPACK` still takes an ACCESS EXCLUSIVE lock for the whole run. The interesting part is `CONCURRENTLY`. It builds the new copy of the table while your application keeps writing to the old one. It captures those concurrent changes with {{logical decoding|reading the write-ahead log and turning it back into row-level changes (insert this row, update that one), the same machinery logical replication uses}}, replays them onto the new copy, and only takes the exclusive lock for the final swap.[^repack]

```viz:flow

```

The catch-up step is why there are limits. `CONCURRENTLY` needs a free {{replication slot|a bookmark in the WAL that stops Postgres from deleting log segments a consumer hasn't read yet}} (the new `max_repack_replication_slots` setting controls how many are available).[^rn] It doesn't work on tables without a primary key, on unlogged or partitioned tables, on materialized views or on system catalogs, and not inside a transaction block. It can fail if someone runs DDL on the table mid-run. The docs also warn that it is "not MVCC-safe".[^repack] In practice, that means a long-running transaction that started before the repack may see the table differently afterwards. Run it when no long-running transactions are using that table.

Plan your disk space too. A rewrite needs free space roughly equal to the table plus its indexes, and about double the table size if it sorts.[^repack]

#### 2. WAIT FOR LSN: read your own writes on a replica

The classic replica bug goes like this. A user saves their profile (a write to the primary), the page reloads, and the read goes to a {{read replica|a standby server that replays the primary's write-ahead log and serves read-only queries}} that hasn't replayed the change yet. The user sees their old data and clicks Save again.

Every change in Postgres has an address in the {{write-ahead log (WAL)|the append-only log where Postgres records every change before touching data files; replicas stay in sync by replaying it}}, called the {{LSN|log sequence number: a byte position in the WAL that only ever increases, so "LSN ≥ X" means "has seen everything up to X"}}. PostgreSQL 19 adds a command that blocks until a standby has reached a given LSN.[^waitfor]

```sql
-- 1. On the primary, after COMMIT, on the same connection:
SELECT pg_current_wal_insert_lsn();   -- e.g. 0/306EE20

-- 2. On the replica, before reading:
WAIT FOR LSN '0/306EE20' WITH (TIMEOUT '100ms', NO_THROW);
SELECT * FROM profiles WHERE user_id = 42;
```

```viz:flow
      style: accent
    - label: SELECT

note: "Pattern from the [WAIT FOR docs](https://postgresql.org/docs/19/sql-wait-for.html) and [rednafi.com](https://rednafi.com/system/pg-wait-for-lsn/)."
```

The command returns `success`, `timeout` or `not in recovery` (if the server is not a standby, or was promoted while waiting). With `NO_THROW` it returns that status instead of raising an error.[^waitfor] The default `MODE` is `standby_replay`, which waits until the change is applied and visible. There are also `standby_write`, `standby_flush` and `primary_flush` modes.[^waitfor]

Two practical rules. First, read the LSN **after** you commit. If you capture it while the transaction is still open, your commit lands at a higher LSN and the wait can return too early.[^rednafi] Second, `WAIT FOR` must be a top-level command: not inside a function or a `DO` block, not while holding a snapshot, and not at isolation levels above READ COMMITTED.[^waitfor]

#### 3. pg_plan_advice: query hints, finally (sort of)

Core Postgres has never had {{query hints|instructions embedded with a query that tell the planner which join order or index to use, instead of letting it decide from statistics}}. PostgreSQL 19 ships a contrib extension, `pg_plan_advice`, that lets you "stabilize and control" the planner's decisions, plus a companion `pg_stash_advice` that applies saved advice automatically based on the query.[^rn]

The neat part is that it can tell you what the planner already chose, in a small language you can feed back to it:[^advice]

```sql
LOAD 'pg_plan_advice';
EXPLAIN (COSTS OFF, PLAN_ADVICE)
  SELECT * FROM join_fact f JOIN join_dim d ON f.dim_id = d.id;
-- ...plan...
-- Generated Plan Advice:
--   JOIN_ORDER(f d)  HASH_JOIN(d)  SEQ_SCAN(f d)  NO_GATHER(f d)

SET pg_plan_advice.advice = 'JOIN_ORDER(f d)';
```

`EXPLAIN` then reports each piece of advice as `matched`, `partially matched`, `not matched`, `inapplicable`, `conflicting` or `failed`.[^advice] The documentation is frank about the risks. Advice stops the planner from adapting when your data changes. It can only choose among plans the planner already considers viable. And bad advice can produce plans marked `Disabled: true` that are worse than no advice at all.[^advice] Treat it as a way to pin a known-good plan for a query that keeps regressing, not as a tuning tool for everyday use.

#### 4. Smarter autovacuum

{{Autovacuum|the background process that runs VACUUM and ANALYZE on tables automatically when enough rows have changed}} gets two upgrades. It can now use parallel workers to vacuum a table's indexes (`autovacuum_max_parallel_workers`, plus a per-table `autovacuum_parallel_workers`). And a new **scoring system** decides which tables to process first, with weights you can tune (`autovacuum_vacuum_score_weight`, `autovacuum_freeze_score_weight` and others). A new view, `pg_stat_autovacuum_scores`, shows each table's score.[^rn]

Why does order matter? The release notes say the goal is to prioritise "the tables that most need vacuuming or analyzing".[^rn] On a database with many tables, that means a table that urgently needs {{freezing|VACUUM rewriting old transaction IDs in a table as "frozen", which has to happen before the transaction counter wraps around}} no longer has to wait its turn behind tables that only need routine cleanup. The separate freeze and multixact-freeze weights let you tune exactly that.

#### 5. Logical replication without the restart

{{Logical replication|copying row-level changes (rather than raw WAL bytes) to another server, often for zero-downtime upgrades or feeding other systems}} gets two long-requested features:[^rn]

- **Sequences are replicated** (`CREATE PUBLICATION ... ALL SEQUENCES`, `ALTER SUBSCRIPTION ... REFRESH SEQUENCES`). Until now, sequence values weren't carried over, so after a logical-replication cutover you had to sync them yourself before the new server could safely take inserts.
- **No restart to turn it on.** If `wal_level` is `replica`, logical replication can now be enabled without a server restart. A new read-only setting, `effective_wal_level`, reports the level actually in effect.

#### 6. Performance work you get for free

The release notes list automatic scaling of the I/O worker pool for {{asynchronous I/O|letting Postgres issue many disk reads at once and keep working while they complete, instead of waiting for each one}} (`io_min_workers`, `io_max_workers`, `io_worker_idle_timeout`, `io_worker_launch_interval`), faster foreign-key checks, and regular table scans that can now mark pages all-visible in the {{visibility map|a per-table bitmap recording which pages contain only rows visible to everyone, which makes index-only scans and VACUUM cheaper}} (before, only `VACUUM` and `COPY ... FREEZE` could).[^rn] For the foreign-key work, the Beta 1 announcement claimed "2x better performance on inserts when foreign key checks are present". That's the project's own number, so measure it on your own workload.[^beta1]

### What it means for you

**New defaults you might not notice.** These quietly change behaviour on upgrade. All of them are from the official "Migration to Version 19" section.[^rn]

```viz:codecompare

left:
  title: "PostgreSQL 18"
  code: |
    jit = on
    default_toast_compression = pglz
    log_lock_waits = off
    max_locks_per_transaction = 64
    standard_conforming_strings
      can be set to off
    RADIUS authentication available
right:
  title: "PostgreSQL 19"
  code: |
    jit = off
    default_toast_compression = lz4
    log_lock_waits = on
    max_locks_per_transaction = 128
    standard_conforming_strings
      is always on
    RADIUS removed
note: "From the [PostgreSQL 19 release notes](https://www.postgresql.org/docs/19/release-19.html). Lock-table sizing also changed, so 128 in 19 holds about what 64 held before."
```

A few of these need a decision:

- **{{JIT|just-in-time compilation: turning parts of a query's expressions into machine code at run time, which can help long analytical queries but adds start-up cost}} is now off by default.** The release notes single out sites running many large analytical queries: they must now turn it back on themselves with the `jit` parameter. If that's you, test with `jit = on` and decide.[^rn]
- **{{TOAST|how Postgres stores large values (long text, big JSON) out of line, compressed and split into chunks}} now uses LZ4.** The project says LZ4 provides "better default compression and decompression performance".[^beta1]<sup>,</sup>[^rn]
- **`max_locks_per_transaction` doubled from 64 to 128**, but the notes say lock-table sizing changed, so values "must now be doubled to match their previous capacity". If you had set it to 256, set it to 512 in 19.[^rn]
- **`standard_conforming_strings` can no longer be turned off.** Dumps made by an older `pg_dump` with it off won't load correctly into 19. Take dumps with the 19 `pg_dump`.[^rn]
- **`pg_upgrade` blockers:** clusters with `btree_gist` indexes on `inet`/`cidr` columns (those operator classes could silently skip matching rows), and databases, roles or tablespaces whose names contain carriage returns or line feeds, will refuse to upgrade until you fix them.[^rn]
- **MD5 passwords now trigger a warning** after a successful login (they were deprecated in 18), and there's a new password-expiry warning, 7 days ahead by default.[^rn]

**What to do this month.** If you run Postgres 14, its final release is on **12 November 2026**, so you need an upgrade plan anyway.[^versioning] Whether to jump straight to 19 or go to 18 first is mostly a question of how soon your cloud provider offers 19 and how much testing time you have. Either way, run your test suite against Beta 4 or the RC now, check for the `pg_upgrade` blockers above, and review JIT if you run analytics.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Blog posts written before September are out of date.** Many "What's new in Postgres 19" articles still show SQL/PGQ, `FOR PORTION OF` and online checksums. None of them is in 19.[^b4]
- **`REPACK CONCURRENTLY` is not a drop-in for every table.** It needs a primary key, a free replication slot and enough disk space, and it is not MVCC-safe.[^repack]
- **`WAIT FOR LSN` only compares numbers.** It "has no notion of which timeline" a WAL record belongs to, so after a failover an LSN taken on the old primary may not mean what you think.[^waitfor]
- **Betas aren't upgradable in place.** Going from a beta to the final release needs `pg_upgrade` or a dump and restore, like any major upgrade.[^b4]
</div>

### What happens next

The RC is due in early October and GA "may" follow in October.[^b4] The next scheduled minor release, on **12 November**, will be PostgreSQL 14's last.[^roadmap]<sup>,</sup>[^versioning] The reverted features are now candidates for PostgreSQL 20, but nothing about them is promised yet. The bigger lesson is cultural: a database whose community will delete 47 commits of a headline feature three weeks before release is one that values your data over its own press release.

# Story 2 · MongoDB 9.0: faster, stricter, and null means something new

<div class="byline">MongoDB 9.0 · GA, announced 29 Sep 2026 · ~14 min read</div>

<p class="opener" markdown="1">Picture a query that has run in your app for years: find orders where `items.discount` is `null`. You upgrade from MongoDB 8.0 to 9.0, change nothing, and the same query now returns more documents than it did yesterday. You haven't hit a bug. MongoDB 9.0 deliberately redefined what `null` means when a dotted path runs into an array. It's one line in the compatibility notes, sitting under a launch that headlined "up to 2x throughput". This story covers both: what's actually new in 9.0, and the small print to read before you upgrade.</p>

### What happened

MongoDB announced 9.0 on **29 September 2026** at an event at Nasdaq MarketSite in New York, alongside a public preview of a new Atlas architecture called **Atlas Infinite**.[^mpr] The release notes list **9.0.0, 9.0.1 and 9.0.2 all dated 28 September**. 9.0.1 includes a fix for **CVE-2026-89099**, and **9.0.3 is "upcoming"**, with a fix for a known sharding hang described below.[^mrn]

MongoDB calls it "the best version of MongoDB ever built".[^mupd] Its own benchmarks, compared with MongoDB 8.0, claim up to **35% faster** find-one queries, up to **30% faster** update-one queries, up to **2x throughput on large instances** and up to **20% more throughput** for transactional workloads.[^mpr] These are vendor numbers from "internal testing with public benchmarks", not independent results.[^mupd]

9.0 is available on Atlas (MongoDB's managed cloud service), in Enterprise Advanced and in the free Community Edition. Like every major version, it gets five years of support.[^mupd]<sup>,</sup>[^mver]

### The background you need

**Major, minor and now "Feature Update" releases.** MongoDB changed its release model with this version, so here is a quick recap.

MongoDB ships {{major releases|an X.0 version with new features and possibly backward-incompatible changes, supported for five years}}, with {{minor releases|interim X.Y versions such as 8.1, 8.2 and 8.3 that deliver new features between majors}} in between. Starting with 8.2, self-managed users could also run the minor releases.[^mver] **9.0 changes the model again.** From now on, minor releases go **only to Atlas clusters on Auto Upgrade**. Self-managed users get one annual **Feature Update** release, numbered **x.5** (so 9.5 would be the next one).[^mver] If you run MongoDB yourself, you'll see new features less often.

**FCV, the safety catch on upgrades.** MongoDB separates "running the new binaries" from "using features that change data on disk". The second is controlled by the {{feature compatibility version (FCV)|a cluster-wide setting that keeps new on-disk formats and features switched off, so you can still downgrade, until you raise it}}. You can only upgrade to 9.0 from **8.0 or 8.3**, with FCV set to `"8.0"`. If you're on 7.0, you have to go to 8.0 first. The upgrade is a rolling one: upgrade the secondaries one at a time, step down the primary, upgrade it, and only then run `setFeatureCompatibilityVersion: "9.0"`.[^mupg] MongoDB recommends a "burn-in period" before raising FCV, because once you raise it, downgrading means first removing any 9.0-only features you've used.[^mupg]

```js
// Only after every member runs 9.0 binaries and you've watched it for a while:
db.adminCommand({ setFeatureCompatibilityVersion: "9.0", confirm: true })
```

### How it works: the six changes that matter

#### 1. `null` on dotted paths now follows a simpler rule

In MongoDB, a {{dotted path|a field reference such as "a.b" that reaches into embedded documents, and automatically into every element when it meets an array}} like `"a.b"` walks into arrays implicitly. The awkward question has always been what `{"a.b": null}` should match when `a` is an empty array, or an array of plain numbers with no `b` anywhere.

9.0's answer is simple: "a dotted path that does not resolve to a non-null value evaluates as `null`."[^mrn] Here's the official example, before and after:[^mcompat]

```viz:codecompare
title: "Same data, same query, different answer"
left:
  title: "MongoDB 8.3 and earlier"
  code: |
    { _id: 1, a: [ 1 ] }
    { _id: 2, a: [ ] }

    find({ "a.b": null })
      → neither document
    find({ "a.b": { $ne: null } })
      → both documents
right:
  title: "MongoDB 9.0"
  code: |
    { _id: 1, a: [ 1 ] }
    { _id: 2, a: [ ] }

    find({ "a.b": null })
      → both documents
    find({ "a.b": { $ne: null } })
      → neither document
note: "From the [9.0 compatibility notes](https://www.mongodb.com/docs/manual/release-notes/9.0-compatibility/). Nested arrays such as a: [[{b: 3}]] change the same way."
```

The change affects `$eq`, `$ne`, `$in`, `$nin`, `$gte`, `$lte` and equality matching in `$lookup`. MongoDB's summary: after the upgrade, `{ $ne: null }` queries "return fewer documents" and `{ $eq: null }` queries "return more documents" when the path crosses an empty array, an array of scalars or a nested array.[^mcompat]

The new rule is easier to reason about. But the most common place you'll find `$ne: null` is an "only documents that have this field" filter, perhaps in a `$lookup` join or a report. Grep your code for `null` comparisons on dotted paths before you raise FCV.

#### 2. Server-side JavaScript is back, in a sandbox

`$where`, `$function` and `$accumulator` let you run JavaScript inside the database. They had been deprecated. In 9.0 they're **no longer deprecated**, because MongoDB rebuilt them on a new JavaScript engine based on {{WebAssembly (WASM)|a portable, sandboxed bytecode format; code inside it can only touch the memory and functions the host explicitly gives it}}. MongoDB says this gives "stronger sandboxing and isolation than prior versions".[^mrn]

There's a behaviour change hiding in this one. The new engine evaluates local `Date` operations **in UTC**, whatever the server's time zone. On a server set to New York time, `date.getHours()` for 13:30 UTC used to return `8`. In 9.0 it returns `13`.[^mcompat] The fix MongoDB recommends is to stop depending on the host's time zone and use aggregation operators with an explicit zone, such as `{ $hour: { date: "$occurredAt", timezone: "America/New_York" } }`.[^mcompat] And on `ppc64le` (IBM Power) servers, there's no JavaScript engine at all in 9.0. Those operations, and `mapReduce`, simply fail there.[^mcompat]

#### 3. Guardrails: memory caps, transaction caps and overload control

The theme of 9.0 is **protecting the cluster from its own workload**. MongoDB pitches this for AI agents with "spiky, unpredictable traffic", but it helps any app that has one bad query.[^mpr] There are three layers:

```viz:layers
title: "Three layers of protection in MongoDB 9.0"
layers:
  - {label: "Ingress queue (Atlas only)", sub: "throttle new operations under overload", highlight: true}
  - {label: "Transaction cap", sub: "max 10,000 open multi-doc transactions"}
  - {label: "Per-operation memory cap", sub: "1 GB or 20% of RAM, whichever is larger"}
  - {label: "Per-stage memory cap", sub: "100 MB per stage, then spill to disk"}
note: "From the [9.0 release notes](https://www.mongodb.com/docs/manual/release-notes/9.0/), [aggregation limits](https://www.mongodb.com/docs/upcoming/core/aggregation-pipeline-limits/) and [Intelligent Workload Management](https://www.mongodb.com/docs/atlas/intelligent-workload-management/) docs."
```

**Per-operation memory limit.** Aggregation stages have a **100 MB per-stage** memory limit. Past it, a stage either {{spills to disk|writes intermediate data to temporary files instead of holding it in RAM; slower, but it finishes}} (with `allowDiskUse`) or fails. 9.0 adds a cap on the **whole operation**: by default "1 gigabyte or 20% of the memory available to the server process, whichever is greater". An operation that exceeds it is ended with `QueryExceededMemoryLimitNoDiskUseAllowed` (if a stage could have spilled but `allowDiskUse` is false) or `ExceededMemoryLimit`.[^magg] A new `serverStatus` counter, `metrics.query.operationsFailedDueToMemoryLimit`, tells you whether it's happening.[^mrn] In plain terms: a pipeline with many medium-sized stages, each under 100 MB but together using several gigabytes, used to finish. Now it can be killed.

**Transaction cap.** The server now limits concurrently open {{multi-document transactions|transactions that read or write several documents atomically, like a SQL transaction}} from external clients. The `maxConcurrentMultiDocumentTransactions` parameter defaults to **10,000**, and new transactions beyond that get a `TooManyOpenTransactions` error.[^mrn] Most apps never get close. An app that leaks open transactions will now find out quickly.

**Intelligent Workload Management (IWM)** is **Atlas-only** and active on dedicated clusters running 9.0.[^miwm] Its core idea is {{admission control|deciding how fast to let new work start, so running work isn't starved by a flood of new requests}}. Each `mongod` runs an ingress rate limiter. When traffic exceeds capacity, excess operations wait in an **ingress queue** instead of competing for CPU and cache. Critical reads and writes and internal work (such as elections) run ahead of "background jobs and expensive queries".[^miwm] Optionally, **Load Shedding** caps the queue and rejects the overflow with an overload error. It's off by default on 9.0, and queueing, prioritisation and Load Shedding need M30 or larger replica sets.[^miwm]

```viz:flow
title: "How Atlas IWM handles a traffic spike"
headers: [Clients, Each mongod, Execution]
columns:
  - - label: Burst of ops
      sub: "agents, batch jobs"
  - - label: Rate limiter
      sub: "admits at a safe rate"
      style: accent
    - label: Ingress queue
      sub: "overflow waits here"
      style: soft
    - label: Load shedding

      style: warn
  - - label: Critical first

    - label: Expensive last
      sub: "slowed under pressure"
note: "Simplified from MongoDB's [Intelligent Workload Management](https://www.mongodb.com/docs/atlas/intelligent-workload-management/) docs. Self-managed 9.0 doesn't include IWM."
```

Coinbase, quoted in the launch, says IWM gives it "confidence that our clusters will stay responsive during peak trading windows".[^mpr] It's a quote, not a measurement, but it shows the use case: sudden spikes you can't scale for fast enough.

#### 4. Schema rules the database guarantees

MongoDB has had {{schema validation|rules, usually written in JSON Schema, that inserts and updates must satisfy}} for years, but with a loophole. The default `strict` level checks new writes, yet documents that were already invalid before you added the rule can stay in the collection.[^mval] 9.0 adds a new level, **`constraint`**, which "guarantees that *every* document in the collection satisfies the rules".[^mrn]

To switch an existing collection to `constraint`, you first run `collMod` with `prepareConstraintValidationLevel: true`. That blocks `bypassDocumentValidation` and validator changes. Then you set `validationLevel: "constraint"`, and MongoDB scans **every** existing document. If one fails, the whole change fails.[^mval] While at `constraint`, you can't edit the rules. To change them, you drop to `strict`, edit, and go back up (with another full scan). And the validation action must be `error` or `errorAndLog`, not `warn`.[^mval] For a team that has been writing "the field is always there" checks in application code, this is the database finally making that promise.

#### 5. Per-query control over the planner

MongoDB already lets you store {{query settings|stored per-query-shape instructions, such as which index to use, that the server applies to every query of that shape}} with the `setQuerySettings` command. 9.0 extends them: you can pass a `querySettings` document **directly** on a single `find`, `distinct` or `aggregate` call, set a `maxTimeMS` timeout for a whole {{query shape|a query with its literal values stripped out, so a filter on status "A" and the same filter on status "B" count as the same shape}}, and override internal server parameters for one shape with `queryKnobs` (which needs FCV 9.0).[^mrn]

You also get better visibility. `$queryStats` now covers `insert`, `update` and `delete` as well as reads, collected by default from a 1% sample of operations.[^mrn] It's the same idea as Postgres's `pg_plan_advice`: when the planner gets one critical query wrong, you can pin that one query without touching the rest.

#### 6. Under the hood: time series, encryption, BSON

- **Time series collections** are now stored as a single namespace of compressed {{buckets|groups of measurements from the same source and time window, stored together in one document}}, instead of being exposed as a view, and you can finally `renameCollection` them. Clusters with **more than 5,000 time series collections in one database** may see a slower upgrade and write-latency spikes.[^mrn]
- **{{Queryable Encryption|client-side encryption where the server can run some queries on data it can't decrypt}}**: prefix, suffix and substring queries on encrypted strings are now GA. The GA format is **incompatible** with the 8.2 public preview, so preview users have to re-create the collection.[^mcompat]
- **BSON validation is on by default.** The server now validates every {{BSON|Binary JSON, MongoDB's on-disk and wire format for documents}} object it ingests, and `net.wireObjectCheck` is deprecated.[^mrn] Separately, `mongocryptd` is deprecated in favour of the Automatic Encryption Shared Library.[^mrn]

### What it means for you

**If you're on Atlas,** your upgrade timing depends on your Atlas settings. Raising FCV is where behaviour changes, so do it deliberately. Check the IWM metrics ("Operation Rate Limiting: Queued operations") after the upgrade, because with reactive auto-scaling enabled, Atlas uses the queued-operation rate to decide when to scale up.[^miwm]

**If you self-manage,** note the new release model. 9.0 is what you'll run until a 9.5 Feature Update, with no interim minors.[^mver] If you're on 7.0, you have to go through 8.0 first.[^mupg]

**A pre-upgrade checklist, all from the official notes:**

1. Search for `null` / `$ne: null` / `$in: [null]` comparisons on dotted paths, including inside `$lookup`.[^mcompat]
2. Search server-side JavaScript for local `Date` methods (`getHours()`, `getDate()` and so on).[^mcompat]
3. Find heavy aggregations and test them against the new per-operation memory cap. Add `allowDiskUse: true` where spilling is acceptable.[^magg]
4. If your code matches on old 2dsphere error codes (`16755`, `16756` and others), switch to `510`/`511`.[^mcompat]
5. Hand-written change-stream loops must handle the new resumable error `11602` (`InterruptedDueToReplStateChange`) after elections. Compliant drivers resume automatically.[^mcompat]
6. Wait for **9.0.3** if you run sharded clusters (see below).[^mrn]

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **A known sharding hang.** SERVER-133518: a shard "can hang during step-up" if a chunk migration was interrupted during an earlier step-down. The shard then can't become primary, and primary reads and writes on it are unavailable. It's fixed in 9.0.3, which isn't out yet.[^mrn]
- **Queries can now be killed mid-flight** with `QueryKilledError` if an indexed field becomes {{multikey|holding an array, so the index stores one entry per array element}} while the query runs. Re-run after the write completes.[^mcompat]
- **Cross-database `renameCollection` on replica sets** now holds an exclusive lock on both collections for the whole operation, blocking writes and DDL. That's safer (it prevents lost writes), but plan for the pause.[^mcompat]
- **IWM and the "spiky traffic" story are Atlas features.** A self-managed 9.0 gets the memory and transaction caps, but not the ingress queue.[^miwm]
- **The headline numbers are MongoDB's own,** compared with 8.0, not with the 8.x minors.[^mpr]
</div>

### What happens next

Watch for 9.0.3 and the SERVER-133518 fix.[^mrn] On the cloud side, **Atlas Infinite**, which separates compute from storage, is in public preview **on AWS only**. MongoDB claims it cuts "time to scale by more than 96%" and delivers "189% more throughput per dollar than Atlas Core" (its own tests), with other clouds planned.[^mpr] Independent 9.0 benchmarks and real migration reports will be the next thing worth reading. The first Feature Update under the new model should be 9.5, but MongoDB hasn't announced a date.

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **Major release**: an X.0 version with possibly incompatible changes and five years of support.
- **Minor release**: an interim X.Y feature release; Atlas Auto Upgrade only from 9.0.
- **Feature compatibility version (FCV)**: the switch that enables new on-disk features; raise it last.
- **Dotted path**: a field path like "a.b" that also walks into arrays.
- **WebAssembly (WASM)**: sandboxed portable bytecode that can only use what the host allows.
- **Spill to disk**: writing intermediate data to temp files instead of RAM.
- **Multi-document transaction**: an atomic read/write across several documents.
- **Admission control**: limiting how fast new work starts so running work isn't starved.
- **Schema validation**: rules that inserts and updates must satisfy.
- **Query settings**: stored per-shape instructions such as index choice.
- **Query shape**: a query with its literal values removed.
- **Buckets**: groups of time-series measurements stored as one document.
- **Queryable Encryption**: client-side encryption the server can still query.
- **BSON**: MongoDB's binary document format.
- **Multikey**: an indexed field that holds an array.
</div>
