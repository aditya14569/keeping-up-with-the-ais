# Story 1 · MySQL's thread pool goes free

<div class="byline">MySQL 26.7.0 · Community Edition · Released 28 Jul 2026 · Percona benchmarks 5 and 12 Oct · ~18 min read</div>

<p class="opener" markdown="1">Imagine a restaurant that hires a new waiter for every customer who walks in. At ten customers it's luxurious. At two thousand, the waiters spend all their time bumping into each other in the kitchen doorway, and nobody gets fed. That's how MySQL has always handled connections by default. For years the fix, a "thread pool" that lets a small crew of waiters serve everyone, was something you had to pay Oracle for. This summer Oracle started giving it away, and this week the first serious benchmarks of the free version landed. The results are spectacular in one corner and disappointing in another, and the reasons why tell you a lot about how a database server really spends its time.</p>

### What happened

On **28 July 2026**, Oracle shipped three MySQL server releases at once: **MySQL 26.7.0**, the first release to use a new calendar-style version number, plus bug-fix releases **9.7.2 LTS** and **8.4.11 LTS**.[^frank] Tucked into the 26.7.0 release notes, under "Thread Pool Notes", is one line: "MySQL Thread Pool plugin, formerly only available in MySQL Enterprise Edition, is now available in MySQL Community Edition 26.7.0. (WL #17296)".[^rn267] Oracle's announcement post repeats it: "The MySQL Thread Pool Plugin is now available in MySQL Community Edition."[^frank]

Both 26.7.0 and 9.7.2 also changed one default: `thread_pool_max_unused_threads` went from 2 to 32.[^rn267]<sup>,</sup>[^rn972]

The feature got little attention until Percona engineer **Bogdan Degtyariov** published a two-part benchmark. Part 1, on **5 October**, measured Percona Server's own thread pool and found it up to **17.9 times** faster than no pool on an I/O-bound workload with 2,560 connections.[^p1] Part 2, on **12 October**, put MySQL's newly free pool head-to-head with Percona's and found that neither wins everywhere.[^p2] The same day, Percona's Anil Joshi published an explainer of the 26.7 release that called the thread pool "the good news" of the release.[^joshi]

A quick word on the version numbers, because they're new. MySQL now uses `Year.Month.Patch`, so 26.7.0 means July 2026. It's an {{Innovation release|a MySQL release line that gets new features quickly but is supported only until the next one, as opposed to a long-term support (LTS) line}}, and the last LTS was 9.7, released in April 2026. Percona says the next Innovation release is tentatively 26.10.0 and the next LTS is expected in April 2028 as 28.4.0, and that you can only reach 26.7 by going through 9.7 first.[^joshi]

### The background you need

#### One thread per connection

When a client connects to MySQL, the server by default creates a dedicated operating-system {{thread|an independent stream of execution inside a process, with its own stack, scheduled onto CPU cores by the operating system}} for it. That thread reads the client's statements, runs them and sends back results, and it lives as long as the connection does. MySQL's documentation describes the model and its limits plainly: "The default thread-handling model in MySQL Server executes statements using one thread per client connection. As more clients connect to the server and execute statements, overall performance degrades."[^tp267]

The docs list three reasons why:[^tp267]

1. "Too many thread stacks make CPU caches almost useless in highly parallel execution workloads." Every thread has its own stack memory, and when thousands of them take turns on the CPU, each one evicts the others' data from the {{CPU cache|small, very fast memory on the processor chip that holds recently used data; a miss means a much slower trip to main memory}}.
2. "With too many threads executing in parallel, {{context switching|the operating system pausing one thread, saving its state and loading another's so it can run on the same core; each switch costs CPU time and pollutes caches}} overhead is high."
3. "Too many transactions executing in parallel increases resource contention. In InnoDB, this increases the time spent holding central {{mutexes|locks inside the server's own code that let only one thread at a time touch a shared data structure}}."

The third point is the subtle one. Running 2,000 queries at once is not faster than running 80 at a time on an 80-core machine. The extra ones just queue up inside the database on internal locks, where waiting is expensive and unfair, instead of queueing outside in an orderly line.

How do you know you're there? MySQL's FAQ gives a rule of thumb: watch the `Threads_running` status variable, which counts statements executing right now. If it "consistently exceeds a region where the server won't operate optimally (usually going beyond 40 for InnoDB workloads), the Thread Pool should be beneficial."[^faq]

#### Your app's connection pool is a different thing

If you use HikariCP, a Go `sql.DB` or Django's persistent connections, you already have a "connection pool". That's on the client side, and it solves a different problem. MySQL's FAQ draws the line: a client-side pool caches idle connections "to ensure that a MySQL client does not constantly connect to and disconnect from the MySQL server", but it "has no visibility as to the query handling capabilities or load of the back-end MySQL server." A {{thread pool|a server-side mechanism that runs statements from many client connections on a small, managed set of worker threads, instead of one thread per connection}} works inside the server and decides how many statements run at once. The two are "orthogonal and can be used independent of each other."[^faq]

The trouble is that client pools multiply. Fifty application instances, each with a pool of 40, is 2,000 connections, and each of them is a server thread.

#### Who had a thread pool before

MySQL's thread pool has been sold as part of {{MySQL Enterprise Edition|Oracle's paid, commercially supported edition of MySQL, which adds plugins such as the thread pool, audit logging and backup tools}}. The 9.7 manual still files it under that heading: "MySQL Enterprise Edition includes MySQL Enterprise Thread Pool, implemented using a server plugin."[^ent97]

If you wanted pooling for free, you had to switch servers. MariaDB has shipped one since its 5.1–5.3 releases, and "MariaDB 5.5 introduced an improved thread pool." MariaDB's is built into the server rather than being a plugin, and uses the operating system's best mechanism for watching many network connections (`epoll` on Linux, the native thread pool on Windows).[^mariadb] Percona Server for MySQL, a free drop-in replacement for MySQL, also has one built in.[^perconadocs] Percona's part 1 also mentions third-party plugins.[^p1]

Oracle has been moving Enterprise features into Community for a while. When MySQL 9.7 LTS shipped in April, an Oracle blog post titled "MySQL 9.7 Is Out and the Community Wins" listed replication metrics components, a telemetry component, writable JSON duality views and the hypergraph optimizer as newly free.[^97wins] The thread pool is the latest, and the one with the most direct effect on performance.

### How it works

#### Thread groups, a listener and two queues

The thread pool breaks the link between a connection and a thread. "The thread pool separates connections and threads, so there is no fixed relationship between connections and the threads that execute statements received from those connections."[^op97]

Here's what happens when your connection sends a query:

1. **Your connection belongs to a group.** The pool is split into {{thread groups|independent sub-pools inside the thread pool, each managing a share of the connections; MySQL's default is 16}}. "As connections are established, the thread pool assigns them to thread groups in round-robin fashion." The default number of groups is 16.[^op97]
2. **A listener notices.** "Each thread group has a {{listener thread|a thread in each group that waits for any of the group's connections to send a statement, instead of one thread per connection waiting}} that listens for incoming statements from the connections assigned to the group."[^op97]
3. **Run now, or queue.** If nothing else is running or queued in the group, the statement runs immediately. Otherwise it's queued.[^op97]
4. **Transactions in progress go first.** There's a high-priority queue and a low-priority queue. "The first statement in a transaction goes to the low-priority queue. Any following statements for the transaction go to the high-priority queue if the transaction is ongoing."[^op97] The idea is to finish transactions that already hold locks before starting new ones.
5. **Nobody starves forever.** A statement that waits too long in the low-priority queue is promoted, controlled by `thread_pool_prio_kickup_timer`, at most "one statement per 10ms (100 per second)" per group.[^op97]
6. **A worker runs it, then goes back for more.** Workers don't exit after a statement. They pick up the next queued one.

#### The hard part: when a query blocks

A pool that only lets one or two statements run per group has an obvious problem. What if the running statement is waiting on a disk read or a row lock? The whole group would sit idle.

MySQL handles this two ways. First, the server code that waits on disk I/O and on {{row locks|locks InnoDB takes on individual rows so two transactions can't change the same row at the same time}} calls back into the pool: "there are callbacks to the thread pool to ensure that the thread pool can immediately start a new thread in this group to execute another statement."[^op97]

Second, for waits the callbacks don't cover, there's a timer. A statement that runs longer than `thread_pool_stall_limit` counts as {{stalled|in MySQL's thread pool, a statement that has run longer than the stall limit, after which it no longer stops others in its group from starting}}. "If the statement executes past the stall time, it is permitted to continue but no longer prevents other statements from starting." The default is 60 ms, the setting is in 10 ms units, and the maximum is 600, or six seconds.[^op97]<sup>,</sup>[^tune267] A background thread "regularly monitors thread group states" so no group gets stuck.[^op97]

That's why the pool is a bet. It works best when most statements are short. The docs recommend it "if your workload comprises mainly short queries", and MariaDB's docs warn it's a poor fit for "many concurrent, long, non-yielding queries" like data-warehouse work.[^faq]<sup>,</sup>[^mariadb]

#### Capping transactions, not just statements

In MySQL 8.0, Oracle added a second throttle, `thread_pool_max_transactions_limit`. An Oracle engineer's 2023 post says it "revitalizes the thread pool", because the original design "addressed the needs of MySQL 5.6" and later InnoDB improvements had eaten into its benefit. With the limit set, each group runs at most `limit / thread_pool_size` transactions at once, rounded up, and a worker sticks with a transaction's statements until it commits or rolls back.[^blanchard]

There's an emergency exit. If every slot is held by a long transaction, the server can look frozen, so a connection with the {{TP_CONNECTION_ADMIN|a MySQL privilege that lets a connection bypass the thread pool's transaction limit, run in a separate Admin thread group, and fix things}} privilege "ignores the limit" and runs in an "Admin thread group", where it can raise the limit or kill blockers. Nobody has it by default.[^op97]

#### Turning it on

MySQL's pool is a plugin you load at startup:[^install84]<sup>,</sup>[^joshi]

```ini
[mysqld]
plugin-load-add=thread_pool.so
```

Then check that it's active with `SELECT PLUGIN_NAME, PLUGIN_STATUS FROM INFORMATION_SCHEMA.PLUGINS WHERE PLUGIN_NAME LIKE 'thread%';`. When it loads, `thread_handling` changes to `loaded-dynamically`, and three Performance Schema tables appear: `tp_thread_group_state`, `tp_thread_group_stats` and `tp_thread_state`.[^install84]

The tuning guide's starting point for InnoDB is: `thread_pool_size` equal to the number of physical cores (up to 512, settable only at startup), `thread_pool_algorithm=1` "for high concurrency", `thread_pool_max_transactions_limit` at physical cores × 32, then lowered while you watch throughput, and `thread_pool_query_threads_per_group=2`.[^tune267] To check whether your stall limit fits your queries, it suggests:[^tune267]

```sql
SELECT SUM(STALLED_QUERIES_EXECUTED) / SUM(QUERIES_EXECUTED)
FROM performance_schema.tp_thread_group_stats;
```

Percona Server and MariaDB do it differently. Their pool is built in and switched on with a server variable, not a plugin, and the knobs have different names and defaults.

Percona's docs are explicit that its implementation "is not compatible with upstream": it's "built into the server" where "upstream implements the thread pool as a plugin", and it "does not minimize the number of concurrent transactions".[^perconadocs] Percona's default for `thread_pool_stall_limit` is 500 ms, and `thread_pool_oversubscribe` (default 3) sets how many workers can be active per group.[^perconadocs]

### What the benchmarks found

#### The setup

Percona's tests used a two-socket Intel Xeon Gold 6230 machine (2 × 20 cores, 80 logical CPUs) with 187 GiB of RAM and an NVMe SSD, on Ubuntu 24.04. The workload was {{sysbench|a widely used open-source benchmarking tool; its OLTP read-write test runs short transactions of point selects, range scans, updates, deletes and inserts}} OLTP read-write against a 24 GB data set (100 million rows across 20 tables), at 40 to 5,120 concurrent connections. Each run had a 10-minute warm-up and a 15-minute measurement, and **each configuration ran once**.[^p1]

The key variable was the {{InnoDB buffer pool|InnoDB's in-memory cache of table and index pages; if your working data fits, reads never touch disk}}. At 2 GB (a 1:12 ratio to the data) the server was I/O-bound. At 12 GB it was partly cached, and at 32 GB everything fit in memory.[^p1]

#### When it shines: lots of connections, lots of disk waits

With a 2 GB buffer pool and 2,560 connections, Percona Server with no pool managed 129 transactions per second. With its best pool settings (10 groups, oversubscribe 4) it did 2,304: "17.9 times faster". It peaked at 2,485 TPS at 640 connections and lost only 7.5% going to 2,560. The no-pool server's throughput "drops sharply" from about 120 connections.[^p1]

MySQL's newly free pool helped too, but less. Same 2 GB setup, 2,560 connections: 371 TPS with the pool and 122 without, about three times better. Its best `thread_pool_size` was 10, smaller than the 40 physical cores.[^p2]

#### When it doesn't: few connections, or everything in memory

Part 1's headline conclusion is the caveat: "Thread pooling does not bring any gains and even causes a small slow down on a low number of server connections." With all data in memory (32 GB), Percona Server without its pool won "at every connection count", and every configuration converged at around 16,000 TPS above 640 connections.[^p1]

Even there, the pool helped the slowest users. At 2,560 connections, the slowest 5% of transactions without a pool took longer than 787 ms ({{p95 latency|the time within which 95% of requests finish; the other 5% are slower}}), while pooled runs stayed between 235 and 297 ms. The author's point: even when the pool doesn't raise throughput, it "allows to minimize the waiting time for slowest transactions."[^p1]

#### MySQL's pool vs Percona's

Part 2 found the two implementations behave quite differently, even though they're built on the same server code:[^p2]

- **I/O-bound (2 GB):** Percona's pool did 2,304 TPS at 2,560 connections against MySQL's 371, a factor of 6.2. MySQL was faster at 40 connections.
- **Fully cached (32 GB):** the result flipped. MySQL's pool did 19,054 TPS against Percona's 15,519, 22% ahead, and its p95 was about 177 ms against Percona's 235 ms. Unlike Percona's, MySQL's pool still beat no pool here: 18,975 against 17,011 TPS, with p95 dropping from 759 to 153 ms.
- **Tuning:** Percona's pool is "very sensitive" to its two main settings; MySQL's mostly isn't. The best Percona setting at 32 GB was 160 groups, while MySQL's was still 10.
- **Where it starts to help:** MySQL's pool mainly helps at 1,280 and 2,560 connections. Percona's helps from about 80.

### What it means for you

**If you run MySQL Community and have connection storms, this is worth testing now.** The classic signs are hundreds or thousands of mostly idle connections, `Threads_running` regularly above about 40, and throughput that falls off a cliff when traffic spikes instead of levelling off.[^faq] Fleets of small app instances, each with its own client pool, are the typical cause.

**If your data fits in memory and you have modest connection counts, expect little.** Both of Percona's articles say the same thing in different ways: the pool "is not a universal database booster".[^p1]

**Test with your own workload, at your own connection counts.** The gap between the best and worst settings was large. In part 1, simply changing `thread_pool_oversubscribe` from 4 to 2 cost 11%.[^p1] Start from the manual's recommendations, then measure.[^tune267]

**Watch the tail, not just the average.** Even where the pool didn't increase TPS, p95 latency at high concurrency fell by a factor of three or more.[^p1]<sup>,</sup>[^p2] If your problem is a few users timing out during spikes, that's the number that matters.

**If you're choosing between MySQL and Percona Server or MariaDB**, the thread pool used to be a reason to switch. It's now a smaller one, though Percona's results suggest its pool is still stronger when you're I/O-bound.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Check that your build has it.** The 26.7.0 release notes say Community 26.7.0. Percona says Community 9.7.2 has it too, but the 9.7.2 release notes don't mention it, and the 9.7 manual still says "For MySQL 9.7, the Thread Pool plugin is included in MySQL Enterprise Edition".[^p1]<sup>,</sup>[^rn972]<sup>,</sup>[^faq] Look for `thread_pool.so` in your plugin directory before you plan around it.
- **It needs a restart.** The plugin loads at startup, and `thread_pool_size` can't change at runtime.[^install84]<sup>,</sup>[^tune267] Switching `thread_pool_max_transactions_limit` from zero to non-zero also needs a restart.[^blanchard]
- **A transaction cap can look like an outage.** With the limit set, new work waits when all slots are busy: "No new threads are created to handle new requests."[^blanchard] Grant `TP_CONNECTION_ADMIN` to an operator account before you need it.[^op97]
- **Long queries and pools don't mix well.** Reports and batch jobs that run for seconds will be treated as stalled. If you have many of them, raise `thread_pool_stall_limit` or keep them on a separate server.[^tune267]<sup>,</sup>[^mariadb]
- **The benchmark numbers are one lab's.** Single runs, one workload, one machine, published by the company that makes Percona Server. Part 2 also gives two different p95 figures for MySQL's pool at 32 GB (153 ms and 177 ms) without explaining the difference.[^p2]
</div>

### What happens next

Percona says the next Innovation release, tentatively 26.10.0, is due later this year.[^joshi] Its release notes will show whether Oracle keeps moving Enterprise features into Community. Also watch the manual: the 26.7 section is titled "MySQL Thread Pool", while the 9.7 one is still "MySQL Enterprise Thread Pool".[^tp267]<sup>,</sup>[^ent97] And if your company uses a managed MySQL service, check whether it exposes the plugin. The release notes say nothing about cloud providers.

# Story 2 · Aurora DSQL learns foreign keys without locks

<div class="byline">Amazon Aurora DSQL · Foreign keys 26 Aug · Partial indexes 15 Sep · AWS deep dive 1 Oct · ~15 min read</div>

<p class="opener" markdown="1">When AWS unveiled Aurora DSQL in December 2024, it promised a Postgres-compatible database that spans regions, never goes down and never makes you think about servers. Then developers tried to migrate, and hit a wall of "not supported". No foreign keys was the one that stung. One Reddit commenter put it bluntly at launch: "You can't truly have 'relational' data without foreign keys."[^infoq] This summer AWS shipped them, along with partial indexes, a new kind of join and a pile of other Postgres features. Foreign keys are the interesting part, because DSQL has a design rule that seems to make them impossible: it never takes locks.</p>

### What happened

Aurora DSQL's release notes for this summer read like a checklist of missing Postgres features being ticked off:[^dsqlrn]

- **3 August:** `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` and `ALTER TABLE ASYNC ... VALIDATE CONSTRAINT`, for adding constraints to big tables without blocking.
- **13 August:** indexes on expressions, such as `lower(title)`.
- **24–25 August:** wider `SELECT ... FOR UPDATE` support, and a new `SELECT ... FOR KEY SHARE`.
- **26 August:** **foreign key constraints**, plus compression for large text values.
- **27 August:** extended statistics (`CREATE STATISTICS`) to help the planner with correlated columns.
- **11 September:** **batched nested-loop joins**.
- **15 September:** **partial indexes**.

AWS's public announcements followed. The What's New post for foreign keys is dated **27 August**, and lists support for the `NO ACTION`, `RESTRICT`, `CASCADE`, `SET NULL` and `SET DEFAULT` actions in all regions where DSQL runs.[^fkwn] InfoQ covered it on **28 September**.[^infoq] On **1 October**, the AWS Database Blog published a long explainer of how the foreign keys work and how to design around them.[^fkblog] On **2 October**, AWS announced partial indexes.[^piwn]

Luc van Donkersgoed, a principal engineer at Dutch railway operator Nederlandse Spoorwegen, summed up the reaction InfoQ found: "Lack of FKs was the biggest gap between DSQL and 'normal' Postgres, blocking many migrations."[^infoq]

### The background you need

#### What DSQL is

{{Aurora DSQL|AWS's serverless, distributed, PostgreSQL-compatible database, designed to run active-active across multiple regions}} entered public preview on 3 December 2024 with "PostgreSQL v16 compatibility", and became generally available on 27 May 2025.[^dsqlrn]<sup>,</sup>[^ga] AWS says it's "designed for 99.99% single-Region and 99.999% multi-Region availability", and that reads and writes to any regional endpoint are strongly consistent.[^ga]

It's "Postgres-compatible" in a specific sense. It uses PostgreSQL's query processing on top, but the storage, replication and transaction machinery underneath are all new. That's why each Postgres feature has to be rebuilt for it, rather than simply switched on.

#### How a DSQL transaction commits

AWS distinguished engineer Marc Brooker described the write path in a 2024 blog post.[^brooker] In short:

1. **Reads happen at a start time.** When your transaction begins, DSQL picks a timestamp and you read everything as of that moment. This is {{MVCC|multi-version concurrency control: keeping several versions of each row so readers see a consistent snapshot without blocking writers}}, the same idea Postgres uses.
2. **Writes are just notes.** An `UPDATE` "simply writes down a planned change locally inside the Query Processor". Nothing goes to storage yet.
3. **At COMMIT, the adjudicator decides.** A separate service called the {{adjudicator|DSQL's commit-time conflict checker: it accepts a transaction only if no other transaction wrote the same keys since it started}} checks whether any other transaction wrote the same keys between your start time and your commit time.
4. **If you pass, the journal makes it durable.** The transaction goes to the {{journal|DSQL's internal replicated log of committed transactions; once written there, a commit is durable}}, you get your success, and storage nodes apply it in the background.

```viz:flow
    - label: "Storage nodes"
      sub: "apply in parallel"
note: "Simplified from Marc Brooker's 'DSQL Vignette: Transactions and Durability' and the DSQL concurrency control docs. QP = Query Processor."
```

This is {{optimistic concurrency control (OCC)|a way to run concurrent transactions without locks: everyone proceeds, and conflicts are detected at commit, where the loser is aborted and must retry}}. The docs: "Instead of using locks, OCC evaluates conflicts at commit time."[^occ] The loser gets `ERROR: change conflicts with another transaction (OC000) (SQLSTATE 40001)`, the standard Postgres code for a serialization failure, and your app retries.[^occ]

Brooker argues this is "the provably minimal amount of coordination" for strong consistency, and that it means a client can never hold a lock it shouldn't, say across a garbage-collection pause.[^brooker] The isolation level is fixed: DSQL provides {{snapshot isolation|each transaction sees a consistent snapshot from its start, and two transactions conflict only if they write the same data}}, which matches Postgres's `REPEATABLE READ`.[^brooker]<sup>,</sup>[^migrate]

DSQL also limits transactions. One can modify at most 3,000 rows, and Brooker gives the other limits as 10 MiB of writes and five minutes per transaction.[^migrate]<sup>,</sup>[^thinking]

#### Why foreign keys are hard here

A {{foreign key|a constraint that says a column's value must match a key in another table, e.g. every order's product_id must exist in products}} check is a *read*. When you insert an order for product 1, the database has to confirm that product 1 exists, and keep it existing until you commit.

Classic Postgres does this with a lock. The AWS blog explains that Postgres takes a {{FOR KEY SHARE lock|a Postgres row lock that says 'I depend on this row's key staying the same'; it blocks deletes and key changes, but not other readers or non-key updates}} on the referenced row, so "a transaction that changes key columns or deletes that row waits for transactions still referencing it."[^fkblog]

DSQL has no locks to take. And plain snapshot isolation only catches *write-write* conflicts. Brooker noted that serializable isolation would also need to check read-write conflicts, which DSQL doesn't do.[^brooker] So consider two transactions. Session A deletes product 1. Session B inserts an order for product 1. B checked its snapshot, and product 1 was there. A and B wrote *different* rows, so the adjudicator, as originally designed, would let both commit, and you'd have an order pointing to a product that doesn't exist. That's exactly the bug a foreign key exists to prevent.

### How it works

#### Teaching the adjudicator about reads

The fix came in two steps, and the release notes show the order. On 25 August, DSQL gained `SELECT ... FOR KEY SHARE`, which "declares that a transaction depends on the key columns of the selected rows."[^dsqlrn] It's not a lock. It tells the adjudicator to treat that read as something that can conflict. The next day, foreign keys shipped on top of it.

The documentation describes the two phases.[^fkdocs]

**Phase 1: check against your snapshot.** "When you insert or update a referencing row, Aurora DSQL reads the referenced table at your transaction's start-time snapshot to confirm the referenced key exists." Deletes and key updates on the parent check the child table the same way. "Because this verification reads from the transaction start-time snapshot instead of taking a lock, other transactions can continue to modify the referenced and referencing tables in parallel."

**Phase 2: settle it at commit.** Phase 1 only proves the constraint held when you started. So "Aurora DSQL implicitly applies the `KEY SHARE` clause to referenced rows to detect whether any concurrent change invalidated your snapshot. If Aurora DSQL detects a conflict, it fails the transaction with a serialization error."

Here's the documented example:[^fkdocs]

```sql
-- products(1, 'Widget') exists; orders.product_id REFERENCES products
-- Session A                         -- Session B
BEGIN;                               BEGIN;
DELETE FROM products                 INSERT INTO orders
  WHERE product_id = 1;                VALUES (100, 1, 5);
COMMIT;  -- succeeds
                                     COMMIT;  -- fails:
-- ERROR: change conflicts with another transaction (OC000)
-- (SQLSTATE 40001)
```

The first to commit wins. B's insert passed its snapshot check, but the adjudicator sees that A deleted a row B had marked as a key dependency, and B is rejected. "You can't end up with an order that points to a deleted product."[^fkdocs]

Brooker summed up the design, quoted by InfoQ: "No blocking, no change in scaling for non-FKC reads."[^infoq] An earlier explainer of the adjudicator by AWS engineer Marc Bowes, written before foreign keys shipped, had sketched the same kind of idea: an "exists" check for inserts that reference a row, which conflicts with deletes but not with other existence checks.[^bowes]

#### What conflicts, and what doesn't

The clever part is what *doesn't* conflict. A key-share mark only cares about the parent's key. The DSQL concurrency docs give the full matrix:[^occ]

| Your transaction did… | vs. insert / delete / key update / FOR UPDATE | vs. non-key update | vs. FOR KEY SHARE |
|---|---|---|---|
| Insert, delete, key update, FOR UPDATE | conflict | conflict | conflict |
| Update of non-key columns only | conflict | conflict | no conflict |
| FOR KEY SHARE (incl. FK checks) | conflict | no conflict | no conflict |

The AWS blog spells out what that means for foreign keys:[^fkblog]

- Deleting a parent while someone inserts a child that references it: **conflict**.
- Changing a parent's primary key while someone references the old key: **conflict**.
- Changing a column that's in a UNIQUE index on the parent (say, a unique `name`): **conflict**. "Key" here means primary keys and columns of non-partial, non-expression unique indexes.
- Changing a non-key column on the parent, such as `price`: **no conflict**.
- Two sessions inserting children under the same parent: **no conflict**.

That last one matters most. A popular parent row, like a best-selling product, can take many simultaneous child inserts "without false conflicts".[^fkblog]

#### Deferred checks, cascades and existing tables

DSQL supports the full set of Postgres foreign key options: the five referential actions, `MATCH SIMPLE` and `MATCH FULL`, and {{deferrable constraints|foreign keys whose check can be postponed until COMMIT, so a transaction can briefly break the rule, e.g. insert a child before its parent}}.[^fkdocs] With `SET CONSTRAINTS fk_product DEFERRED`, you can insert an order line before its product within one transaction, and the check runs at commit.[^fkblog]

Cascades have a DSQL-specific catch. `CASCADE`, `SET NULL` and `SET DEFAULT` change child rows for you, and those changes "count against the 3,000-row transaction mutation limit, so cascading deletes on large child sets fail." AWS recommends `NO ACTION` or `RESTRICT` whenever the number of children is unbounded.[^fkblog] (Brooker had already called `ON DELETE CASCADE` a bad idea in a footnote on his blog.[^thinking])

To add a foreign key to a table that already has data, you split it into two steps, so you never scan a big table inside a blocking statement:[^fkblog]<sup>,</sup>[^dsqlrn]

```viz:codecompare
title: "Adding a foreign key to a big existing table"
left:
  title: "PostgreSQL habit"
  code: |
    ALTER TABLE order_items
      ADD CONSTRAINT fk_product
      FOREIGN KEY (product_id)
      REFERENCES products;
    -- scans every row now
right:
  title: "Aurora DSQL"
  code: |
    ALTER TABLE order_items
      ADD CONSTRAINT fk_product
      FOREIGN KEY (product_id)
      REFERENCES products NOT VALID;
    -- new writes checked from now
    ALTER TABLE ASYNC order_items
      VALIDATE CONSTRAINT fk_product;
    -- runs as a job; see sys.jobs
note: "DSQL syntax from the AWS Database Blog (1 Oct 2026) and the DSQL release notes. Each DDL statement must be in its own transaction."
```

The validation runs as an asynchronous job you can watch in `sys.jobs`.[^dsqlrn] That's important in DSQL, where "a transaction can include only 1 DDL statement" and DDL and DML have to be in separate transactions.[^migrate]

#### Partial indexes and batched joins

The other two features target performance, and both make sense once you know DSQL's storage is a remote, distributed service rather than a local disk.

A {{partial index|an index over only the rows that match a WHERE condition, so it stays small even as the table grows}} is a standard Postgres feature that DSQL added on 15 September: "Add a `WHERE` clause to `CREATE INDEX` to index only the rows that satisfy a predicate." The planner uses it "when it can prove that the query's `WHERE` conditions imply the index's predicate."[^dsqlrn] AWS's example is a table with a small working set and a long history, such as open orders among years of completed ones.[^piwn] In DSQL, every index build is asynchronous, so the statement looks like this:[^cix]

```sql
CREATE INDEX ASYNC orders_open_idx
  ON orders (customer_id)
  WHERE status = 'open';
```

Functions in the predicate must be immutable, the same rule as for index expressions.[^cix] AWS's own `dsql-lint` migration checker stopped flagging partial indexes as incompatible in a change merged on 16 September.[^lint]

A {{nested-loop join|a join that, for each row from one input (the outer side), looks up matching rows in the other (the inner side)}} is ideal when the outer side is small and the inner side has an index. But in DSQL, each inner lookup is a round trip from the query processor to storage. A {{batched nested-loop join|a nested-loop join that collects many outer rows first and looks up the inner side for the whole batch at once, cutting round trips}} "collects a batch of outer rows, builds the inner scan work for the entire batch, and then joins the returned inner rows back to the matching outer rows." It shows up in `EXPLAIN` as `Nested Loop (Batched Join)`, and you can switch it off per session with `SET dsql.enable_batched_nestloop = off;`.[^bnl]

### What it means for you

**If foreign keys were your blocker, the migration story just got a lot better.** You can bring your schema across with its constraints instead of rewriting referential integrity into application code. AWS's blog suggests two paths for data: load parents before children, or load everything without foreign keys and then add them with `NOT VALID` and an async `VALIDATE`.[^fkblog] ORMs are catching up too: the Drizzle ORM adapter added on 25 August includes opt-in OCC retries.[^dsqlrn]

**Retries go from "nice to have" to "required".** In Postgres, a foreign key conflict means a short wait. In DSQL it means an error. AWS's guidance:[^fkblog]

- `40001` / `OC000` (data conflict): retry the whole transaction from `BEGIN`, with exponential backoff and jitter and a cap on attempts.
- `OC001` (the session's cached schema is out of date): usually succeeds on the first retry.
- `23503` (an actual foreign key violation): don't retry. That's a bug in your data or logic.

**Design around hot parents.** Ordinary child inserts don't conflict with each other, but anything that touches a parent's *key* does. AWS's advice is to keep referenced keys stable and move frequently changing values into non-key columns.[^fkdocs] Its blog also warns about "scale-explosive" relationships, such as every audit log row pointing to one tenant, or every engagement row to one viral post. There, avoid `CASCADE`, soft-delete the parent and clean up children in batches of 3,000 or fewer, and copy mutable attributes like price into the child row when you write it.[^fkblog] If you see a steady rise in 40001 errors, AWS says it's a sign of a hot parent row.[^fkblog]

**Benchmark first.** "All data manipulation language (DML) operations on referenced or referencing tables incur extra reads to guarantee referential integrity." AWS's advice is to benchmark before adding a constraint.[^fkdocs] It hasn't published numbers for that overhead.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **No performance numbers yet.** Neither the docs nor the 1 October blog post quantify the cost of the extra reads or the conflict rate under load.[^fkblog]
- **Updating a unique column on a parent conflicts with child inserts.** That includes columns that seem harmless, such as a unique `name` or `email`, not just the primary key.[^fkblog]
- **Cascades hit the 3,000-row limit.** A `DELETE` that cascades to 5,000 children fails.[^fkblog]
- **`SET CONSTRAINTS` only affects foreign keys.** Primary key, unique, `NOT NULL` and `CHECK` constraints are always checked immediately.[^fkblog]
- **It's still not identical to Postgres.** Isolation is fixed at Repeatable Read, `FOR SHARE` and `FOR NO KEY UPDATE` aren't supported, and indexes must be built with `CREATE INDEX ASYNC`.[^migrate]<sup>,</sup>[^occ]<sup>,</sup>[^cix] Two concurrent updates to the same row conflict even if they change different non-key columns.[^occ]
</div>

### What happens next

The pace suggests more is coming. Since June, DSQL's release notes have added a Postgres feature roughly every week or two.[^dsqlrn] Meanwhile, if you migrate, the AWS blog post is the best guide so far to which relationships will scale and which will fight you.[^fkblog]

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **Aurora DSQL**: AWS's serverless, distributed, PostgreSQL-compatible database, designed to run active-active across regions.
- **MVCC**: multi-version concurrency control; keeping several versions of each row so readers see a consistent snapshot without blocking writers.
- **Adjudicator**: DSQL's commit-time conflict checker.
- **Journal**: DSQL's internal replicated log of committed transactions.
- **Optimistic concurrency control (OCC)**: running transactions without locks and detecting conflicts at commit, where the loser must retry.
- **Snapshot isolation**: each transaction sees a consistent snapshot from its start; transactions conflict only if they write the same data.
- **Foreign key**: a constraint that a column's value must match a key in another table.
- **FOR KEY SHARE lock**: a Postgres row lock meaning "I depend on this row's key staying the same".
- **Deferrable constraints**: foreign keys whose check can wait until COMMIT.
- **Partial index**: an index over only the rows that match a WHERE condition.
- **Nested-loop join**: a join that looks up matching inner rows for each outer row.
- **Batched nested-loop join**: a nested-loop join that looks up the inner side for many outer rows at once, cutting round trips.
