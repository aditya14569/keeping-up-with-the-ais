# Story 1 · The JDBC driver that padded your data with someone else's

<div class="byline">pgjdbc 42.7.14 · Released 7 Oct 2026 · CVE-2026-107315 and CVE-2026-107314 · ~17 min read</div>

<p class="opener" markdown="1">Imagine you tell a courier the parcel is a metre long, then hand over something half that size. A careful courier pads the box with clean packing paper. For about two years the PostgreSQL JDBC driver padded it with scraps from the last few parcels it had carried instead: earlier SQL statements, earlier parameter values, possibly from a different request that had borrowed the same pooled connection. And the database stored those scraps as part of your data.</p>

### What happened

On **7 October 2026** the PostgreSQL JDBC project, usually called **pgjdbc**, shipped version **42.7.14** as a security release. The postgresql.org announcement, posted on 9 October, lists two CVEs and their GitHub Security Advisories: **CVE-2026-107314** (GHSA-rhp9-mr79-r74h) and **CVE-2026-107315** (GHSA-f64h-wr5q-3qf3).[^ann] The project's homepage now lists 42.7.14, dated 7 October, as the current release.[^home]

The project's security page summarises both bugs:[^secpage]

- **CVE-2026-107315, "padding with earlier traffic".** When a value is shorter than its declared length, the driver fills the gap with bytes from earlier messages on the connection instead of with zeros, so the server can end up storing SQL text or parameter values. **Affected: 42.7.4 through 42.7.13.** Versions 42.7.3 and earlier pad with zeros.
- **CVE-2026-107314, "`requireAuth` not enforced".** If the `requireAuth` connection property excludes all six authentication methods the driver knows, the driver applies no restriction at all and will accept a cleartext password request from the server. **Affected: 42.7.11 through 42.7.13.**

Both are fixed in 42.7.14. The CVE records rate them Medium: **5.3** for the padding bug and **5.9** for the `requireAuth` bug, on the CVSS 3.1 scale.[^nvd315]<sup>,</sup>[^nvd314] The CVE records credit Vladimir Sitnikov as the finder of the padding bug and Daniel Coles as the reporter of the `requireAuth` bug.[^nvd315]<sup>,</sup>[^nvd314]

The same update to the security page also documented an older, already-fixed bug of the same family: **CVE-2026-107313**, in which, on GSS-encrypted connections, 42.7.4 and 42.7.5 could send old send-buffer contents in place of the first 16,320 bytes of a large value. That one was fixed back in **42.7.6**.[^secpage]<sup>,</sup>[^pr]

Downstream projects started moving quickly. Camunda, for example, merged a bump to 42.7.14 on its `stable/8.6` branch on 9 October. That branch had been on 42.7.11, inside the `requireAuth` window, although the commit message argues the vulnerable path is unreachable because that release line never opens a PostgreSQL connection.[^camunda]

Neither bug is a remote "take over the database" hole. But one quietly writes earlier traffic into your tables, and the other turns a security setting into a no-op. Both are worth understanding, because both come from the small print of how a driver talks to Postgres.

### The background you need

#### What a JDBC driver actually does

{{JDBC|Java Database Connectivity, the standard Java API (`Connection`, `PreparedStatement`, `ResultSet`) that every Java database driver implements}} is just a set of interfaces. The code that actually talks to PostgreSQL is the driver, and for Postgres that's pgjdbc, published on Maven Central as `org.postgresql:postgresql`.[^ann] If your Java, Kotlin or Scala service uses Postgres through Hibernate, Spring Data, jOOQ, MyBatis or plain JDBC, this jar is almost certainly underneath.

The driver turns your method calls into messages in the {{wire protocol|the binary message format that PostgreSQL clients and servers exchange over the network connection}}. You rarely think about that layer, but this story lives there.

#### The protocol makes you say how long a value is before you send it

When you run a prepared statement, the driver sends a **Bind** message that fills in the parameter values. Here's the relevant part of Bind's layout, from the PostgreSQL documentation:[^proto]

- `Int32`: "The length of the parameter value, in bytes (this count does not include itself)." A value of -1 means NULL.
- `Byte`*n*: "The value of the parameter … *n* is the above length."

COPY works the same way: each **CopyData** message carries an `Int32` length "of message contents in bytes, including self", followed by the data.[^proto]

So the length goes on the wire **first**, and the bytes follow. That ordering is what makes {{message framing|how the receiver knows where one message ends and the next begins; here, by trusting the declared length}} work. The server reads the length, then reads exactly that many bytes and treats them as the value. It has no other way to know where the value stops.

Now suppose the driver has already sent "the next value is 1,000 bytes long" and your code only produces 600. The driver can't take the length back: it's already in the buffer, maybe already on the network. If it just stopped, the server would read the next 400 bytes of the following message as part of your value, and the connection would fall apart. So the driver has to send 400 more bytes of *something*. That's padding. The only question is what goes in it.

#### When can a value be shorter than declared?

In most JDBC calls, the driver knows the exact length because you handed it a `String` or a `byte[]`. The risky APIs are the ones where you declare a length and then stream the data yourself. The advisory names five of them:[^nvd315]<sup>,</sup>[^hol]

- `PreparedStatement.setObject` with a `ByteStreamWriter`
- `CopyIn.writeToCopy`
- `PGCopyOutputStream.write`
- `LargeObject.write`
- `Blob.setBytes`

{{ByteStreamWriter|a pgjdbc interface for sending a binary parameter by writing to an OutputStream, so you don't have to build one big byte array on the heap}} is the clearest example. Its Javadoc says you implement two methods: `getLength()`, which returns the number of bytes, and "The length must be known ahead of the stream being written to"; and `writeTo(target)`, which writes the data and "should not write more than `getLength()` bytes".[^bsw] The interface stops you writing *more* than you promised. Before 42.7.14, nothing stopped you writing *less*.

{{Large objects|PostgreSQL's older facility for storing big binary values outside normal rows, written and read in chunks through a special API}} and {{COPY|PostgreSQL's bulk-load command, which streams many rows to the server in a single operation}} have the same shape. You pass an `(array, offset, length)` triple, and if the length runs past the real data, the driver has to fill in the rest.

### How it works

#### Where the stale bytes came from

Here's the key sentence from the advisory: the driver "pads a value that is shorter than its declared length with bytes left in its send buffer instead of zeros".[^hol]

A {{send buffer|a block of memory where the driver assembles outgoing messages before writing them to the network socket in one go}} is reused for every message on a connection. After a few statements it holds the remains of earlier Bind messages, query strings and parameter values. If padding copies "whatever is in the buffer right now" instead of writing fresh zeros, those remains are what gets sent.

The CVE record spells out the consequences. The leftover bytes "can include earlier SQL text and parameter values", "possibly from other requests on a pooled connection". Each padded value "can carry up to 8192 bytes" of that traffic, "or 16320 bytes with GSS encryption".[^nvd315]

The numbers above are illustrative. The mechanism and the per-value limits come from the advisory.[^nvd315]

Why did this start in 42.7.4? The advisory doesn't name the commit that introduced it. But the 42.7.4 changelog is suggestive. That release (announced 23 August 2024[^r474ann]) replaced Java's `BufferedOutputStream` with a new unsynchronized `PgBufferedOutputStream`, removed a separate `PGStream.streamBuffer` so that `PgBufferedOutputStream`'s own buffer is reused when sending data from an InputStream, added a `maxSendBufferSize` connection property, and "improved `writeZeros` tests".[^r474] A rewrite of the write path, a reused buffer and new tests for the zero-writing code all landing in the first affected release looks like the likely origin. That is our reading of the changelog, not something the advisory says.

The GSS variant fits the same pattern. CVE-2026-107313 describes old contents of the "GSS send buffer" being sent in place of a large value on encrypted connections in 42.7.4 and 42.7.5.[^secpage] {{GSS encryption|encrypting the Postgres connection using Kerberos (via the GSSAPI) instead of TLS}} has its own send buffer, and its leak limit (16,320 bytes) is larger than the normal one (8,192).

#### Who can actually exploit it?

This isn't a bug an attacker can trigger from outside on its own. Three things have to be true at once, according to the CVE record:[^nvd315]

1. Your application uses one of the five APIs and **declares a length larger than the data it supplies**. The driver accepted that "without error".
2. An attacker can get your application to **store** such a value.
3. The attacker can **read that value back**: download the file, view the blob, export the table.

Applications "whose declared lengths always match their data are not affected".[^nvd315] So the realistic victim is something like a document service that streams uploads into a `bytea` column or a large object, with a length taken from an HTTP `Content-Length` header or a metadata field that can disagree with the real body. If an attacker can make the declared length bigger than the data and then download their own "file", they get up to 8 KB of whatever the connection carried before, per upload. On a pooled connection that could be another user's query parameters. The CVSS vector reflects this: network-reachable, **high** attack complexity, low privileges, **high** confidentiality impact, no integrity or availability impact.[^nvd315]

There's a second, quieter consequence: even with no attacker at all, a buggy length calculation means your database has been storing values with junk on the end. That junk can include secrets, and it ends up in backups and replicas.

#### The other bug: a filter that filtered nothing

`requireAuth` lets the client decide which authentication methods it will accept from the server. That matters because, in Postgres, the **server** picks the method. A fake server sitting between you and the real one (a {{man-in-the-middle|an attacker who intercepts the connection and pretends to be the server to the client, and the client to the server}}) can simply ask for a cleartext password. An {{AuthenticationCleartextPassword|the server message (`R` with code 3) that tells the client to send its password unencrypted}} request is just a message with code 3.[^proto] A client that answers it hands over the password.

The idea came from libpq, the C client library. PostgreSQL 16 added a `require_auth` parameter, in a commit authored by Jacob Champion and dated 14 March 2023. It takes a comma-separated list of `password`, `md5`, `gss`, `sspi`, `scram-sha-256` and `none`. A `!` prefix turns an entry into an exclusion, you can't mix the two forms in one list, and if the server asks for a method that isn't allowed, the connection fails before any secret is sent.[^paquier] pgjdbc's `requireAuth` follows the same idea.

The bug is a classic {{fail-open|a security check that, in an unexpected case, lets everything through instead of blocking everything}} edge case. The CVE record explains: in 42.7.11–42.7.13, if the value excludes all six known methods, for example `!password,!md5,!gss,!sspi,!scram-sha-256,!none`, or contains no method at all (a lone comma), "the driver then accepts whatever method the server requests, including cleartext password authentication".[^nvd314] The weakness is filed as CWE-636, "Not Failing Securely ('Failing Open')".[^nvd314b] Positive lists like `requireAuth=scram-sha-256` and partial exclusions like `!password,!md5` were enforced correctly, and because the property has no default, deployments that never set it aren't affected.[^nvd314]

```viz:codecompare

  title: "Fail open (no check at all)"
  code: |
    # excludes every method:
    requireAuth=!password,!md5,!gss,

    requireAuth=,

right:
  title: "Enforced correctly"

    requireAuth=scram-sha-256

    requireAuth=!password,!md5
    # pair with TLS checks:
    sslmode=verify-full
note: "Behaviour from the CVE record for CVE-2026-107314. Values are shown wrapped for width."
```

Who would write a list that excludes everything? Probably nobody on purpose. It's what you get from config templating gone wrong, an empty environment variable, or an "exclude everything we don't trust" list built by a script. The point of a security setting is that its strange cases fail safe. In 42.7.14 they do: such connections are refused with {{SQLState|the standard five-character error code JDBC drivers attach to SQL exceptions}} `08004`, and an empty method value is rejected as invalid.[^nvd314b]

#### A pattern: "the setting didn't do what it said"

This is the third time in about 16 months that a pgjdbc connection setting meant to resist a man-in-the-middle turned out to be weaker than its name.

{{Channel binding|a SCRAM authentication feature that ties the login to the specific TLS connection, so a man-in-the-middle with a different certificate can't relay it}} is the other protection in this area. In June 2025, CVE-2025-49146 found that with `channelBinding=require`, pgjdbc "would incorrectly allow connections to proceed with authentication methods that do not support channel binding (such as password, MD5, GSS, or SSPI authentication)". It was fixed in 42.7.7.[^cve2025] Then CVE-2026-54291 found that 42.7.4 through 42.7.11 could silently downgrade from {{SCRAM-SHA-256-PLUS|the SCRAM password login with channel binding switched on}} to plain SCRAM-SHA-256 when the server certificate used a signature algorithm with no channel-binding hash, such as Ed25519. That was fixed in 42.7.12.[^secpage]<sup>,</sup>[^suse]

None of these is a disaster on its own. Together they make a useful lesson: a client-side security setting is only as good as its tests for the odd cases. "Exclude everything", "server picks an unusual certificate" and "the stream ended early" are exactly the cases nobody writes a test for until someone files a CVE.

### What it means for you

**Upgrade to 42.7.14.** That's the fix for both bugs, and it's a patch release in the same 42.7.x line you're probably already on. In Maven or Gradle that means bumping `org.postgresql:postgresql` to `42.7.14`.[^ann]

If you use Spring Boot, the driver's version comes from Boot's dependency management. You can override it with the `postgresql.version` property (for example `<postgresql.version>42.7.14</postgresql.version>` in a Maven POM) until your Boot version picks it up.[^boot] Check what you actually run with `mvn dependency:tree` or `gradle dependencies`. A transitive dependency can easily pin an older driver.

**If you can't upgrade today**, the advisories describe what makes you safe:

- For the padding bug, make every declared length match the data. `ByteStreamWriter.getLength()` must equal the number of bytes `writeTo()` writes, and the `(offset, length)` pairs you pass to the byte-array methods must stay inside the array. There's no connection property that turns the behaviour off.[^hol] Search your code for `ByteStreamWriter`, `CopyIn`, `PGCopyOutputStream`, `LargeObject` and `Blob.setBytes`. If none of them appear, you're very likely not exposed.
- For `requireAuth`, grep your connection strings and config for the property. An allow-list such as `requireAuth=scram-sha-256` is fine. A value that excludes every method, or is empty, is the problem. Combining it with `sslmode=verify-full` also means a man-in-the-middle has to beat certificate verification before it can ask for a password at all.

**If you think you were exposed to the padding bug**, look at stored values written through those APIs since you moved to 42.7.4 or later. If any of them were shorter than declared, their tails may contain earlier traffic. That data is in your backups and replicas too. Fixing the driver stops new leaks but doesn't clean old rows.

<div class="box realworld" markdown="1">
**🌍 In the real world**

Camunda's bump on its 8.6 branch is a good template for triage. The commit message names the CVE, notes that the branch was on 42.7.11 (inside the affected range), explains why the team believes the vulnerable path is unreachable (DataSource auto-configuration is excluded on that line, so it never opens a PostgreSQL connection), and upgrades anyway. The bump was manual because Renovate doesn't cover that branch.[^camunda] Most teams will be in the same position: probably not exploitable, cheap to fix, so fix it.
</div>

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **"Newer is safer" didn't hold here.** 42.7.3 and earlier padded with zeros. The padding leak was introduced in 42.7.4. Downgrading isn't the fix. 42.7.14 is.
- **Scanners may show odd version ranges.** One aggregator lists only 42.7.4–42.7.8 as affected by the padding bug, while the CVE text says 42.7.4–42.7.13.[^imfht] Go by the CVE text.
- **Severity labels differ.** The CVSS 3.1 scores are Medium (5.3 and 5.9),[^nvd315]<sup>,</sup>[^nvd314] but some feeds label the padding advisory "High".[^imfht] Your scanner's triage queue may sort them differently.
- **NVD analysis was still pending** when we checked, so expect scores and CPE data to change.[^nvd315]
</div>

### What happens next

The pgjdbc changelog on GitHub already has an "Unreleased" section with more fixes, mostly around XA transactions and `PGStream.skip`, so another 42.7.x will follow.[^changelog] The bigger open question is testing. Most of the recent pgjdbc security fixes came from edge cases in features that work fine on the normal path. Expect the project, and other drivers that copied libpq's `require_auth` idea, to look harder at their "everything excluded" and "short stream" cases.

# Story 2 · Cloudflare K2: a Kafka-style log with no brokers and no disks

<div class="byline">Cloudflare K2 · Public beta, announced 1 Oct 2026 · Event streaming on R2 · ~15 min read</div>

<p class="opener" markdown="1">For a decade, "event streaming" has meant Kafka, and Kafka has meant brokers: long-running servers with fast local disks, copying every byte to each other across data centres. Cloudflare just launched a streaming service with none of that. No brokers to size, no disks to fill, no partitions to rebalance. Its log lives entirely in object storage, the same kind of storage you use for images and backups. The price is about a second of latency on every write. Whether that's a bargain depends on what you stream.</p>

### What happened

On **1 October 2026**, Cloudflare announced **K2** in public beta. The post, by Micah Wylde and Marc Selwan, describes K2 as a "fully serverless" durable event-streaming service that "implements a partitioned, durable log on top of R2 object storage".[^k2blog] InfoQ covered it on 9 October, along with the Hacker News discussion that followed.[^k2infoq]

The basics, from the launch post and the docs:

- **Model:** producers write records to a **stream**, which keeps them as an ordered log for a retention period you choose. Consumers read through **subscriptions**, either sharing the work or each getting every record.[^k2blog]<sup>,</sup>[^k2docs]
- **Interfaces:** produce through a Workers binding or an HTTP API. Consume over HTTP with a lease-based API. Create streams from the dashboard, the API, Wrangler, or Cloudflare's new `cf` CLI.[^k2blog]
- **Latency:** the first release adds "about 1 second of produce latency at the 99th percentile".[^k2blog] That's Cloudflare's own figure.
- **Availability:** Workers Paid plan only.[^k2blog]
- **Price after the beta:** $0.04 per GB produced, $0.04 per GB consumed and $0.02 per GB-month retained. Nothing is billed during the beta.[^k2blog]

The limits page lists 20 streams per account, retention between 1 hour and 30 days (default 7 days), 30 MB/s of produce throughput per stream, records of up to about 1 MB and 5 MB per produce request.[^k2limits] There's one inconsistency to note: the launch post says the beta allows "10GB of storage" **per stream**,[^k2blog] while the limits page says 10 GB **total across all streams** in an account.[^k2limits] Plan for the stricter one.

### The background you need

#### What an event stream is for

An {{event stream|an append-only, ordered log of records that many independent readers can consume at their own pace}} sits between the systems that produce events and the systems that use them. Cloudflare's example is an online shop: every transaction event goes to an analytics system and a fraud-detection service. Without a buffer in between, the post points out, "events are dropped" whenever producers outrun consumers or a downstream service goes offline.[^k2blog] The stream absorbs the writes and lets each reader catch up in its own time. That decoupling is why most companies above a certain size run Kafka or something like it.

#### How Kafka does it, and what that costs

In {{Apache Kafka|the open-source distributed event-streaming platform; the de facto standard for event logs}}, a topic is split into {{partitions|independent ordered logs that together make up a topic; each is owned by one broker at a time}}. Each partition lives on the local disk of a {{broker|a Kafka server that stores partitions and serves reads and writes for them}}, and is copied to other brokers, usually in other {{availability zones|separate data centres within one cloud region, with independent power and networking}}, so that losing one machine loses nothing.

That design is fast, since you're writing to a local disk, and battle-tested. But in the cloud, the replication has a price tag. Kafka's own proposal for "diskless" topics, **KIP-1150**, says replicating active segments across zones is a major infrastructure cost for operators on the big clouds. It quotes cross-zone traffic at **$0.02 per GiB on AWS** and **$0.01 per GiB on Google Cloud**, while Azure doesn't charge for it.[^kip1150] Every byte you produce gets copied to other zones, and on AWS every copy costs money. On top of that are the operational costs: rebalancing data when you add brokers, sizing disks, replacing failed nodes.

#### The object-storage alternative

{{Object storage|storage you use through HTTP PUT and GET of whole objects (S3, R2, GCS); very durable and cheap, but slower per request than a local disk}} services already replicate data across zones and charge you for storage, not for internal copying. Cloudflare's R2 is "designed to provide 99.999999999% (eleven 9s) of annual durability", stores data across several data centres in a region, and only returns `HTTP 200` for a write "once the data has been persisted to disk".[^r2dur] So if a streaming system can keep its log in object storage, durability and replication become someone else's problem, and brokers become stateless processes you can add or remove freely.

The idea isn't new. **WarpStream** built a Kafka-compatible platform on object storage and was bought by Confluent on 9 September 2024. Confluent positioned it for "high-scale workloads with relaxed latency requirements", such as logging, observability and feeding data lakes.[^warp] Kafka itself followed. KIP-1150 was accepted on **2 March 2026**, with 9 binding votes, as the umbrella for a new topic type that writes data through to object storage and uses local disks mainly as a cache. The detailed design lives in follow-up KIPs, KIP-1163 (Diskless Core) and KIP-1164 (Diskless Coordinator), which were still being worked on when Aiven wrote about the vote.[^aiven]<sup>,</sup>[^kip1150] KIP-1150 is explicit about the cost: diskless topics "will incur higher produce latency" than classic ones.[^kip1150]

#### Why Cloudflare couldn't just run Kafka

K2 didn't start as a product. Cloudflare built it first as the durable buffer behind **Pipelines**, its serverless ingestion service (part of the Basin data platform we covered in issue #2). Pipelines runs on the Arroyo stream-processing engine, which *pulls* data, so accepted events have to be stored durably until Arroyo reads them. And Pipelines promises never to drop an accepted event.[^k2blog]

Kafka was a poor fit for where that buffer had to run. Cloudflare's network spans "over 335 cities", and its stateful services get small, short-lived slices of machines that talk to each other over the public internet, conditions in which, the post says, traditional distributed systems like Kafka are often impractical.[^k2blog] Building on R2 meant not running that kind of software at all.

### How it works

#### Problem one: object stores can't append

A log is an append-only data structure, and object stores don't support appends. You can write a whole new object, but you can't add ten bytes to the end of an existing one. Writing one object per event would be ruinous anyway, because object stores charge per request. R2's list price is **$4.50 per million** "Class A" operations, which include `PutObject`.[^r2price]

K2's answer is to batch. Writes collect in memory on an edge service, and "after a short wait for data to arrive", all of them are written to R2 as a single {{segment file|one object in storage holding a contiguous run of records from the log}}, large enough to spread the per-object cost.[^k2blog] That short wait is where the second of produce latency comes from. It's a dial between latency and cost, and Cloudflare has set it to "about a second" for now.

How much does that dial matter? Here's a back-of-the-envelope calculation using R2's public PUT price. It's our arithmetic, not Cloudflare's: K2's internal costs and exact flush interval aren't published.

Flushing every 10 ms instead of every second multiplies the request bill by 100, for every stream. That's the basic economics of object-storage streaming. A competitor said as much in the Hacker News thread: "One of the tensions of course is how long to linger before flushing to object storage."[^k2infoq]

#### Problem two: ordering without a coordinator

A log also needs ordering: every record gets a strictly increasing {{offset|a record's position in the log; consumers track how far they've read by offset}}. In Kafka, the partition's leader broker hands those out. Many object-storage designs add a separate metadata service or database to do it.

K2 skips that. The post says it uses R2's "atomic operations" to get ordering and strictly increasing offsets, so it doesn't need a separate coordination service.[^k2blog] It doesn't say which operations. Object stores commonly offer conditional writes, where a write only succeeds if the object doesn't exist yet or hasn't changed, and that's the usual building block for this kind of trick. But Cloudflare hasn't said that's what K2 uses and has promised a separate technical deep dive.[^k2blog]

#### Producing

The launch post shows a Worker producing through a binding.[^k2blog] Adapted from that example, it looks like this:

```js
const result = await env.EVENTS.send([
  { content: JSON.stringify({ type: "page_view", path: url.pathname }) },
]);
if (!result.success) {
  console.error(result.error);
  return new Response("try later", {
    status: result.error.retryable ? 503 : 500,
  });
}
```

K2 stores record content as plain bytes, so choosing JSON, Avro or Protobuf is up to you.[^k2blog] Records can also carry up to 32 headers.[^k2limits]

#### Consuming: leases, not partitions

This is where K2 differs most from Kafka. A Kafka consumer group assigns whole partitions to consumers and each consumer commits offsets. K2's consumer API doesn't expose partitions at all. Instead it works more like a job queue:[^k2consume]

1. You create a **subscription** with `start_at` set to `earliest` (oldest retained record) or `latest`. Subscriptions can't be changed after creation, and a stream can have up to 100.
2. A worker calls `consume` with a `worker_id` and `max_records` (up to 10,000). It gets back a `batch_id`, the records, and `leased_until_ms`.
3. The batch is leased to that worker for **five minutes**. K2 "never leases the same records to two workers at once", and a subscription can have up to 128 active leases.
4. The worker then **acks** the batch (done), **nacks** it (send it to someone else now), or **extends** the lease by another five minutes. If the lease expires, the records go to the next worker that asks.

```bash
curl "$K2_ENDPOINT/subscriptions/$SUB_ID/consume" \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"worker_id": "worker-1", "max_records": 100}'
```

Two details are easy to miss. First, a nacked batch blocks progress: "The subscription does not advance past these records until the redelivered batch is acked."[^k2consume] One poison batch that always fails can stall a whole subscription, and there's no dead-letter queue. Second, the guarantees are modest. Delivery is **at least once**, so your consumer must cope with duplicates, and ordering is not guaranteed across workers sharing a subscription.[^k2consume] {{At-least-once delivery|every record is delivered one or more times, so duplicates are possible and consumers must be idempotent}} is normal for streaming, but losing ordering across workers is a real difference from Kafka, where each partition is read in order by exactly one consumer in a group.

Why this design? The K2 tech lead, posting on Hacker News, said he finds the Kafka API "too low-level for typical users and too high-level for deep integration with stream processing engines". The team argues that leases suit Workers, which "parallelize well but are individually weak": many small workers can each grab a batch, without partitions limiting how many can read at once.[^k2infoq] Kafka has been moving in a similar direction. Its **share groups** ("Queues for Kafka"), declared production-ready in Kafka 4.2 in February 2026, bring queue-style consumption with acquisition locks on records, and KIP-1222 added a way to "extend acquisition lock timeouts on records requiring longer processing times".[^kafka42]

{{Lease|a time-limited claim on some work; if the holder doesn't finish or renew it in time, the work is handed to someone else}} is the key word in both designs: neither trusts a consumer to stay alive, so unfinished work goes back to the pool when a lease or lock runs out.

#### What the first testers saw

The Hacker News thread produced the first independent numbers, and they're less flattering than the headline. One beta user reported writes under a second, but **end-to-end** delivery (produce to consume) of **2.5 seconds at p95 and 7.5 seconds at p99**. Someone answering for the team said the tail was higher than they'd expect, that the consume API needs performance work, and that read-latency improvements should land within about a week.[^k2infoq] That's one user's measurement with an undescribed setup, so treat it as an early data point, not a benchmark.

A commenter who disclosed that he works on competitor S2 (s2.dev) argued that object-storage streams can do far better: faster single-zone tiers like S3 Express still need quorum writes across zones for regional durability, but he said his service reaches about 50 ms p99 acknowledgement in the same region.[^k2infoq] That's a competitor's own claim, but it shows how much the batching window, not object storage itself, decides the latency.

### What it means for you

**K2 is a good fit when latency in seconds is fine and you're already on Cloudflare.** Think analytics events, logs, clickstreams, audit trails, fan-out to a few slow consumers, or a buffer in front of a data lake. If the data ends up as files or Iceberg tables in R2 anyway, Cloudflare itself recommends Pipelines rather than K2. K2 is for custom processing or other destinations.[^k2blog] For individual work items that need retries, delays and dead-letter queues, Cloudflare points you to its Queues product instead.[^k2blog]

**It's not a Kafka replacement yet.** There are no Kafka clients (they're on the roadmap), no message keys or key-based ordering, retention tops out at 30 days unless you ask for more, and the beta caps storage at 10 GB.[^k2blog]<sup>,</sup>[^k2limits] If your consumers depend on per-key ordering, such as applying updates to an account in sequence, K2 can't give you that today.

**Do the cost maths with fan-out in mind.** At $0.04 per GB produced plus $0.04 per GB consumed, one consumer costs $0.08 per GB moved, and each extra subscription adds another $0.04.[^k2blog] A commenter pointed out exactly this, though the same commenter also argued K2 would still undercut Google Pub/Sub for long retention and managed Kafka for the effort saved.[^k2infoq] Five subscriptions on 1 TB a day is about $240 a day at list price ($40 produce plus $200 consume), before retention. That's our arithmetic from the published prices.

<div class="box gotcha" markdown="1">
**💥 Watch out for**

- **Beta limits disagree.** The launch post says 10 GB storage per stream; the limits page says 10 GB per account. Assume the smaller.[^k2blog]<sup>,</sup>[^k2limits]
- **One stuck batch stalls a subscription.** Nacked records block progress until they're acked, and there's no dead-letter queue. Build your own "give up and park it" logic.[^k2consume]
- **Don't retry `10218`.** If extending a lease fails with that code, the lease is gone. Stop processing and fetch a new batch, or you'll process records another worker now owns.[^k2consume]
- **Latency numbers are early.** Cloudflare's ~1 s p99 is for produce, not end-to-end, and is a vendor figure. One tester saw 7.5 s p99 end to end.[^k2infoq]
</div>

### What happens next

Cloudflare's roadmap lists multi-GB/s write parallelism, message keys with key-based ordering, push-based Worker consumers, a lower-latency **Express** tier, and drop-in support for Apache Kafka clients.[^k2blog] The Express tier is the one to watch: it's an admission that a second is too slow for many uses, and S2's numbers suggest how far object-storage designs can go. Meanwhile, Kafka's own diskless topics still need KIP-1163 and KIP-1164 to land before you'll see them in a release.[^aiven] If they do, you'll get roughly the same trade-off (cheaper, slower writes) on a per-topic basis inside Kafka.

<div class="box glossary" markdown="1">
**📖 Words from this story**

- **Event stream**: an append-only, ordered log of records that many readers consume at their own pace.
- **Apache Kafka**: the open-source distributed event-streaming platform; the de facto standard for event logs.
- **Partitions**: independent ordered logs that together make up a Kafka topic.
- **Broker**: a Kafka server that stores partitions and serves reads and writes for them.
- **Availability zones**: separate data centres in one cloud region with independent power and networking.
- **Object storage**: storage used via HTTP PUT/GET of whole objects (S3, R2, GCS); durable and cheap but slower per request.
- **Segment file**: one stored object holding a contiguous run of log records.
- **Offset**: a record's position in the log, used by consumers to track progress.
- **At-least-once delivery**: every record is delivered one or more times, so consumers must handle duplicates.
- **Lease**: a time-limited claim on work that goes back to the pool if not finished or renewed.
</div>
