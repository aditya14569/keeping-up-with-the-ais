# Part 1 · Learn

## 🧱 How a database stores a row: pages, heaps and the B-tree

<span class="tag learn">FOUNDATIONS</span><span class="tag learn">~10 MIN</span><span class="tag learn">LEVEL 3</span>

**You've written `SELECT * FROM users WHERE id = 42` thousands of times. Do you know how many disk reads it costs, or why a random UUID primary key can make inserts slower?** Almost every database performance conversation, from indexes and bloat to VACUUM, cache hit ratios and "why is this insert slow", comes back to one idea: **the page**.

### The unit of everything: the page

Disks and SSDs are slow compared with RAM, and they're happiest moving data in chunks. So relational databases never read or write a single row. They move **fixed-size pages**:

- **PostgreSQL:** 8 kB pages by default (set at compile time). [(PostgreSQL docs)](https://www.postgresql.org/docs/current/storage-page-layout.html)
- **MySQL InnoDB:** 16 kB pages by default (set with `innodb_page_size` when the instance is initialised). [(MySQL docs)](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

A table is a file of pages. An index is another file of pages. A hot page lives in RAM in the **buffer pool** (Postgres calls it *shared buffers*), so the database can skip the disk entirely. That's why "does my working set fit in memory?" is the first question in any database sizing discussion.

### Inside a Postgres page

Here's the part most developers never see. Each 8 kB Postgres page has a small **header (24 bytes)**, then an array of **line pointers (4 bytes each)** growing forward, then **free space**, then the actual **row versions ("tuples")** packed from the *end* of the page backwards. [(PostgreSQL docs)](https://www.postgresql.org/docs/current/storage-page-layout.html)

Why the indirection? A row's address, its **`ctid`**, is *(page number, line-pointer number)*. Because line pointers never move, Postgres can shuffle tuples around inside a page to compact free space without breaking any index that points at them. [(PostgreSQL docs)](https://www.postgresql.org/docs/current/storage-page-layout.html)

### Two philosophies: heap vs clustered index

Here Postgres and MySQL take genuinely different paths, and it changes how you should design primary keys.

```viz:versus
title: "Where does the row actually live?"
left:
  emoji: 🐘
  title: "PostgreSQL: heap + separate indexes"
  points:
    - "The table is a **heap**: rows go wherever there's free space"
    - "**Every** index, including the primary key, is a separate B-tree whose leaves hold a `ctid`"
    - "A lookup = walk the index → jump to the heap page"
  example: "users_pkey: 42 → (page 7, item 3)"
right:
  emoji: 🐬
  title: "InnoDB: the table IS the PK B-tree"
  points:
    - "Rows are stored **inside the primary-key B-tree** (the clustered index)"
    - "Secondary index leaves store the **primary key value**, not a physical address"
    - "Lookup by email = email index → PK → clustered index"
  example: "idx_email: a@b.in → id 42 → row"
note: "Sources: [PostgreSQL storage docs](https://www.postgresql.org/docs/current/storage-page-layout.html), [MySQL: clustered and secondary indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)."
```

MySQL's docs spell out the consequence: because every secondary index carries the primary key, **"if the primary key is long, the secondary indexes use more space, so it is advantageous to have a short primary key."** [(MySQL docs)](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

### The B-tree in one picture

A B-tree is a **balanced tree of pages**. Each internal page holds many sorted keys plus pointers to child pages, and the leaves hold the entries. Because one page holds many keys, the tree is very wide and very shallow. Every leaf is the same distance from the root, so a lookup costs a handful of page reads even for huge tables, and that cost grows **logarithmically** with table size. [(Use The Index, Luke)](https://use-the-index-luke.com/sql/anatomy/the-tree)

<div class="box realworld" markdown="1">
**🌍 In the real world: the random-UUID primary key**

A very common pattern: an `orders` table in MySQL keyed by a random **UUIDv4**. Each new key lands at a random spot in the clustered B-tree, so inserts hit random pages all over the index instead of appending to the end. InnoDB's own docs describe the effect. With **sequential** inserts, pages fill to about **15/16**, but with **random** inserts they end up anywhere **between 1/2 and 15/16 full**. [(MySQL docs)](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html) The result is more pages, more page splits, a bigger index competing for the buffer pool, and slower inserts as the table grows.

The fix that's become standard: **time-ordered IDs**. New keys sort near each other, so inserts append to the "right edge" of the tree. **PostgreSQL 18 added a built-in `uuidv7()`** for exactly this: a UUID whose leading bits are a millisecond timestamp. [(PostgreSQL 18 docs)](https://www.postgresql.org/docs/18/functions-uuid.html) You keep globally unique IDs without the random-insert penalty.
</div>

<div class="box gotcha" markdown="1">
**💥 Gotcha: in Postgres, an UPDATE is really an INSERT**

Look at the tuple header again: every row version records `xmin` (the transaction that created it) and `xmax` (the one that deleted or replaced it). [(PostgreSQL docs)](https://www.postgresql.org/docs/current/storage-page-layout.html) When you `UPDATE` a row, Postgres doesn't overwrite it. It writes a **new tuple** and marks the old one dead. Dead tuples stay on the page until **VACUUM** cleans them up. Skip that and a heavily updated table "bloats": it gets bigger and slower even though the row count hasn't changed. One mitigation is the table's **`fillfactor`** (default 100, meaning pages are packed full). Lowering it to around 80–90 on update-heavy tables leaves room for the new version on the *same* page, which makes cheap "HOT" updates more likely. [(PostgreSQL docs)](https://www.postgresql.org/docs/current/sql-createtable.html) MVCC and VACUUM get their own issues soon.
</div>

<div class="box devs" markdown="1">
**🔬 Under the hood**

- **The 23-byte tuple header** holds `t_xmin`, `t_xmax`, `t_cid`, a 6-byte `t_ctid` pointing to the newer version of the row (if any), flags and the offset to your data. That's why a table of tiny rows is mostly overhead. [(PostgreSQL docs)](https://www.postgresql.org/docs/current/storage-page-layout.html)
- **InnoDB with no primary key** quietly picks the first `UNIQUE NOT NULL` index, and failing that generates a hidden clustered index on a synthetic row-ID column (`GEN_CLUST_INDEX`). You don't control it, so always declare a primary key. [(MySQL docs)](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)
- **InnoDB merges pages** when they drop below `MERGE_THRESHOLD` (50% by default), shrinking the tree after deletes. [(MySQL docs)](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)
</div>

**🧪 Try it (15 minutes, Docker)**

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=pw postgres:18

```

```sql
CREATE TABLE t (id int, note text);
INSERT INTO t SELECT g, 'row ' || g FROM generate_series(1, 5) g;
SELECT ctid, * FROM t;                 -- (0,1) … (0,5): page 0, items 1–5
UPDATE t SET note = 'changed' WHERE id = 2;
SELECT ctid, * FROM t;                 -- id 2 now lives at (0,6): a new tuple!
CREATE EXTENSION pageinspect;
SELECT lower, upper, pagesize FROM page_header(get_raw_page('t', 0));
SELECT lp, t_xmin, t_xmax, t_ctid FROM heap_page_items(get_raw_page('t', 0));
```

In the last query, the old version of row 2 shows a non-zero `t_xmax` and a `t_ctid` pointing to (0,6). That's MVCC on the actual bytes. `lower` and `upper` are where the free space starts and ends. (`pageinspect` needs a superuser, which `postgres` is.) [(pageinspect docs)](https://www.postgresql.org/docs/current/pageinspect.html)

### Use it tomorrow: see the pages your query touches

All of this is visible from SQL. In Postgres 18, `EXPLAIN ANALYZE` automatically reports **buffers**: how many pages a query found in cache (**hit**) and how many it had to fetch from storage (**read**). [(PostgreSQL docs)](https://www.postgresql.org/docs/current/sql-explain.html)

```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE id = 42;
--  Index Scan using users_pkey on users ...
--    Index Cond: (id = 42)
--    Buffers: shared hit=4          <- 3 index pages + 1 heap page, all from RAM
```

The output above is illustrative, but the shape is what you'll see. **A point lookup should touch a handful of pages.** If the same query reports thousands of buffers, it isn't using the index you think it is. If `read` is high and `hit` is low, your working set doesn't fit in memory. Four habits that follow from today's model:

1. **Read `Buffers:` before you read timings.** Time varies with load; page counts don't lie.
2. **Pick primary keys deliberately.** Short and time-ordered (`bigint` identity, or `uuidv7()`) beat random UUIDs, especially in InnoDB, where every secondary index carries the key.
3. **Give update-heavy Postgres tables room to breathe** with `fillfactor` below 100, and watch for bloat.
4. **Size memory for the hot pages, not the whole database.** A 500 GB database with a 20 GB hot set behaves very differently from one that touches everything.

## Top story 1 · PostgreSQL 19 cuts five features to ship on time

<span class="tag hot">POSTGRES</span><span class="tag watch">RC EARLY OCTOBER</span>

**What happened.** **PostgreSQL 19 Beta 4** shipped on **24 September**, and it's notable for what it *removed*. The project reverted several headline features rather than ship them half-baked. A release candidate is planned for **early October**, and GA "may also occur in October." The release note puts it bluntly: *"PostgreSQL must be reliable."* [(PostgreSQL 19 Beta 4)](https://www.postgresql.org/about/news/postgresql-19-beta-4-released-3386/)

**Why it matters.** Two of the survivors hit everyday pain directly. **Autovacuum scoring** changes how Postgres decides which tables to vacuum first. That matters for exactly the bloat problem in today's gotcha. **`REPACK`** targets reclaiming space from bloated tables. And the cuts are a healthy sign: Postgres ships every year, on schedule, because it's willing to drop what isn't ready. The reverted features may come back in a later release.

**The date to put in your calendar:** **PostgreSQL 14's final release is 12 November 2026.** After that it gets no bug or security fixes. Each major version is supported for five years, and 15 follows in November 2027. [(postgresql.org versioning)](https://www.postgresql.org/support/versioning/)

## Top story 3 · Databricks makes change data automatic and Iceberg sharing copy-free

<span class="tag dev">DATABRICKS</span><span class="tag try">GA</span>

**What happened.** Databricks' September release notes include several quiet but significant changes [(Databricks release notes)](https://docs.databricks.com/aws/en/release-notes/product/2026/september):

- **Automatic Change Data Feed (Auto CDF).** Row-level changes are computed at query time, with no need to enable CDF on each table first. Databricks says MERGE/UPDATE operations run about **15% faster**.
- **Share foreign Delta and Iceberg tables** via OpenSharing, without copying the data into Databricks first.
- **Query history system table (GA):** account-wide records of every query on SQL warehouses and serverless compute, with execution metrics.
- **Managed agent memory and sessions (beta),** backed by Lakebase, Databricks' Postgres-compatible operational database.

Copy-free Iceberg sharing continues the industry's shift: **open table formats as the common layer**, with each engine (Databricks, Snowflake, ClickHouse, Fabric) querying the same files.
