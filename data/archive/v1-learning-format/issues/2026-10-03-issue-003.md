# Part 1 · Learn

## ⚡ Redis I: data structures, one thread, and why it's fast

<span class="tag learn">SYSTEMS</span><span class="tag learn">~10 MIN</span><span class="tag learn">LEVEL 3</span>

**Your Postgres is running dozens of backend processes, a buffer pool and a WAL writer. Redis runs your commands on one thread, and it's still usually the fastest thing in your stack.** That sounds backwards until you see where the time actually goes. In the last two issues we followed a row through pages on disk and an index through a B-tree. Redis skips nearly all of that: **the data is in RAM, the structures are built for the commands, and nothing waits on a lock.**

### Four reasons Redis is fast

1. **Everything is in memory.** There's no buffer pool deciding what's hot and no page to fetch from disk. Every read touches RAM.
2. **One thread runs the commands.** Redis's own course puts it this way: single-threading **avoids race conditions and CPU-heavy context switching**, and **CPU is rarely the bottleneck**; you usually run out of memory or network first. [(Redis University)](https://redis.io/learn/operate/redis-at-scale/talking-to-redis/redis-server)
3. **Purpose-built encodings.** Small hashes, sets and sorted sets are stored as compact byte arrays instead of pointer-heavy hash tables. That saves memory and keeps data close together in CPU cache.
4. **Non-blocking I/O.** One event loop watches every client socket at once, so a slow client never holds up a fast one.

### The event loop: one thread, many clients

Redis doesn't use a library like libevent. It has its own small event library, **`ae`**, which wraps the operating system's readiness API (`epoll` on Linux). The loop registers sockets with the OS, waits until some are ready, then runs the callbacks for those: accept a connection, read a query, write a reply. Timers for periodic housekeeping run on the same loop. [(Redis docs: event library)](https://redis.io/docs/latest/operate/oss_and_stack/reference/internals/internals-rediseventlib/) Eli Bendersky's walkthrough of the source sums up the bet: Redis is **network-bound, spending much more time waiting on the network than inside its data structures**, so non-blocking I/O on one thread is enough. [(Eli Bendersky)](https://eli.thegreenplace.net/2017/concurrent-servers-part-5-redis-case-study/)

The pay-off is that **every command is atomic for free**. `INCR`, `LPUSH`, `ZADD`: no other command can run halfway through yours, because there is no other command running. You get this guarantee without any locks.

**"Single-threaded" isn't quite true any more.** Redis has used background threads for disk work since 2.4, for example the `fsync` behind `appendfsync everysec`. [(Redis docs: latency)](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/) Redis 6.0 added **I/O threads** for socket reads and writes, which Redis says boosts throughput by **up to 2× for some workloads**. [(Redis University)](https://redis.io/learn/operate/redis-at-scale/talking-to-redis/redis-server) Redis 8.0 replaced them with a new asynchronous implementation, still enabled with `io-threads`. [(Redis 8.0 release notes)](https://redis.io/docs/latest/operate/oss_and_stack/stack-with-enterprise/release-notes/redisce/redisos-8.0-release-notes/) The key detail: **I/O threads read, parse and write, but the main thread still executes every command.**

### The data structures and their secret second form

Every Redis type has **two encodings: a compact one for small values and a general one for big values.** Redis switches automatically when a value outgrows the compact form. You can see which one you have with `OBJECT ENCODING key`. [(Redis docs)](https://redis.io/docs/latest/commands/object-encoding/)

| Type | Small encoding | Large encoding | Switches when (defaults, Redis ≥ 7) |
|---|---|---|---|
| String | `int` / `embstr` | `raw` | `embstr` holds up to **44 bytes** |
| Hash | `listpack` | `hashtable` | > **512** fields or a value > **64** bytes |
| Sorted set | `listpack` | `skiplist` (+ hash table) | > **128** members or a member > **64** bytes |
| Set | `intset` / `listpack` | `hashtable` | > **512** integers; > **128** strings (7.2+) |
| List | `listpack` nodes | `quicklist` | a linked list of listpacks |
| Stream | n/a | `stream` | a radix tree of listpacks |

Thresholds from the [memory optimization docs](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/) and [`OBJECT ENCODING`](https://redis.io/docs/latest/commands/object-encoding/). They are tunable with `hash-max-listpack-entries` and similar settings.

A **listpack** stores entries back to back in one block of memory. Finding a field means scanning it, which is O(N), but N is capped at a few hundred and the scan is cache-friendly. Redis says these special encodings use **up to 10× less memory (5× on average)**. [(Redis docs)](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

Sorted sets deserve a special mention: the large form is a **skip list plus a hash table**. The skip list keeps members ordered by score for `ZRANGE` and rank queries, and the hash table answers `ZSCORE` in O(1). It's the reason leaderboards and rate limiters are a natural fit for Redis.

### The price of one thread: one slow command blocks everyone

Since commands run one after another, **the latency of the slowest command is added to every command queued behind it.** Redis's latency guide is blunt: `GET`, `SET` and `LPUSH` are fine, but O(N) commands such as `SORT`, `LREM` and `SUNION` on big values hurt, and **`KEYS` should only be used for debugging**. Use `SCAN`, `HSCAN`, `SSCAN` and `ZSCAN` to iterate in small steps, and watch `SLOWLOG`. [(Redis docs: latency)](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

Deleting is a hidden case. `DEL` on a key with millions of elements frees every allocation on the main thread. **`UNLINK` removes the key from the keyspace in O(1) and frees the memory in another thread.** [(Redis docs)](https://redis.io/docs/latest/commands/unlink/)

The other classic stall is **`fork()`**. RDB snapshots and AOF rewrites fork the process, and copying the page tables blocks the main thread for a time that grows with the dataset size:

<div class="box realworld" markdown="1">
**🌍 In the real world: Instagram's 300 million keys**

Instagram needed to map about **300 million photo IDs to the user IDs** that owned them. Stored as plain string keys, a test of 1 million keys took about **70 MB**, which projected to roughly **21 GB** for the full set. The fix used the compact encoding from today's table: split each media ID into a **bucket** (the ID divided by 1,000) and store the pairs as fields in a hash per bucket, with the hash encoding limit tuned to about 1,000 entries. One million keys then took about **16 MB**, and the whole dataset fit in **just under 5 GB**. [(Instagram Engineering)](https://instagram-engineering.com/storing-hundreds-of-millions-of-simple-key-value-pairs-in-redis-1091ae80f74c) The Redis docs describe the same trick and measured **11 MB → 1.7 MB** for 100,000 objects. [(Redis docs)](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)
</div>

<div class="box gotcha" markdown="1">
**💥 Gotcha: the cache that never evicts**

On 64-bit systems **`maxmemory` defaults to 0, meaning no limit**, so a "cache" grows until the OS kills it. [(Redis docs: eviction)](https://redis.io/docs/latest/develop/reference/eviction/) Setting a limit isn't enough on its own: the **`volatile-*` policies only evict keys that have a TTL, and behave like `noeviction` if none do**. Then writes start failing with OOM errors while reads keep working. Managed services pick their own defaults; Google's Memorystore for Redis, for example, defaults to **`volatile-lru`**. [(Google Cloud)](https://docs.cloud.google.com/memorystore/docs/redis/supported-redis-configurations?hl=de) Check with `CONFIG GET maxmemory-policy`. For a pure cache, the Redis docs call **`allkeys-lru` a good default**. Also leave headroom: replication and AOF buffers **don't count toward `maxmemory`**. [(Redis docs: eviction)](https://redis.io/docs/latest/develop/reference/eviction/)
</div>

### Use it tomorrow

1. **Never run `KEYS` in production.** Use `SCAN` and its type-specific variants.
2. **Use `UNLINK` instead of `DEL`** for anything that might be big.
3. **Keep hashes and sorted sets under the listpack limits** when you have millions of small objects. Bucket them if needed.
4. **Set `maxmemory` and a policy that matches your keys**, and check what your managed service picked for you.
5. **Pipeline batches** of commands, in chunks (the docs suggest about 10k), because the server holds the replies in memory until you read them.

<div class="box devs" markdown="1">
**🔬 Under the hood**

- **Expiry is lazy plus sampled.** On top of expiring keys when they're accessed, Redis runs an active cycle **10 times a second**, sampling **20 keys** with a TTL and deleting the expired ones. **If more than 25% of a sample has expired, it repeats.** A huge batch of keys expiring in the same second can therefore block the server. Add jitter to your TTLs. [(Redis docs: latency)](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- **LRU is approximate.** Redis samples **`maxmemory-samples` (5)** keys and evicts the oldest, keeping a pool of good candidates since 3.0. Raising it to 10 gets very close to true LRU, at some CPU cost. **LFU** uses a probabilistic **Morris counter** (0–255) that decays every minute by default. [(Redis docs: eviction)](https://redis.io/docs/latest/develop/reference/eviction/)
- **New in 8.6: LRM eviction.** `allkeys-lrm` updates the timestamp only on writes, so it evicts data that hasn't **changed** recently, even if it's read a lot. [(Redis docs: eviction)](https://redis.io/docs/latest/develop/reference/eviction/)
- **Find your floor.** `redis-cli --intrinsic-latency 100` measures what the OS and hypervisor add before Redis does anything. The docs cite about **0.115 ms** on a physical server versus up to **40 ms** in a bad virtualized environment. [(Redis docs: latency)](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
</div>

## Top story 1 · Databricks: deleting a pipeline no longer deletes its tables

<span class="tag hot">BEHAVIOUR CHANGE</span><span class="tag dev">DATABRICKS</span>

**What happened.** On **25 September**, Databricks changed the default: when you delete a **Unity Catalog pipeline** that uses the default publishing mode, **the UI and the Pipelines `DELETE` API now keep its materialized views, streaming tables and views**. To delete them along with the pipeline, set **`cascade` to `true`** in the API request. [(Databricks release notes)](https://docs.databricks.com/aws/en/release-notes/product/2026/september)

The same week brought two more governance changes. **Query tags for SQL warehouses** went GA on **30 September**: custom key-value tags on SQL workloads that show up in `system.query.history`, for grouping, filtering and **cost attribution**. And **ABAC row filters and column masks now apply to views** (Beta, Databricks Runtime 19+). [(Databricks release notes)](https://docs.databricks.com/aws/en/release-notes/product/2026/september)

**Why it matters.** It's the safer default, since nobody loses a table by deleting the wrong pipeline. But **automation that relied on cascade-by-default will now leave orphaned tables behind**, still costing storage and still visible to anyone with grants on the schema.

<div class="box care" markdown="1">
**👀 What to do.** Search your Terraform, CI and cleanup scripts for pipeline deletes. Where tables should go with the pipeline, add `cascade: true` explicitly. If you pay one Databricks bill across several teams, start tagging warehouse queries now so next month's cost report can be split by team.

## Top story 2 · Perplexity swaps DynamoDB for its own Rust key-value store

<span class="tag dev">CASE STUDY</span><span class="tag watch">KEY-VALUE</span>

**What happened.** InfoQ reported on **25 September** that Perplexity built **CobbleDB**, a distributed key-value store in Rust, to serve batched document lookups for its answer engine in place of DynamoDB. Perplexity gave three reasons. Usage-based pricing became unsustainable at **200,000+ requests per second**, since every byte transferred is billed. Tail latency was a black box it couldn't tune. And bulk reprocessing jobs competed with live user reads. [(InfoQ)](https://www.infoq.com/news/2026/09/cobbledb-perplexity/)

**How it's built.** **RocksDB** with memory-mapped caching on local **NVMe** disks, **three replicas per partition** with **asynchronous replication**, which means eventual consistency. A stateless router handles zone affinity and **hedged requests**, and a batched `MultiGet` API cuts round trips. Writes arrive as batches from S3, so heavy ingestion is kept away from serving. It was about **40,000 lines of Rust** written in **two months** by two engineers plus AI coding agents, and Perplexity says it plans to open-source it. [(InfoQ)](https://www.infoq.com/news/2026/09/cobbledb-perplexity/)

For most teams, a managed store is still the right call. The lesson is to know **which line on the bill grows with your payload size**.

<div class="box care" markdown="1">
**👀 Should you care?** Only if a managed key-value store is a top-three line on your bill. If it is, check whether you're paying per request, per byte or per capacity unit, and whether batching reads (`BatchGetItem`, `MGET`, `MultiGet`) would cut it before you think about building anything.

## Top story 3 · Meta puts a proxy in front of ZippyDB to stop connection storms

<span class="tag dev">CASE STUDY</span><span class="tag learn">ARCHITECTURE</span>

**What happened.** Meta described **ZGateway**, a stateless proxy between clients and **ZippyDB**, its distributed key-value store for metadata, counters and configuration. More than **one million client hosts** connecting directly created a many-to-many mesh, and **connection storms** caused file-descriptor exhaustion and out-of-memory errors on database servers. ZGateway now handles **over 1 billion operations per second**, about **40% of ZippyDB traffic**, and cuts **per-host connections by 97–98%** (about **19× fewer** persistent connections). It also batches and coalesces requests, enforces **per-tenant admission control**, and sheds load under overload. [(InfoQ)](https://infoq.com/news/2026/09/meta-zgateway-zippydb-proxy), from [Meta's engineering post](https://engineering.fb.com/2026/09/03/core-infra/zgateway-proxy-zippydb-meta/)

**Why it matters.** At scale, **connections become a resource you have to manage on their own**, separate from queries. Each connection costs memory and a file descriptor on the server, even for a single-threaded engine like Redis. It's the same problem PgBouncer solves for Postgres (a later Learn topic) and that Redis proxies solve for big clusters. **If your client count grows with your pod count, you'll hit this long before you hit CPU limits.**

<div class="box revision" markdown="1">
**📌 Revision card**

- Redis is fast because data is **in RAM**, commands run on **one thread** with no locks, and small values use **compact encodings**.
- The **`ae` event loop** uses `epoll` to serve many clients. Every command is **atomic** because nothing else runs at the same time.
- **I/O threads** (6.0; rebuilt in 8.0) read, parse and write. The **main thread still executes** every command.
- Small hashes/zsets/sets are **listpacks**; past **512** hash fields or **64**-byte values they become hash tables. Check with `OBJECT ENCODING`.
- One slow command blocks all clients: **no `KEYS`**, use `SCAN`; **`UNLINK`** instead of `DEL`; watch `SLOWLOG`.
- **`fork()` pauses grow with memory size**; disable transparent huge pages.
- **`maxmemory` 0 = unlimited** on 64-bit; `volatile-*` with no TTLs **acts like `noeviction`**.
- **Databricks pipeline delete now keeps tables**: add `cascade: true` where you mean it.
